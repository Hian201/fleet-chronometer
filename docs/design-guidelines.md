# 設計綱要（UI／圖示）

本文彙整**目前實際採用**的視覺決定，作為之後提出介面修改或圖示設計時的討論基準。
不是重新設計，是把已經做出來、且已驗證可行的選擇記下來，避免同一問題在不同時間點
用不同答案解決（例如字距曾經四處各自硬寫死不成比例的值）。

有明確理由被否決的方向也記在這裡（見「刻意不做的事」）——下次有人（包含未來的我）
提議同樣的方向時，不必重新推導一次為什麼不做。

三個擴充頁面（`panel/index.html`／`overview/index.html`／`popup/index.html`）
**各自一份 `<style>`，刻意不抽共用 CSS 檔**（popup 的註解已寫明：頁面太小不值得抽）。
本綱要是三份之間的一致性契約——改一處規則時，三份都要跟著改。

## 1. 色彩系統

### 1.1 角色變數（非直接色碼）

所有元件一律吃 CSS 變數，不直接寫色碼。深色為預設，`:root[data-theme="light"]`
覆蓋。變數命名是**角色**（這個顏色扮演什麼功能），不是色相本身：

| 變數 | 深色 | 淺色 | 角色 |
|---|---|---|---|
| `--bg` | `#10151d` | `#eef0f4` / `#f2f0ea` | 頁面底色 |
| `--panel` | `#182030` | `#ffffff` | 卡片/區塊底色 |
| `--line` | `#2a3548` | `#d3d8e2` / `#d8d2c4` | 邊框、分隔線 |
| `--text` | `#cfd6e4` | `#26303f` / `#2c2f36` | 主要文字 |
| `--dim` | `#7d8aa0` | `#6b7688` / `#6b7280` | 次要/輔助文字 |
| `--brass` | `#b8860b` | `#9a6b0b` / `#8a6d1a` | 標題級距標籤、強調邊框（黃銅） |
| `--sparkle` | `#e6c35c` | `#8a6d1a` | 高亮強調（提督名、選中狀態、金色系數值） |
| `--stub` | `#4a5468` | `#aab3c2` | 停用/佔位狀態 |

> overview 目前把 `--brass`/`--sparkle` 兩個角色的深淺色合流成同一個 `#8a6d1a`
> （見 [index.html:40-41](../entrypoints/overview/index.html#L40)）——這是初版佔位，
> 兩者角色不同（強調邊框 vs. 高亮強調），未來調亮色主題時應該分開，不必照抄現狀。

**新增變數前先問**：這是新角色，還是既有角色換個名字？八個角色已覆蓋大部分情境，
新增前先確認現有變數是否已經夠用。

### 1.2 語意色（不隨主題變化）

傷害/狀態類顏色是**語意色**，深淺主題共用同一組值——它們傳達的是遊戲內客觀狀態
（大破／中破／小破），不是裝飾，換主題不應該改變讀法：

```
--dmg-major: #e05555   /* 大破 */
--dmg-mid:   #e08b3d   /* 中破 */
--dmg-minor: #d4b83a   /* 小破 */
```

rank 顏色同理（`sortie-log` 等分區的 `.rank-s/.rank-a/.rank-b`）固定值，不吃主題變數。

出擊標籤狀態（`event-ops` 分區）是**另一組獨立的語意色**，同樣不隨主題變化：

```
--sally-ok:      #5f9e6b   /* 已持有本關卡允許的標籤 */
--sally-blocked: #b8524d   /* 持有別的標籤 → 這隊走不了這條路線 */
--sally-stamp:   #c98a35   /* 無標籤 → 出擊後會被貼上，不可逆消耗 */
```

**刻意與 `--dmg-*` 取不同色值**（而非直接複用紅／橙）：標籤狀態講的是「這隊能不能走這條
路線」，與大破／中破／小破是兩套完全無關的語意，共用色值會讓兩者互相稀釋（見 4.5）。

資源消長（`resource-log` 分區）是**第三組獨立語意色**，同理不隨主題變化、不挪用上面兩組：

```
--res-gain:  #2f8fcf   /* 資材增加 */
--res-drain: #cf7526   /* 資材消耗 */
```

**這組色值是算出來的，不是挑出來的**：用 dataviz skill 的 `validate_palette.js`
對深色 `#182030` 與亮色 `#ffffff` 兩種底色各跑一次，四項檢查（OKLCH 亮度帶／彩度下限／
protan・deutan 的 CVD ΔE 分離／WCAG 對比）皆 PASS。**新增資料視覺化用色時照這個流程做**
——不要用肉眼判斷色盲友善度，那是可計算的東西。刻意避開綠／紅這組直覺選擇，正是因為
它在 protan／deutan 下分不開。

### 1.3 半透明疊色：一律 `color-mix`，不用裸 `rgba`

現有的透明疊色（chip 底色、選中態底色）用 `color-mix(in srgb, var(--brass) 14%, transparent)`
這種形式，而非寫死的 `rgba(184,134,11,0.14)`——好處是換主題變數時疊色自動跟著色相走，
不必為每個主題各寫一份。**例外**：大破警告框的 `rgba(224,85,85,…)` 是語意色（見 1.2），
維持獨立、不吃主題。

`prefers-reduced-transparency` 開啟時，這些疊色改為 `color-mix(…, var(--panel))`
（混進不透明底色而非 `transparent`）而不是整個拿掉效果——色調視覺上不變，只是不透光。

### 1.4 捲軸吃主題變數，軌道一律 transparent

瀏覽器預設捲軸在深色底上是一條亮灰，比內容本身還顯眼。三個頁面都套同一組規則
（overview／panel 已套；popup 沒有捲動區，不需要）：

```css
* { scrollbar-width: thin; scrollbar-color: var(--line) transparent; }   /* 標準屬性 */
::-webkit-scrollbar-thumb { background: var(--line) padding-box; border: 2px solid transparent; }
::-webkit-scrollbar-thumb:hover { background: var(--dim) padding-box; }
::-webkit-scrollbar-track, ::-webkit-scrollbar-corner { background: transparent; }
```

**軌道必須是 `transparent`，不可寫成 `var(--bg)`**：捲動區不只頁面本身，還有底色是
`--panel` 的容器（如裝備／艦娘的表格框）。寫死其中一種底色，另一種就會出現一條對不上的
色帶。滑塊沿用既有的 `--line`／`--dim`，**不新增顏色角色變數**。

WebKit 的滑塊用「透明邊框＋`padding-box`」做內縮，不要改成實色邊框——那會在滑塊四周
畫出一圈實線，等於又把軌道塗成固定色。

## 2. 排版

### 2.1 字型堆疊

```css
font: 13px/1.5 system-ui, -apple-system, "Hiragino Sans", sans-serif;
```

`system-ui` 置前：依使用者 OS／語系解析到當地系統字（macOS SF、日文環境 Hiragino、
中文環境思源黑體…），已內建字級光學調整；`-apple-system` 僅作舊版 WebKit 回退。
**除非有具體理由，不要換成自訂字型**——面板要在 zh-TW/ja/en 至少三種語系下都好讀，
系統字已經是各平台調過的答案。

### 2.2 字距（tracking）四級距

字距與字級成反比：字愈小需要愈多字距才好讀，字愈大則要收緊（負值）。
四個級距變數（三頁共用同一組值）：

| 變數 | 值 | 適用字級 | 範例 |
|---|---|---|---|
| `--track-tag` | `.14em` | 8–9px 極小標籤 | 艦種縮寫、掉落 tag |
| `--track-label` | `.12em` | 10–11px 小標題 | `h3`、種類 badge |
| `--track-body` | `0` | 13–14px 內文 | 一般文字 |
| `--track-title` | `-.01em` | 15px 以上標題 | 提督名、頁面標題 |

**新加文字樣式時直接套對應級距變數，不要另外寫一個字距數值。** 這批變數就是為了
取代過去四處各自硬寫死、彼此不成比例的舊值（曾經出現 9px 用 `.04em`、11px 用
`.12em`，比例反了）。

**窄徽章的尾隨字距補償**：`letter-spacing` 會在最後一個字後面也留白，窄底色徽章
（如 `.stype`、`.s-drop-tag`）若不補償，文字會在框內看起來偏左。做法：

```css
padding: 0 calc(3px - var(--track-tag)) 0 3px;  /* 右內距扣掉一個字距 */
```

### 2.3 大字收緊行高

字級 ≥14px 的標題類，行高比內文的 `1.5–1.6` 收緊到 `1.2` 左右，避免大字看起來鬆散：

```css
#header h1 { font-size: 15px; line-height: 1.2; letter-spacing: var(--track-title); }
```

## 3. 動效

### 3.1 唯一動效原則：按下即回饋

任何可點擊元件（按鈕、tab、side nav 項目）都該有 `:active` 態，**不等 click 處理完成**
（開視窗、hash 路由、組字串產 Blob 都需要時間，回饋不能等它們）：

```css
.btn {
  transition: border-color 100ms ease-out, color 100ms ease-out, transform 100ms ease-out;
}
.btn:active {
  border-color: var(--sparkle);
  transform: scale(.97);
}
```

`100ms` + `scale(.97)` 是目前的統一值，新元件照抄即可，不必每次重新決定數值。

### 3.2 三個無障礙 media query（每個新頁面/大改版都要檢查）

```css
@media (prefers-reduced-motion: reduce) {
  /* 拿掉會位移的 transform；保留純色彩變化的回饋，不是整個關掉回饋。
     若有持續性動畫（如警告脈動），換成靜態的等效強調，不能無聲無息消失——
     訊號重要性不能因為使用者開了這個系統設定就下降。 */
}
@media (prefers-reduced-transparency: reduce) {
  /* color-mix 的第二參數從 transparent 換成 var(--panel)。*/
}
@media (prefers-contrast: more) {
  /* --line/--dim 換成更高對比的值；語意狀態（如大破警告）從淡底文字
     換成實心底+反色文字，不能只靠淡色差異表示。*/
}
```

### 3.3 刻意沒有的東西

**沒有 spring/momentum 物理、沒有手勢驅動動效、沒有動畫函式庫依賴。** 這不是還沒做，
是評估過 Apple 那套 fluid-interface 設計語言（spring damping/response、velocity
handoff、rubber-banding……）後主動排除的方向：

1. 本專案沒有拖曳/滑動類互動——所有畫面都是 `innerHTML` 整塊重繪（見 4.2），沒有
   「使用者抓著一個正在動的元素」的場景，spring 的核心價值（可被中斷、從當前值接續）
   無處施展。
2. 引入動畫函式庫（如 Motion/Framer Motion）違反 CLAUDE.md 的權限精簡與零依賴立場——
   目前唯一 runtime 依賴是 dexie。
3. 若未來面板改成局部 DOM diff 更新（而非整塊 `innerHTML` 替換），這個否決前提才會
   改變，屆時可重新評估。**在那之前，不要為裝飾性動效引入函式庫。**

## 4. 元件慣例

### 4.1 尺寸量表（現狀，非強制規格）

`border-radius` 實測分布：面板小 chip/badge 用 `4px`（最多見），卡片/區塊用 `6px`／`8px`。
`3px`／`5px`／`12px` 為零星例外，新元件不必模仿，直接在 `4/6/8` 三級裡選：

| 用途 | 建議值 |
|---|---|
| chip、badge、小按鈕 | `4px` |
| 卡片、輸入框、一般按鈕 | `6px` |
| 大區塊、主要容器 | `8px` |

間距（`gap`/`padding`）沒有嚴格量表，但 `4/6/8/12px` 是目前最常見的四個值，新排版
優先從這幾個裡選，不必發明新數值。

### 4.1.1 可選欄位的紀錄表格

建造與開發這類「時間 × 結果 × 投入量」紀錄，採固定工具列、時間／歷史名稱篩選、欄位
選單與黏附表頭的詳細表格。開發的單次三連結果需拆為三個視覺列，讓結果篩選與計數都以
單次開發為單位；來源摘要仍維持一筆，避免重複寫入資料。欄位多時只讓表格容器橫向捲動，避免撐出整個頁面的橫向捲軸；數字欄採等寬數字、
同欄靠右，以便直向比較配方。欄位選擇與每頁筆數是純 UI 偏好，存 `localStorage`，不寫入
Dexie 或備份；至少保留一欄，避免使用者把表格變成無內容狀態。

### 4.2 全量重繪，非局部 diff（現況的結構限制）

`panel/main.ts`、`overview/sections/*.ts` 目前都是整塊 `innerHTML` 替換式渲染。
這個事實限制了動效能做到什麼程度（見 3.3 第 1 點）——**在討論任何「進場/離場轉場」
「元素從 A 移到 B 的動畫」之前，先確認這塊有沒有變（改成局部 diff）**，否則討論會
建立在錯誤的前提上。

**例外：帶有持續輸入控制項的分區**——目前是 `overview/ship-picker.ts`（鎮守府全船篩選
清單）、`overview/sections/ships.ts`（艦娘全覽詳細清單）與 `overview/sections/equipment.ts`
（裝備全覽）。三者的篩選器都含關鍵字輸入框（ships 還有等級範圍），若沿用全量重繪，每打一個
字元就重建 DOM、輸入框失焦，實際上打不了字。故它們把「控制項」與「結果」分開：控制項只在
建立時渲染一次並綁定，之後的變更**只重繪結果區**（清單／表格、計數、分頁列）。結果區一律用
事件委派（每次重繪都換掉子元素，逐項綁定會失效）。新元件若也有持續輸入的控制項，照這個
作法；其餘一律維持全量重繪。

**第二種例外：有「使用者展開的狀態」要保住的分區**——`overview/sections/sortie-log.ts`
（出擊紀錄）沒有輸入框，但每張卡可以展開，且展開內容是即時解析原始封包算出來的。若切個
分類就整塊重繪，使用者剛展開的那幾張全部收起來、捲動位置也歸零，等於每次篩選都懲罰一次。
故同樣把工具列建一次、只重繪清單區，展開狀態存在分區內的 `Set` 裡跨重繪存活；展開內容
（跑過戰鬥重放的 HTML）另外快取，收合再展開不重算。
`overview/sections/resource-log.ts`（資源紀錄）屬同一類：要保住的是圖表的十字準線、詳細
清單的捲動位置與分頁。**判準是「有沒有使用者自己造出來、重繪就會消失的狀態」**
（輸入焦點、展開、捲動位置、游標位置），不是元件複雜度。

### 4.2.1 先畫殼、再讀資料；失敗不可留白

非同步分區（要讀 IndexedDB 的那些）一律**先把控制項渲染出來並綁好事件，之後才 await 資料**。
理由是失敗模式：資料讀取可能很慢、可能丟例外、也可能**無限等待**（Dexie 版本升級被其他分頁
或面板擋住時 `open()` 不會 reject，只會一直等）。若順序反過來，使用者看到的是一片空白，
連「匯入 JSON」這種與資料無關的功能都按不到，而且沒有任何錯誤訊息可回報。

三件事一起做才算完整：

1. 殼先出現（工具列／匯入面板等不依賴資料的控制項）。
2. 資料區在載入期間顯示「載入中…」，失敗時顯示**原因**（不是空白也不是假的空狀態）。
3. 分區的 `render()` 例外由 `overview/main.ts` 的 `renderSection()` 接住並顯示——
   **任何分區都不得靜默留白**。

### 4.3 圖示即控制項（裝備全覽的圖示篩選架）

`overview/sections/equipment.ts` 的 `.eq-rail` 把既有的裝備圖示直接當成篩選鈕（一顆圖示
一個 toggle、右下角疊持有件數、多選＝聯集）。這是本專案第一個「圖示不只是裝飾，本身就是
主導覽」的元件，成立條件有三，缺一就別照抄：

1. **該領域的第一層心智分類本來就是視覺的**——挑裝備時玩家腦中先浮現的是圖示長相，不是
   類別名稱。艦娘就不是這樣（艦種是文字概念），故艦娘全覽用的是文字分段控制。
2. **圖示是既有資產且辨識度已驗證**（M7 的 74 顆，含描邊與明度下限，亮暗底皆可讀）。
3. **只列實際持有的**——選項數量隨資料收斂（全 master 有 59 個圖示 id，全排出來會把
   「我有什麼」淹掉）。

選中態沿用既有語言（`--sparkle` 邊框＋`color-mix` 的 `--brass` 淡底），不另發明。
`prefers-contrast: more` 下淡底色差異在一整排圖示裡幾乎看不出來，故改為粗邊＋`outline`。

**展開／收合的方向指示用字元（▸/▾）而非 `transform: rotate`**：旋轉在
`prefers-reduced-motion` 下必須關掉，關掉後開合兩態的箭頭長得一模一樣，狀態訊號就消失了
（違反 §3.2「訊號重要性不能因為使用者開了系統設定就下降」）。換字元則不依賴動效。

### 4.4 側欄三態：釘選／收合／滑入（overview）

`overview` 的側欄有三個 `body[data-nav]` 狀態，控制器在 `overview/main.ts`：

| 狀態 | 版面 | 何時 |
|---|---|---|
| `pinned` | 側欄佔一欄（`--nav-w: 200px`），內容區退讓 | 預設；使用者按 header 的 `⟨` 可切掉 |
| `hidden` | 側欄不佔寬度，滑到左緣熱區／tab 進去才以浮層滑出 | 使用者收合，或視窗 ≤760px |
| `open` | 浮層被按鈕固定打開（窄視窗的抽屜） | 窄視窗按 `☰` |

三個必須一起成立的細節，少一個就會變成「看起來能用但實際不能用」：

1. **浮層用 `position: fixed`，不推擠內容**——否則滑鼠每掃過左緣一次，整頁就重排一次。
2. **窄視窗時按鈕不可以去切「釘選」**。釘選在窄視窗會被強制無效化（200px 側欄會把內容
   壓到不能看），此時切它畫面毫無反應＝按鈕壞掉。故窄視窗改切浮層開合，釘選意願原封不動
   （放大視窗就自動釘回去）。
3. **hover 不是唯一入口**。鍵盤與觸控沒有 hover，故 header 的按鈕、`:focus-within`
   （tab 進側欄自動浮出）、Escape 收起，三者都要有。

收合時左緣留一條 3px 漸層提示——完全無痕的熱區等於沒有這個功能（靠右時沒有這條提示，
理由見下）。

**側欄左右側**（`body[data-nav-side="left"|"right"]`＋localStorage `kc-overview-nav-side`，
2026-07-23，2026-07-23 second pass 修正）與上面三態**正交**：側是「在哪一邊」，態是
「佔不佔版面寬度」，兩者互不影響，換側不會重置釘選／收合意願。實作是 CSS 鏡射（grid 欄序與
`grid-template-areas` 互換、浮層固定改貼右緣、邊框／陰影方向翻面），三態的 JS 邏輯完全不變。

**靠右時 hover 熱區整個不做**（`#nav-hotspot { display: none }`，只在 `data-nav-side="right"`
時生效）——這不是窄視窗才有的問題，是**結構性**的：右緣同時是 `#content` 捲軸的所在，兩者
搶同一條窄邊，滑鼠稍微移動、或去拖曳捲軸，就會一直觸發熱區的顯示/隱藏 transform，體感是
「側欄自己在亂跳」。左緣沒有這個問題（捲軸不會出現在左邊），故左側維持原本的 hover 熱區。
靠右唯一的開合入口只剩 header 按鈕與 `:focus-within`（鍵盤 tab 進側欄，不靠滑鼠不會跟捲軸
衝突），仍符合「hover 不是唯一入口」的規則3——只是對右側而言，hover 乾脆整條路都不給。

**header 的兩顆按鈕（`#nav-toggle`／`#nav-side-toggle`）會跟著側欄換邊**（CSS `order`，
`body[data-nav-side="right"] #nav-toggle { order: 10 }`，把它排到 header 最右端、緊貼
`#nav-side-toggle`）。**理由**：按鈕若固定留在左上角，但側欄彈在右邊，使用者會覺得
「按了沒反應」——其實有反應，只是彈在完全沒在看的另一側，這在窄視窗（側欄整個是浮層，
視線更集中在彈出的那一角）特別明顯。按鈕跟著側欄移動後，開合的入口永遠在使用者正在看的
那一側，不管視窗寬窄。`#nav-side-toggle` 同樣遵守「圖示表示按下去的結果」慣例：目前靠左
顯示「移到右側」的箭頭，反之亦然。

**⚠️ CSS specificity 陷阱（真的讓側欄完全彈不出來過一次，別重蹈覆轍）**：靠右的「收起來」
規則多帶了一個 `[data-nav-side="right"]` 屬性選擇器，比三態那條泛用的「展開」規則
（`body[data-nav="open"] #nav { transform: translateX(0) }`）specificity 更高。
CSS 的 specificity 不看選擇器先後、只看選擇器本身「重不重」，故靠右時那條泛用展開規則
**永遠打不贏**帶了額外屬性的收起規則——結果側欄狀態明明已經是 `open`，`#nav` 卻還是卡在
`translateX(100%)`，形同完全彈不出來。**這不是靠讀 CSS 看得出來的 bug**——兩條規則分開看
都合理，只有實際跑起來量測 `#nav` 的 bounding rect 才會發現它停在螢幕外。修法是每次幫
`data-nav="hidden"/"open"` 的側寫規則時，**兩側都要各自補一條同 specificity（或更高）的
展開規則**，不能只靠一條不分側的泛用規則去對抗一條分側的收起規則。已用 `playwright-core`
（`channel: "chrome"`，指向系統既有 Chrome）實際跑 `.output/chrome-mv3/overview.html`、
量測點擊前後 `#nav` 的 `getBoundingClientRect()` 驗證過三種寬度×兩側的六種組合。

### 4.5 語意色不可挪用做裝飾

`--dmg-major`／`--dmg-mid`／`--dmg-minor`／rank 色只能用在其語意對應的狀態上
（大破/中破/小破、rank S/A/B/C/D）。不要因為某個顏色好看就借去用在無關的裝飾元素，
會稀釋這些顏色原本承載的「一眼看出狀態」功能。

### 4.6 資料視覺化：一張圖、多條線、圖例即開關

`resource-log` 的趨勢圖是本專案第一個圖表元件。**形狀由使用者定案**：最上方一張大圖，
所有序列疊在一起，圖例可逐條開關。（初版做成「一項一格的小倍數」被明確否決——
量級差距不是拆圖的理由。）

1. **量級差距用「開關」解，不用拆圖、更不用雙 y 軸**。y 軸值域**只由目前顯示中的序列
   決定**：關掉十萬級的燃料，千級的螺絲就會撐滿整張圖。**雙 y 軸一律不做**——兩套刻度
   沒有共同基準，任何交叉都是視覺巧合。另外備一兩顆「常用組合」捷徑（例：只看四大資源），
   讓最常見的比較不必逐顆點。
2. **圖例是控制項，不是說明**。色塊＋名稱＋目前值，點了就開關。**關掉的序列要留在列上**
   （淡化＋空心色塊），消失掉使用者就不知道還有那一項可以打開。
3. **色彩跟著實體，不跟著排名**。第 i 個實體恆定拿第 i 個色位，開關序列時絕不重新分配
   ——否則關掉一條線會讓其他線全部換色。色盤取 dataviz skill 參考色盤的**原始順序**
   （順序一改，它保證的相鄰色對分離度就不成立了），深淺兩套各自跑 `validate_palette.js`。

四個容易做錯的細節：

- **`hidden` 是 HTML 屬性，對 SVG 元素無效**。十字準線與游標點掛了 `hidden` 照樣畫在
  (0,0)，畫面左上角會多一顆莫名其妙的點。要用 CSS `[hidden] { display: none }`。
- **不要用 `preserveAspectRatio="none"`**。非等比縮放會把軸刻度文字橫向拉伸（容器
  1600px 時字被拉成 1.6 倍寬）。等比縮放＋`aspect-ratio`，線寬另用
  `vector-effect: non-scaling-stroke` 固定成實際像素。
- **抽稀是純減量，不平滑**：每個時間桶取最後一筆、首尾必留。移動平均之類的平滑會把
  「一次活動燒掉十萬燃料」的那道陡降磨圓，而那正是這張圖唯一要看的東西。
- **x 依時間比例，不用等距索引**：取樣本來就不等距（一天打十場、隔天不上線），
  等距畫會把時間軸扭曲。

圖表元件的動效沿用 §3.1／§3.2：十字準線是即時位置回饋、沒有 transition，故
`prefers-reduced-motion` 只需處理圖例按鈕；`prefers-contrast: more` 下折線加粗、十字準線
改實線（虛線在高對比下反而更難追），**圖例的開／關不能只靠 `opacity`**（高對比下看不出
差別），改加刪除線。

## 5. 圖示

圖示生成器與完整設計約束在 [tools/icons/README.md](../tools/icons/README.md)，
**改圖示前必讀**，這裡只列會影響「介面設計」判斷的結論：

- **74 顆全部由 `tools/icons/` 的 python 生成器產生，禁止手改 SVG**——改生成器再重跑。
- **全圖示帶統一深墨描邊**（`INK = #37302a`，`feMorphology` 外輪廓）——這是亮暗主題
  切換的前提（SVG 以 `<img src>` 載入吃不到外部 CSS，無法靠 CSS 改色，描邊讓圖示
  在亮底/暗底都自足可讀）。**新增圖示或討論圖示改動時，這個約束不可放寬。**
- **暗底明度下限**（HSL 明度 ≥ 0.26）是硬約束，禁用近黑色（會被深色面板背景吸收）。
- **尺寸已正規化**（`normalize.py`，較長邊=29 單位、置中）——並排 chip 顯示時各圖示
  視覺高度一致，這是既有保證，不要在新增圖示時繞過正規化流程手動調尺寸。
- 徽章（飛機族機型標記）**不參與縮放**，固定尺寸——因為它是小圖下的主要辨識信號。
- 配色語言：口徑→明度分級（`#ff8080→#ff4040→#ff0000`）、機身色統一靠徽章色區分機種，
  不是靠機身變色。新裝備圖示要延用同一套邏輯，不要每顆自訂一套配色規則。

## 6. 刻意不做的事（整理版，含理由）

| 方向 | 為何不做 | 若要重新考慮 |
|---|---|---|
| 動畫函式庫（Motion 等） | 違反權限精簡＋零依賴（CLAUDE.md 硬約束） | 沒有觸發條件，除非專案立場改變 |
| Spring/手勢動效 | 沒有拖曳類互動，`innerHTML` 全量重繪與可中斷動畫的前提互斥 | 面板改局部 DOM diff 之後 |
| 抽共用 CSS 檔（三頁合一份） | popup 太小不值得抽；三份小到手動同步的成本低於抽象成本 | 若三份的規則開始頻繁漂移不同步，才考慮 |
| 自訂字型取代 system-ui | 系統字已含平台級光學調整，且要覆蓋 zh-TW/ja/en 三語系 | 有具體排版問題系統字解不了才考慮 |
| 圖表函式庫（Chart.js 等） | 同上：違反零依賴。目前的需求（折線＋十字準線）用純函式算幾何＋內聯 SVG 就夠，見 `utils/line-chart.ts` | 需要的圖表型別多到自己算幾何比引入還貴時 |
| 雙 y 軸圖表 | 兩套刻度沒有共同基準，交叉點是視覺巧合而非事實（見 4.6） | 不考慮——量級不同就分格 |
| 手改 SVG 圖示 | 74 顆共用同一套描邊/正規化管線，手改會破壞一致性且下次重新生成會被覆蓋 | 不考慮——一律改生成器 |

## 使用方式

之後提出介面或圖示修改時，先對照本文判斷：

1. 這是新角色/新規則，還是既有規則的變體？→ 變體直接套用第 1–4 節的現有變數/量表。
2. 這個方向是否在第 6 節列為「刻意不做」？→ 若是，先確認觸發重新考慮的條件是否成立，
   不要重新從零推導一次。
3. 影響圖示？→ 先讀 `tools/icons/README.md`，改生成器，不手改 SVG。

改動落地後，若引入了新的角色變數／量表值／否決過又重新考慮的方向，**回來更新本文**，
維持它是「目前實際狀態」而不是某個時間點的快照。
