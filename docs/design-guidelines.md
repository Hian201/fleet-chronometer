# 設計綱要（UI／圖示）

本文彙整**目前實際採用**的視覺決定與非顯而易見的理由，作為之後提出介面修改或圖示
設計時的討論基準。字距、色彩與版面規則集中在這裡，避免同一角色在不同頁面使用不一致
的數值。

三個擴充頁面（`panel/index.html`／`overview/index.html`／`popup/index.html`）
**各自一份 `<style>`，刻意不抽共用 CSS 檔**（popup 的註解已寫明：頁面太小不值得抽）。
本綱要是三份之間的一致性契約——改一處規則時，三份都要跟著改。

**不要重複資訊**（UI 最高原則，見 CLAUDE.md 設計原則 6）：同一事實只在一個位置完整
呈現。別處若需要狀態訊號，只標「是什麼」、不把數字／倒數／明細再抄一遍。

## 1. 色彩系統

### 1.1 角色變數（非直接色碼）

所有元件一律吃 CSS 變數，不直接寫色碼。深色為預設，`:root[data-theme="light"]`
覆蓋。變數命名是**角色**（這個顏色扮演什麼功能），不是色相本身：

| 變數 | 深色 | 淺色 | 角色 |
|---|---|---|---|
| `--bg` | `#10151d` | `#eef0f4` / `#f2f0ea` | 頁面底色 |
| `--panel` | `#182030` | `#ffffff` | 卡片/區塊底色 |
| `--line` | `#2a3548` | `#d3d8e2` / `#d8d2c4` | 邊框、分隔線 |
| `--text` | `#cfd6e4` | `#26303f` / `#2c2f36` | 主要文字 |
| `--dim` | `#7d8aa0` | `#6b7688` / `#6b7280` | 次要/輔助文字 |
| `--brass` | `#b8860b` | `#9a6b0b` / `#8a6d1a` | 標題級距標籤、強調邊框（黃銅） |
| `--sparkle` | `#e6c35c` | `#8a6d1a` | 高亮強調（提督名、選中狀態、金色系數值） |
| `--stub` | `#4a5468` | `#aab3c2` | 停用/佔位狀態 |

> overview 目前把 `--brass`/`--sparkle` 兩個角色的深淺色合流成同一個 `#8a6d1a`
> （見 [index.html:40-41](../entrypoints/overview/index.html#L40)）——overview 目前將兩個
> 角色共用同一組亮色值；角色仍然不同（強調邊框 vs. 高亮強調），調整亮色主題時必須分開。

**新增變數前先問**：這是新角色，還是既有角色換個名字？八個角色已覆蓋大部分情境，
新增前先確認現有變數是否已經夠用。

### 1.2 語意色（不隨主題變化）

傷害/狀態類顏色是**語意色**，深淺主題共用同一組值——它們傳達的是遊戲內客觀狀態
（大破／中破／小破），不是裝飾，換主題不應該改變讀法：

```
--dmg-major: #e05555   /* 大破 */
--dmg-mid:   #e08b3d   /* 中破 */
--dmg-minor: #d4b83a   /* 小破 */
```

rank 顏色同理（`sortie-log` 等分區的 `.rank-s/.rank-a/.rank-b`）固定值，不吃主題變數。

出擊標籤狀態（`event-ops` 分區）是**另一組獨立的語意色**，同樣不隨主題變化：

```
--sally-ok:      #5f9e6b   /* 已持有本關卡允許的標籤 */
--sally-blocked: #b8524d   /* 持有別的標籤 → 這隊走不了這條路線 */
--sally-stamp:   #c98a35   /* 無標籤 → 出擊後會被貼上，不可逆消耗 */
```

**刻意與 `--dmg-*` 取不同色值**（而非直接複用紅／橙）：標籤狀態講的是「這隊能不能走這條
路線」，與大破／中破／小破是兩套完全無關的語意，共用色值會讓兩者互相稀釋（見 4.5）。

資源消長（`resource-log` 分區）是**第三組獨立語意色**，同理不隨主題變化、不挪用上面兩組：

```
--res-gain:  #2f8fcf   /* 資材增加 */
--res-drain: #cf7526   /* 資材消耗 */
```

**這組色值是算出來的，不是挑出來的**：用 dataviz skill 的 `validate_palette.js`
對深色 `#182030` 與亮色 `#ffffff` 兩種底色各跑一次，四項檢查（OKLCH 亮度帶／彩度下限／
protan・deutan 的 CVD ΔE 分離／WCAG 對比）皆 PASS。**新增資料視覺化用色時照這個流程做**
——不要用肉眼判斷色盲友善度，那是可計算的東西。刻意避開綠／紅這組直覺選擇，正是因為
它在 protan／deutan 下分不開。

配裝參考（`equip-ref` 分區）是**第四組獨立語意色**，同樣不隨主題變化、不挪用上面三組：

```
--eq-bonus: #4aa3c9   /* 藍字加成 */
--eq-fit:   #8b7cc9   /* 正適性（晝戰命中項） */
--eq-over:  #c17a4a   /* 過重（負適性） */
--eq-lack:  #c9a36a   /* 鎮守府庫存沒有此裝備 */
```

任務種類（panel 任務清單、任務導覽）是**第五組獨立語意色**，對齊遊戲任務清單的分類色，
不隨主題變化、不挪用其他組。種類取自即時 `api_category`（對照在 `utils/quest-category.ts`），
只以名稱前 4px 色標呈現，種類名稱放在提示與輔助標籤；種類不明只畫空框：

```
--qc-composition:   #2a8144   /* 編成 */
--qc-sortie:        #c0413e   /* 出擊 */
--qc-practice:      #559d3d   /* 演習 */
--qc-expedition:    #39a29e   /* 遠征 */
--qc-supply-dock:   #d8ba63   /* 補給／入渠 */
--qc-arsenal:       #6b473c   /* 工廠 */
--qc-modernization: #a783b9   /* 改裝 */
```

### 1.3 半透明疊色：一律 `color-mix`，不用裸 `rgba`

現有的透明疊色（chip 底色、選中態底色）用 `color-mix(in srgb, var(--brass) 14%, transparent)`
這種形式，而非寫死的 `rgba(184,134,11,0.14)`——好處是換主題變數時疊色自動跟著色相走，
不必為每個主題各寫一份。**例外**：大破警告框的 `rgba(224,85,85,…)` 是語意色（見 1.2），
維持獨立、不吃主題。

`prefers-reduced-transparency` 開啟時，這些疊色改為 `color-mix(…, var(--panel))`
（混進不透明底色而非 `transparent`）而不是整個拿掉效果——色調視覺上不變，只是不透光。

### 1.4 捲軸吃主題變數，軌道一律 transparent

瀏覽器預設捲軸在深色底上是一條亮灰，比內容本身還顯眼。三個頁面都套同一組規則
（overview／panel 已套；popup 沒有捲動區，不需要）：

```css
* { scrollbar-width: thin; scrollbar-color: var(--line) transparent; }   /* 標準屬性 */
::-webkit-scrollbar-thumb { background: var(--line) padding-box; border: 2px solid transparent; }
::-webkit-scrollbar-thumb:hover { background: var(--dim) padding-box; }
::-webkit-scrollbar-track, ::-webkit-scrollbar-corner { background: transparent; }
```

**軌道必須是 `transparent`，不可寫成 `var(--bg)`**：捲動區不只頁面本身，還有底色是
`--panel` 的容器（如裝備／艦娘的表格框）。寫死其中一種底色，另一種就會出現一條對不上的
色帶。滑塊沿用既有的 `--line`／`--dim`，**不新增顏色角色變數**。

WebKit 的滑塊用「透明邊框＋`padding-box`」做內縮，不要改成實色邊框——那會在滑塊四周
畫出一圈實線，等於又把軌道塗成固定色。

### 1.5 面板 631 色彩比例

面板的色彩決策採 **60／30／10（631）** 作為視覺面積與注意力預算：

- **60% 主色**：以 `--bg` 為大面積底色，維持整體深色基調；不要用多組不同深藍切割背景。
- **30% 輔助色**：以 `--panel`、`--line`、`--text`、`--dim` 建立卡片、分隔與資訊層級；同一區塊優先共用既有角色，不另加色相。
- **10% 強調色**：只用既有 `--brass`／`--sparkle` 做選中、重要狀態、關鍵數值與操作提示；強調色應集中，不得讓一整列變成彩色文字帶。

這是面積與注意力的比例原則，不要求每個畫面精算像素，也不代表語意色可以刪除。`--dmg-*`、出擊標籤與資源消長等客觀狀態仍依 §1.2 保留獨立角色，但不得拿來裝飾摘要列。

編成摘要的 `.fs-ops` 與 `.fs-metrics` 另有以下硬規則：服務名稱、標籤、metadata 與數值一律以正常字重為基準，不使用粗體堆疊；資訊層級改由字級、間距、排列與 `--text`／`--dim` 區分。主數字不用提高字重，也不用新增色相；加速、選中與最重要的值才進入 `--brass`／`--sparkle` 的 10% 強調層。低速／高速／高速＋／最速若需要區分，限用中性文字與既有黃銅系的明度階，不新增綠、藍、紫等彩色分支；四種速度的亮度順序固定為低速 < 高速 < 高速＋ < 最速，最速使用最亮的既有強調色。倒數數字與狀態標籤即使同屬強調層，也要透過不同字級、間距或 token 保持語意分離。

泊地修理摘要的倒數若存在，代表可觀測到的共享結算週期；配對修理的 `5/6` 只影響每次 HP 回復量，不得直接把共享的 20 分鐘計時器縮短。一般修理倒數與加速修理倒數必須使用不同顏色階，且加速文字不以粗體呈現；無法取得錨點時顯示明確的不可考狀態，不得把缺值當成零。

## 2. 排版

### 2.1 字型堆疊

```css
font: 13px/1.5 system-ui, -apple-system, "Hiragino Sans", sans-serif;
```

`system-ui` 置前：依使用者 OS／語系解析到當地系統字（macOS SF、日文環境 Hiragino、
中文環境思源黑體…），已內建字級光學調整；`-apple-system` 僅作舊版 WebKit 回退。
**除非有具體理由，不要換成自訂字型**——面板要在 zh-TW/ja/en 至少三種語系下都好讀，
系統字已經是各平台調過的答案。

### 2.2 字距（tracking）四級距

字距與字級成反比：字愈小需要愈多字距才好讀，字愈大則要收緊（負值）。
四個級距變數（三頁共用同一組值）：

| 變數 | 值 | 適用字級 | 範例 |
|---|---|---|---|
| `--track-tag` | `.14em` | 8–9px 極小標籤 | 艦種縮寫、掉落 tag |
| `--track-label` | `.12em` | 10–11px 小標題 | `h3`、種類 badge |
| `--track-body` | `0` | 13–14px 內文 | 一般文字 |
| `--track-title` | `-.01em` | 15px 以上標題 | 提督名、頁面標題 |

**新加文字樣式時直接套對應級距變數，不要另外寫一個字距數值。** 統一級距可避免小字
與大字使用不成比例的字距，並讓三個頁面維持相同的閱讀節奏。

**窄徽章的尾隨字距補償**：`letter-spacing` 會在最後一個字後面也留白，窄底色徽章
（如 `.stype`、`.s-drop-tag`）若不補償，文字會在框內看起來偏左。做法：

```css
padding: 0 calc(3px - var(--track-tag)) 0 3px;  /* 右內距扣掉一個字距 */
```

### 2.3 大字收緊行高

字級 ≥14px 的標題類，行高比內文的 `1.5–1.6` 收緊到 `1.2` 左右，避免大字看起來鬆散：

```css
#header h1 { font-size: 15px; line-height: 1.2; letter-spacing: var(--track-title); }
```

### 2.4 多語系排版核對

面板與情報總括是固定幾何，同一欄要同時裝得下漢字與拉丁文。拉丁文案通常比對應的台灣華語長，只核對一種語言會漏掉溢出、相鄰欄互相覆蓋、或折行把固定列高撐破。

改介面、可見文案或固定欄寬樣式時，**至少**以台灣華語（`zh-TW`）與英文（`en`）各看一次受影響畫面。日文長度與這兩者明顯不同時一併看。通過條件：

- 相鄰欄位不得互相覆蓋
- 超長文案只在自身欄位省略，不得畫到隔壁或蓋住圖示
- 折行不得改變 §7 釘死的列高，也不得把編成推跑
- 畫面上的標籤須隨語系切換，不得在英文介面留下未翻譯的中文（或反之）

離線預覽若只產一種語言，須另用切語言後的正式頁或等寬英文對照核對，不能只看預覽的中文量測 fixture 就結案。

## 3. 動效

### 3.1 唯一動效原則：按下即回饋

任何可點擊元件（按鈕、tab、side nav 項目）都該有 `:active` 態，**不等 click 處理完成**
（開視窗、hash 路由、組字串產 Blob 都需要時間，回饋不能等它們）：

```css
.btn {
  transition: border-color 100ms ease-out, color 100ms ease-out, transform 100ms ease-out;
}
.btn:active {
  border-color: var(--sparkle);
  transform: scale(.97);
}
```

`100ms` + `scale(.97)` 是目前的統一值，新元件照抄即可，不必每次重新決定數值。

### 3.2 三個無障礙 media query（每個新頁面/大改版都要檢查）

```css
@media (prefers-reduced-motion: reduce) {
  /* 拿掉會位移的 transform；保留純色彩變化的回饋，不是整個關掉回饋。
     若有持續性動畫（如警告脈動），換成靜態的等效強調，不能無聲無息消失——
     訊號重要性不能因為使用者開了這個系統設定就下降。 */
}
@media (prefers-reduced-transparency: reduce) {
  /* color-mix 的第二參數從 transparent 換成 var(--panel)。*/
}
@media (prefers-contrast: more) {
  /* --line/--dim 換成更高對比的值；語意狀態（如大破警告）從淡底文字
     換成實心底+反色文字，不能只靠淡色差異表示。*/
}
```

### 3.3 刻意沒有的東西

**沒有 spring/momentum 物理、沒有手勢驅動動效、沒有動畫函式庫依賴。** 目前頁面沒有
需要可中斷的拖曳或滑動動畫，且互動以 CSS 轉場即可表達：

1. 本專案沒有拖曳/滑動類互動——所有畫面都是 `innerHTML` 整塊重繪（見 4.2），沒有
   「使用者抓著一個正在動的元素」的場景，spring 的核心價值（可被中斷、從當前值接續）
   無處施展。
2. 引入動畫函式庫（如 Motion/Framer Motion）違反 CLAUDE.md 的零依賴立場。
3. 若未來面板改成局部 DOM diff 更新（而非整塊 `innerHTML` 替換），才需要重新評估
   動效模型；目前不引入裝飾性動效函式庫。

## 4. 元件慣例

### 4.1 尺寸量表（現狀，非強制規格）

`border-radius` 實測分布：面板小 chip/badge 用 `4px`（最多見），卡片/區塊用 `6px`／`8px`。
`3px`／`5px`／`12px` 為零星例外，新元件不必模仿，直接在 `4/6/8` 三級裡選：

| 用途 | 建議值 |
|---|---|
| chip、badge、小按鈕 | `4px` |
| 卡片、輸入框、一般按鈕 | `6px` |
| 大區塊、主要容器 | `8px` |

間距（`gap`/`padding`）沒有嚴格量表，但 `4/6/8/12px` 是目前最常見的四個值，新排版
優先從這幾個裡選，不必發明新數值。

### 4.1.1 可選欄位的紀錄表格

建造與開發這類「時間 × 結果 × 投入量」紀錄，採固定工具列、時間／歷史名稱篩選、欄位
選單與黏附表頭的詳細表格。開發的單次三連結果需拆為三個視覺列，讓結果篩選與計數都以
單次開發為單位；來源摘要仍維持一筆，避免重複寫入資料。欄位多時只讓表格容器橫向捲動，避免撐出整個頁面的橫向捲軸；數字欄採等寬數字、
同欄靠右，以便直向比較配方。欄位選擇與每頁筆數是純 UI 偏好，存 `localStorage`，不寫入
Dexie 或備份；至少保留一欄，避免使用者把表格變成無內容狀態。

### 4.2 全量重繪，非局部 diff（現況的結構限制）

`panel/main.ts`、`overview/sections/*.ts` 目前都是整塊 `innerHTML` 替換式渲染。
這個事實限制了動效能做到什麼程度（見 3.3 第 1 點）——**在討論任何「進場/離場轉場」
「元素從 A 移到 B 的動畫」之前，先確認這塊有沒有變（改成局部 diff）**，否則討論會
建立在錯誤的前提上。

**例外：帶有持續輸入控制項的分區**——目前是 `overview/ship-picker.ts`（鎮守府全船篩選
清單）、`overview/sections/ships.ts`（艦娘全覽詳細清單）與 `overview/sections/equipment.ts`
（裝備全覽）。三者的篩選器都含關鍵字輸入框（ships 還有等級範圍），若沿用全量重繪，每打一個
字元就重建 DOM、輸入框失焦，實際上打不了字。故它們把「控制項」與「結果」分開：控制項只在
建立時渲染一次並綁定，之後的變更**只重繪結果區**（清單／表格、計數、分頁列）。結果區一律用
事件委派（每次重繪都換掉子元素，逐項綁定會失效）。新元件若也有持續輸入的控制項，照這個
作法；其餘一律維持全量重繪。

**第二種例外：有「使用者展開的狀態」要保住的分區**——`overview/sections/sortie-log.ts`
（出擊紀錄）沒有輸入框，但每張卡可以展開，且展開內容是即時解析原始封包算出來的。若切個
分類就整塊重繪，使用者剛展開的那幾張全部收起來、捲動位置也歸零，等於每次篩選都懲罰一次。
故同樣把工具列建一次、只重繪清單區，展開狀態存在分區內的 `Set` 裡跨重繪存活；展開內容
（跑過戰鬥重放的 HTML）另外快取，收合再展開不重算。
`overview/sections/resource-log.ts`（資源紀錄）屬同一類：要保住的是圖表的十字準線、詳細
清單的捲動位置與分頁。**判準是「有沒有使用者自己造出來、重繪就會消失的狀態」**
（輸入焦點、展開、捲動位置、游標位置），不是元件複雜度。

### 4.2.1 先畫殼、再讀資料；失敗不可留白

非同步分區（要讀 IndexedDB 的那些）一律**先把控制項渲染出來並綁好事件，之後才 await 資料**。
理由是失敗模式：資料讀取可能很慢、可能丟例外、也可能**無限等待**（Dexie 版本升級被其他分頁
或面板擋住時 `open()` 不會 reject，只會一直等）。若順序反過來，使用者看到的是一片空白，
連「匯入 JSON」這種與資料無關的功能都按不到，而且沒有任何錯誤訊息可回報。

三件事一起做才算完整：

1. 殼先出現（工具列／匯入面板等不依賴資料的控制項）。
2. 資料區在載入期間顯示「載入中…」，失敗時顯示**原因**（不是空白也不是假的空狀態）。
3. 分區的 `render()` 例外由 `overview/main.ts` 的 `renderSection()` 接住並顯示——
   **任何分區都不得靜默留白**。

### 4.3 圖示即控制項（裝備全覽的圖示篩選架）

`overview/sections/equipment.ts` 的 `.eq-rail` 把既有的裝備圖示直接當成篩選鈕（一顆圖示
一個 toggle、右下角疊持有件數、多選＝聯集）。這個元件將圖示作為篩選控制項，成立條件有三，
缺一就不要套用：

1. **該領域的第一層心智分類本來就是視覺的**——挑裝備時玩家腦中先浮現的是圖示長相，不是
   類別名稱。艦娘就不是這樣（艦種是文字概念），故艦娘全覽用的是文字分段控制。
2. **圖示是既有資產且辨識度已驗證**（裝備／資源／UI 76 顆＋數值 17 顆，含描邊與明度下限，亮暗底皆可讀）。
3. **只列實際持有的**——選項數量隨資料收斂（全 master 有 59 個圖示 id，全排出來會把
   「我有什麼」淹掉）。

選中態沿用既有語言（`--sparkle` 邊框＋`color-mix` 的 `--brass` 淡底），不另發明。
`prefers-contrast: more` 下淡底色差異在一整排圖示裡幾乎看不出來，故改為粗邊＋`outline`。

**展開／收合的方向指示用字元（▸/▾）而非 `transform: rotate`**：旋轉在
`prefers-reduced-motion` 下必須關掉，關掉後開合兩態的箭頭長得一模一樣，狀態訊號就消失了
（違反 §3.2「訊號重要性不能因為使用者開了系統設定就下降」）。換字元則不依賴動效。

### 4.4 側欄三態：釘選／收合／滑入（overview）

`overview` 的側欄有三個 `body[data-nav]` 狀態，控制器在 `overview/main.ts`：

| 狀態 | 版面 | 何時 |
|---|---|---|
| `pinned` | 側欄佔一欄（`--nav-w: 200px`），內容區退讓 | 預設；使用者按 header 的 `⟨` 可切掉 |
| `hidden` | 側欄不佔寬度，滑到左緣熱區／tab 進去才以浮層滑出 | 使用者收合，或視窗 ≤760px |
| `open` | 浮層被按鈕固定打開（窄視窗的抽屜） | 窄視窗按 `☰` |

三個必須一起成立的細節，少一個就會變成「看起來能用但實際不能用」：

1. **浮層用 `position: fixed`，不推擠內容**——否則滑鼠每掃過左緣一次，整頁就重排一次。
2. **窄視窗時按鈕不可以去切「釘選」**。釘選在窄視窗會被強制無效化（200px 側欄會把內容
   壓到不能看），此時切它畫面毫無反應＝按鈕壞掉。故窄視窗改切浮層開合，釘選意願原封不動
   （放大視窗就自動釘回去）。
3. **hover 不是唯一入口**。鍵盤與觸控沒有 hover，故 header 的按鈕、`:focus-within`
   （tab 進側欄自動浮出）、Escape 收起，三者都要有。

收合時左緣留一條 3px 漸層提示——完全無痕的熱區等於沒有這個功能（靠右時沒有這條提示，
理由見下）。

**側欄左右側**（`body[data-nav-side="left"|"right"]`＋localStorage `kc-overview-nav-side`）
與上面三態**正交**：側是「在哪一邊」，態是
「佔不佔版面寬度」，兩者互不影響，換側不會重置釘選／收合意願。實作是 CSS 鏡射（grid 欄序與
`grid-template-areas` 互換、浮層固定改貼右緣、邊框／陰影方向翻面），三態的 JS 邏輯完全不變。

**靠右時 hover 熱區整個不做**（`#nav-hotspot { display: none }`，只在 `data-nav-side="right"`
時生效）——這是**結構性**的：右緣同時是 `#content` 捲軸的所在，兩者
搶同一條窄邊，滑鼠稍微移動、或去拖曳捲軸，就會一直觸發熱區的顯示/隱藏 transform，體感是
「側欄自己在亂跳」。左緣沒有這個問題（捲軸不會出現在左邊），故左側保留 hover 熱區。
靠右唯一的開合入口只剩 header 按鈕與 `:focus-within`（鍵盤 tab 進側欄，不靠滑鼠不會跟捲軸
衝突），仍符合「hover 不是唯一入口」的規則3——只是對右側而言，hover 乾脆整條路都不給。

**header 的兩顆按鈕（`#nav-toggle`／`#nav-side-toggle`）會跟著側欄換邊**（CSS `order`，
`body[data-nav-side="right"] #nav-toggle { order: 10 }`，把它排到 header 最右端、緊貼
`#nav-side-toggle`）。**理由**：按鈕若固定留在左上角，但側欄彈在右邊，使用者會覺得
「按了沒反應」——其實有反應，只是彈在完全沒在看的另一側，這在窄視窗（側欄整個是浮層，
視線更集中在彈出的那一角）特別明顯。按鈕跟著側欄移動後，開合的入口永遠在使用者正在看的
那一側，不管視窗寬窄。`#nav-side-toggle` 同樣遵守「圖示表示按下去的結果」慣例：目前靠左
顯示「移到右側」的箭頭，反之亦然。

**⚠️ CSS specificity 約束**：靠右的「收起來」
規則多帶了一個 `[data-nav-side="right"]` 屬性選擇器，比三態那條泛用的「展開」規則
（`body[data-nav="open"] #nav { transform: translateX(0) }`）specificity 更高。
CSS 的 specificity 不看選擇器先後、只看選擇器本身「重不重」，故靠右時那條泛用展開規則
**永遠打不贏**帶了額外屬性的收起規則——結果側欄狀態明明已經是 `open`，`#nav` 卻還是卡在
`translateX(100%)`，形同完全彈不出來。**這不是只看單條 CSS 就能判斷的約束**——兩條規則分開看
都合理，只有實際跑起來量測 `#nav` 的 bounding rect 才會發現它停在螢幕外。修法是每次幫
`data-nav="hidden"/"open"` 的側寫規則時，**兩側都要各自補一條同 specificity（或更高）的
展開規則**，不能只靠一條不分側的泛用規則去對抗一條分側的收起規則。已用 `playwright-core`
（`channel: "chrome"`，指向系統既有 Chrome）實際跑 `.output/chrome-mv3/overview.html`、
量測點擊前後 `#nav` 的 `getBoundingClientRect()` 驗證過三種寬度×兩側的六種組合。

### 4.4b 工具列裡的下拉浮層錨定整條工具列，不是觸發它的按鈕

「顯示欄位」這類 `<details>` 下拉（`.rs-colbox`／`.eq-colbox`，用於艦娘／裝備／打撈／建造／
開發／遠征六個分區）**一律 `position: absolute` 錨在工具列上、`left: 0; right: 0` 與工具列
同寬**；觸發用的 `<details>` 本身**刻意不設 `position: relative`**。六條工具列
（`.rs-bar`／`.eq-bar`／`.bl-bar`／`.dl-bar`／`.el-bar`／`.vl-bar`）都已是 `position: sticky`，
本來就是定位元素，**故不必、也不該再補 `relative`**——但反過來說，日後若把某條工具列的
sticky 拿掉，下拉會往上找到更外層祖先當錨點、寬度與位置全跑掉，改動時要一併處理。

**理由**：工具列是 `flex-wrap`，觸發按鈕會隨換行移動；若浮層貼齊按鈕右緣，按鈕落到下一列的**最左**
邊，下拉仍往左展開就直接溢出內容區、被側欄整片蓋住勾選框——使用者只看到半截文字。貼齊按鈕
的做法在「按鈕位置會隨換行浮動」的容器裡不可能兩側都安全（改成 `left: 0` 只是把溢出方向換到
右邊而已）。錨定工具列後，按鈕落在哪一列都與浮層位置無關，左右都不可能溢出。

欄位格改用 `repeat(auto-fill, minmax(150px, 1fr))`：欄位多時往下長而不是往旁邊擠，也不必再
為窄視窗寫死欄數。浮層固定錨在工具列，不要貼齊會移動的觸發按鈕。

### 4.4c 本機代碼複製工具（overview）

艦隊全覽的代碼工具只整理目前 `GameState` 的唯讀 view，不開啟或連線外部網站。對話框分為
全持有裝備、出擊隊伍、支援隊伍三項；後兩項各自提供艦隊勾選，出擊隊伍另可選擇基地航空隊，
輸出為 DeckBuilder v4 JSON，艦隊依原編號連續填入 `f1`、`f2`…，基地依海域／基地編號填入
`a1`、`a2`、`a3`。複製按鈕只寫入使用者的剪貼簿，不改變顯示範圍偏好。

沒有選取艦隊或資料不完整時，輸出留空並顯示原因，不以空資料或猜測值代替。艦隊選擇控制項
需保留鍵盤焦點樣式、`role="alert"` 回饋，以及深色／淺色、`prefers-reduced-motion`、
`prefers-contrast` 下的既有 CSS 變數語言。

### 4.5 語意色不可挪用做裝飾

`--dmg-major`／`--dmg-mid`／`--dmg-minor`／rank 色只能用在其語意對應的狀態上
（大破/中破/小破、rank S/A/B/C/D）。不要因為某個顏色好看就借去用在無關的裝飾元素，
會稀釋這些顏色承載的「一眼看出狀態」功能。

### 4.6 資料視覺化：一張圖、多條線、圖例即開關

`resource-log` 的趨勢圖採用最上方一張大圖、所有序列疊在一起、圖例逐條開關的形狀。
量級差距以序列開關處理，不拆成多張圖。

1. **量級差距用「開關」解，不用拆圖、更不用雙 y 軸**。y 軸值域**只由目前顯示中的序列
   決定**：關掉十萬級的燃料，千級的螺絲就會撐滿整張圖。**雙 y 軸一律不做**——兩套刻度
   沒有共同基準，任何交叉都是視覺巧合。另外備一兩顆「常用組合」捷徑（例：只看四大資源），
   讓最常見的比較不必逐顆點。
2. **圖例是控制項，不是說明**。色塊＋名稱＋目前值，點了就開關。**關掉的序列要留在列上**
   （淡化＋空心色塊），消失掉使用者就不知道還有那一項可以打開。
3. **色彩跟著實體，不跟著排名**。第 i 個實體恆定拿第 i 個色位，開關序列時絕不重新分配
   ——否則關掉一條線會讓其他線全部換色。色盤取 dataviz skill 參考色盤的**原始順序**
   （順序一改，它保證的相鄰色對分離度就不成立了），深淺兩套各自跑 `validate_palette.js`。

四個容易做錯的細節：

- **`hidden` 是 HTML 屬性，對 SVG 元素無效**。十字準線與游標點掛了 `hidden` 照樣畫在
  (0,0)，畫面左上角會多一顆莫名其妙的點。要用 CSS `[hidden] { display: none }`。
- **不要用 `preserveAspectRatio="none"`**。非等比縮放會把軸刻度文字橫向拉伸（容器
  1600px 時字被拉成 1.6 倍寬）。等比縮放＋`aspect-ratio`，線寬另用
  `vector-effect: non-scaling-stroke` 固定成實際像素。
- **抽稀是純減量，不平滑**：每個時間桶取最後一筆、首尾必留。移動平均之類的平滑會把
  「一次活動燒掉十萬燃料」的那道陡降磨圓，而那正是這張圖唯一要看的東西。
- **x 依時間比例，不用等距索引**：取樣本來就不等距（一天打十場、隔天不上線），
  等距畫會把時間軸扭曲。

圖表元件的動效沿用 §3.1／§3.2：十字準線是即時位置回饋、沒有 transition，故
`prefers-reduced-motion` 只需處理圖例按鈕；`prefers-contrast: more` 下折線加粗、十字準線
改實線（虛線在高對比下反而更難追），**圖例的開／關不能只靠 `opacity`**（高對比下看不出
差別），改加刪除線。

### 4.7 情報總括雙欄：容器夠寬就並排（硬約束）

情報總括裡「左選右看」的分區（配裝參考的艦清單／裝備區、任務導覽的目錄／選中）**必須
在內容區還能並排時維持左右兩欄**。右側出現一大片空白、左側清單卻被整塊堆到上面，就是
違規。

**禁止**用 viewport `@media (max-width: 760px)`／`820px` 這類「視窗看起來不算窄」的斷點
把這類雙欄改成單欄。理由：

1. **viewport 不是內容區**。側欄釘選佔 200px，再加上 `#content` 內距；視窗 900px 時內容
   區可能已低於 820，但艦清單 240px 旁邊仍放得下裝備區。
2. **側欄在 ≤760px 才轉浮層**（§4.4）。那個斷點管的是導覽要不要佔寬，不是內容要不要
   改單欄。任務導覽在 ≤760px 仍維持 `.qf-board` 兩欄，配裝參考必須同一標準。
3. **真的放不下才改單欄**。配裝參考以 `.er` 為 container，只在容器 **≤520px**
   （艦清單下限 240 + gap 12 + 裝備區還能讀）才改單欄，並限制艦清單高度讓裝備區仍看得到。
   用 `@container` 量內容區，不要用 `@media` 量視窗。

新的左右並排分區照這條：先算左欄下限＋間距＋右欄還能讀的最小寬，用 container query
（或 `minmax(min(Npx, 100%), …)` 這種會在更窄時自己收）承接，**不要先寫一個 800 上下的
viewport 斷點再說**。測試：`tests/overview-two-pane-layout.test.ts`。

### 4.8 同名艦種標籤：不得兩顆都叫「戰艦」（硬約束）

`api_mst_stype` 的 id 8 與 9 都叫「戰艦」。篩選晶片若用名稱當 Map key、或列上直接寫
`stype` 字串，就會出現兩顆一模一樣的「戰艦」、低速／高速戰艦也無法分辨。

分類與顯示**必須**走 `utils/stype-label.ts`（艦娘全覽與配裝參考共用）：

- 篩選控制項鍵仍是 **stype id**。名稱真的重複時才加註；多數高速的那群顯示「高速戰艦」，
  另一群維持「戰艦」。低速側不加「低速」。
- 列上用該艦自己的 `api_soku`，不得用 stype id 當航速捷徑（stype 8 有低速 Гангут 線，
  stype 9 有高速深海戰艦棲姫改）。
- `overview/ship-picker.ts` 的 `rebuildStypeLabels` **沒有**這套消歧，新分區不要抄它。

測試：`tests/ships-stype-label.test.ts`。

## 5. 圖示

圖示生成器與完整設計約束在 [tools/icons/README.md](../tools/icons/README.md)，
**改圖示前必讀**，這裡只列會影響「介面設計」判斷的結論：

- **裝備／資源／UI 76 顆＋數值 17 顆全部由 `tools/icons/` 的 python 生成器產生，禁止手改 SVG**——改生成器再重跑。數值圖在 `public/icons/stat/`（`gen_stats.py`）。
- **全圖示帶統一深墨描邊**（`INK = #37302a`，`feMorphology` 外輪廓）——這是亮暗主題
  切換的前提（SVG 以 `<img src>` 載入吃不到外部 CSS，無法靠 CSS 改色，描邊讓圖示
  在亮底/暗底都自足可讀）。**新增圖示或討論圖示改動時，這個約束不可放寬。**
- **暗底明度下限**（HSL 明度 ≥ 0.26）是硬約束，禁用近黑色（會被深色面板背景吸收）。
- **尺寸已正規化**（`normalize.py`，較長邊=29 單位、置中）——並排 chip 顯示時各圖示
  視覺高度一致，這是既有保證，不要在新增圖示時繞過正規化流程手動調尺寸。
- 徽章（飛機族機型標記）**不參與縮放**，固定尺寸——因為它是小圖下的主要辨識信號。
- 配色語言：口徑→明度分級（`#ff8080→#ff4040→#ff0000`）、機身色統一靠徽章色區分機種，
  不是靠機身變色。新裝備圖示要延用同一套邏輯，不要每顆自訂一套配色規則。

### 5.1 面板系統圖示：擬真剪影語言（定版）

本節是本專案**所有 panel 系統圖示**（現有與未來）的定版風格指標。除非使用者
明確指示修改，砲擊支援、雷擊支援、航空支援、對潛支援、陸航、索敵雷達、觸接、
對空 CI 機槍、夜戰與友軍等系統圖示，以及之後新增的 panel 系統圖示，都必須沿用
這套語言。這裡的「系統圖示」是面板中表達戰況或系統狀態的圖示，不是艦娘裝備列的
既有裝備／資源／UI SVG。

這套 panel 圖示語言與上方 `tools/icons/` 的 SVG 生成管線分開管理；既有 SVG 仍須
遵守上方規則與 [tools/icons/README.md](../tools/icons/README.md)，不可為了套用
panel 剪影風格而繞過或改寫既有生成器。

定版參考資產位於 `public/icons/tactical/`：砲擊支援使用
`yamato-north-style.png`，雷擊支援使用 `knox-torpedo-support.png`，航空支援使用
`comet-air-support.png`，對潛支援使用 `ka2-asw-support.png`，陸航使用
`b25-lbas-support.png`，對空 CI 使用 `bofors-40mm-aaci-mirrored.png`，弦月使用
`brass-crescent.png`；掉落櫻錨使用 `sakura-anchor-new.png`（新掉落）與
`sakura-anchor-owned.png`（已有船）；索敵雷達則是 `entrypoints/panel/main.ts` 的內嵌 SVG。預覽與
正式 panel 必須指向同一套公開資產，不得各自維護一套替代圖。

風格規則如下：

- **以可辨識的真實物件剪影為主體**：保留艦艇、飛機、雷達、機槍等物件的輪廓與
  受限的立體透視，不以 emoji、Unicode 符號或泛用幾何符號取代已有真實主體。
- **透明背景、完整取景、保留比例**：素材不得帶底色、內嵌文字或裝飾徽章；不得因
  縮放裁掉船艏、機翼、天線、砲管或弦月尖端，也不得用非等比拉伸填滿欄位。
- **暗色面板優先的金屬剪影質感**：未發動時以低明度、去彩或灰階保持退場狀態；
  發動時以黃銅／金色高光、亮度與 `--sparkle` 狀態表達啟用，不為每一顆圖示任意
  更換一套顏色。物件本身負責辨識，狀態文字與數字放在圖示外側或 hover 內容。
- **小尺寸仍要讀得出形**：底部系統列的一般圖示以約 `18×15px` 的視覺槽位呈現，寬體
  艦艇或雷擊支援可用約 `24×15px`（五格須在 370px 面板的左半欄內，不能壓到右側掉落格）；使用 `object-fit: contain`，由素材保留比例，不能
  讓不同來源的圖在欄位中互相擠壓。
- **資訊與互動分離**：圖示要有適當的 `title`／`aria-label`；Type 數字、傷害值、
  觸接飛機名稱等狀態資料不畫進圖片。需要細節時透過 hover 顯示，例如陸航對敵傷害
  或敵我觸接飛機名稱；觸控與無障礙路徑仍要有可讀的替代文字。

每次新增或替換 panel 系統圖示，都要確認透明 alpha、比例與完整取景，並在暗色面板
的啟用／未啟用狀態及 `370×850` 預覽尺寸下檢查沒有裁切、溢位或文字重疊。流程固定
為先更新離線預覽，再同步正式 panel，最後以瀏覽器檢查並跑型別、建置與測試驗證。

## 6. 刻意不做的事（整理版，含理由）

| 方向 | 為何不做 | 若要重新考慮 |
|---|---|---|
| 動畫函式庫（Motion 等） | 違反權限精簡＋零依賴（CLAUDE.md 硬約束） | 沒有觸發條件，除非專案立場改變 |
| Spring/手勢動效 | 沒有拖曳類互動，`innerHTML` 全量重繪與可中斷動畫的前提互斥 | 面板改局部 DOM diff 之後 |
| 抽共用 CSS 檔（三頁合一份） | popup 太小不值得抽；三份小到手動同步的成本低於抽象成本 | 若三份的規則開始頻繁漂移不同步，才考慮 |
| 自訂字型取代 system-ui | 系統字已含平台級光學調整，且要覆蓋 zh-TW/ja/en 三語系 | 有具體排版問題系統字解不了才考慮 |
| 圖表函式庫（Chart.js 等） | 同上：違反零依賴。目前的需求（折線＋十字準線）用純函式算幾何＋內聯 SVG 就夠，見 `utils/line-chart.ts` | 需要的圖表型別多到自己算幾何比引入還貴時 |
| 雙 y 軸圖表 | 兩套刻度沒有共同基準，交叉點是視覺巧合而非事實（見 4.6） | 不考慮——量級不同就分格 |
| 手改 SVG 圖示 | 74 顆共用同一套描邊/正規化管線，手改會破壞一致性且下次重新生成會被覆蓋 | 不考慮——一律改生成器 |
| 把資源條混進裝備 chip | 資源殘量需要保留油、彈各自的語意色與百分比，不能擠佔 chip 圖示／改修／熟練資訊 | 不考慮——油彈條固定在 chip 前方獨立排列（見 §7.4） |
| 艦隊 chip 圖示放大到 20px | 比 16px 艦種徽章高，頂到艦名 | 不考慮——圖示與徽章同高 |
| `justify-content: space-between` 消化編成餘裕 | 列距疏密失控，不像刻意排版 | 餘裕還給列內 proximity 與列 padding |
| 把預覽 850 當實機內容高 | 實機 850 含標題列，七船會裁第 7 艘 | 預覽「用掉」硬安全線 ≤740 |
| 大破進摘要徽章 | wrap 就裁七船；聯合檢視會憑空多一列 | 長在艦身（§7.4） |
| 編成列再顯示入渠倒數 | 一般分頁入渠欄已有艦名＋倒數；抄一遍違反「不要重複資訊」 | 不考慮——編成只標「入渠」 |
| 離線預覽沿用面板 `overflow: hidden` | 整頁不能捲，只能拉瀏覽器視窗 | 只解預覽頁；假窗 `.pv-app` 仍 hidden |

## 7. 面板彈窗（370×850）

面板是 `chrome.windows.create` 彈出的監控窗，不是 overview 分頁。一般分頁與編成已於
2026-08 定案；之後改出擊／遠征／工廠／調度時對齊這一節，不要為單一分子頁發明另一套
密度或把編成區推跑。硬約束的程式契約仍以 `CLAUDE.md` 慣例為準，這裡寫「為什麼」與
跨分頁要共用的視覺語言。

離線預覽：

```bash
npx vite-node --config vitest.config.ts tools/preview/panel-sortie.ts   # 出擊＋編成／連合場景
npx vite-node --config vitest.config.ts tools/preview/panel-general.ts  # 一般分頁
npx vite-node --config vitest.config.ts tools/preview/panel-general-ledger.ts  # 母港／任務／道具版面
npx vite-node --config vitest.config.ts tools/preview/panel-items.ts  # 道具頁（打包正式 general.ts；?lang=&q=&pins=&open=）
npx vite-node --config vitest.config.ts tools/preview/fleet-photo-panel.ts  # 編成寫真托盤＋header 縮放（打包正式 fleet-photo.ts；?lang=&mode=&shots=&export=1&nick=）
```

→ `.preview/panel-sortie{,-light}.html`（編成／連合艦隊由頁面上方選項切換）與
`.preview/panel-taiha-en.html`（英文大破對照）。預覽是獨立的
量測 fixture，不是正式面板的實作來源；版面變更後必須同步 `tools/preview/panel-sortie.ts`、
`entrypoints/panel/main.ts` 與相關測試。

### 7.1 視窗幾何

正式面板內容區目標寬度為 370px、高度 850px。`background.ts openPanelWindow` 建立視窗後，
`fitPanelInnerWidth()` 依實際內容區寬度補足差值；一般、遠征、出擊與下方編成都共用這個
內容寬度。正式面板 `html, body { overflow: hidden }`，不得靠外層捲軸補高度。

編成摘要 `.fs-metrics` 與單隊裝備列均以 370px 內容寬度量測。各欄必須可收縮且不得把摘要、
增設 chip 或右側資訊推到視窗外；中文與英文都要實際檢查，不能用 420px 舊基準推估。

離線預覽 `.pv-app` 對應 370×850 的面板內容區。六／七船編成連同摘要的實際底緣須在
**730px 排版目標內**，以 740px 作為不可越過的硬上限，保留至少 10px 餘裕。預覽須涵蓋
六／七船、有／無 `.fs-ops`、增設格與六格裝備等情境，摘要需放入正式會顯示的欄位。

### 7.2 垂直切分

上到下固定切分，編成不隨資訊區內容上下跑：

| 區塊 | 高度 | 備註 |
|---|---|---|
| header＋分頁列 | ≈70px | 只准收 padding，不准加 |
| `#tabpanel` | **270px 釘死** | 禁止改 `max-height` 讓不足時收縮 |
| `#fleetnav` | ≈32px | |
| `#fleets` | 其餘 | 瓶頸是單隊七船 |

一般分頁在固定的 `#tabpanel` 內切換母港、任務與道具。母港的八項資源採 4×2 圖示加數值，
完整名稱放在提示與輔助標籤；遠征、入渠、建造各自切換並依封包資料列出狀態。任務列出
全部受注項目；八項收攏狀態須在 270px 面板內全數可見，展開說明造成內容超出時才在任務清單內捲動，
以原生 `<details>` 顯示完整敘述且不重複加「任務說明」標籤。四個入渠與建造船塢列須完整放在母港區內，
正常船塢上限時不出現捲軸。道具搜尋列平時收起，由道具欄分頁列右端的放大鏡展開，收起或按 Esc
即清空條件，避免看不見的篩選殘留；搜尋
同時比對繁中、日文及英文名稱與兩個道具欄。釘選的道具依釘選先後排在所屬道具欄最前面、名稱前加黃銅圖釘，
釘選鈕只放在展開內容，不佔收攏列寬；釘選存 localStorage（`kc-item-pins`），不進備份。
「持有量依最近取得的遊戲資料」只放在數量提示，不另佔一列；未取得可靠持有量前，名稱索引不得顯示
預覽數字作為即時持有量。切換、展開、輸入與捲動均不得改變 `#tabpanel` 高度或推動下方
編成。倒數每秒只改既有文字節點；任務 DOM 僅在清單內容變化時重建。

出擊戰鬥列第二列另釘 **165px**；陣型／支援／対空CI／夜戰／rank／友軍列釘在敵艦區下方，
不隨敵艦數量上移。敵艦少於 6 時列內留白是刻意的。

有餘裕時，先調整名稱、HP 與裝備列之間的留白，再調整艦列外距。**不准**用
`justify-content: space-between` 把底部空間攤開；不准加高 850 或讓正式 panel 長出捲軸。
連合 compact 使用自己的雙欄密度，不套用單隊六／七船列距。

七船由 `main.ts` 依 `f.ships.length >= 7` 加上 `.fleet-seven`，CSS 只對
`.fleet.fleet-seven` 收緊；不能用 `.ship:nth-of-type(7)`，因為 `.fsummary` 同樣是
`div`，會使艦列序號判斷失真。

header 固定 39px、單行：提督名＋Lv、艦數、裝備數、相機鈕。提督名放得下時維持原字級；會被
截斷時整排以 `--hs` 等比縮小（`entrypoints/panel/header-fit.ts`），名稱維持完整，不改成上下兩行，
也不改變 header 高度。驗收以 12 個全形字＋3 位艦數＋4 位裝備數為最寬情境。

編成寫真托盤（`#photo-tray`）開啟時取代 `#tabpanel`，同樣 270px：標題列、提示列（拍攝後改顯示
結果或錯誤）、格線區、底列（拍下一張／輸出設定／輸出 PNG／複製）。格線區以 container 尺寸推算
格子大小，任何艦數都不撐破 270px。艦隊為 2 欄、由左而右再往下，與遊戲編成畫面相同；格子是
「縮圖＋艦名／編號・Lv／狀態」橫排。基地航空隊為一列直式縮圖，欄寬固定三分之一、不足三隊時
置中。只有「下一張」用黃銅強調；需重拍的格子淡化縮圖並以文字標示，不借用大破等語意色。
輸出設定用原生 `<details>`，托盤更新時保留同一份控制項，展開狀態與選單不被重繪洗掉。
拍攝來源以遊戲分頁區分：唯一來源自動選取，多個來源須在設定的「遊戲分頁」選單指定；未選時顯示提示並展開設定。

### 7.3 資訊階層

同一 370px 面板只准一套權重，出擊／遠征對齊編成，不要各分頁自己定主數字。`.fs-ops` 與 `.fs-metrics` 是摘要列例外：依 §1.5 統一使用正常字重，不以粗體建立階層。

| 層 | 視覺 | 編成例子 | 其他分頁應對齊 |
|---|---|---|---|
| 主數字 | `--text`／`font-weight: 600` | 制空、索敵、殘 HP | 遠征倒數、出擊 rank／殘 HP |
| 類別 | brass **線框**小徽章，無填黃底 | 艦種 32×16、10px | 遠征編號、海域代號 |
| 狀態 | 有才出現的全稱線框 tick | `.fs-ops` 泊地修理／給糧／遠征中 | 不要常駐空徽章列 |
| 輔助 | `--dim`、約 10px；士氣例外用 12px／600 | 航速、Lv 合計、TP、燃彈殘量；士氣以 `✦` 加強辨識 | 條件說明、次要數值 |
| 警告 | `--dmg-*` 只用語意 | 大破在艦身 | 出擊大破框（`.s-taiha`） |

遠征收益固定使用燃料、彈藥、鋼材、鋁土四欄表格；成功／大成功狀態併在結果名稱列，資源圖示作欄頭，數值靠右並使用等寬數字。結果狀態以簡短符號呈現，完整說明留在輔助標籤與提示，避免英文名稱與狀態互相擠壓。資源欄頭圖示需清楚可辨，數字欄左右留白以區分相鄰資源。已確認沒有收益的資源顯示 `0`，未確認的收益不得以 `0` 代替。道具收益另列並允許換行，保留隨機與大成功限定說明。成功門檻與大成功追加門檻分組；各組未達條件優先，條件及目前值留在同一列，條件區固定雙欄且允許換行；條件名稱必須覆蓋全域 `.grow` 的隱藏溢位與省略號，使用內容高度呈現完整文字，華語艦種需求需包含最長組合的換行壓測。門檻標題需重置共用 `h3` 的底線與內距：標題本身用留白與字色層級辨認，兩種門檻之間保留一條分隔線，避免每個標題都重複畫線。資源表格內保留欄頭及結果列分隔，收益與條件區之間以一條細線加留白分組，不另加整塊背景。拉丁文字依單字自然折行，避免在一般空間中逐字斷開。整個收益與條件區須在 370px 面板的 270px 高度內完整顯示，不靠內部捲軸。大成功率以 `~` 表示估算，依據留在提示文字。

一般分頁也使用同一套層級：八項資源維持 4×2，每格讓圖示與數值靠近並靠左成組，組與組之間保留
明確欄距；不要為了跨資源數字對齊，把數值推到下一個圖示旁。主要資源數值 12px／600、其他資源
11px／500，任務與運作名稱 12px／500；倒數、道具持有量與任務進度使用
`font-variant-numeric: tabular-nums` 並靠右對齊。
分頁選取以黃銅底線表示，分頁摘要數量緊鄰所屬標籤成組呈現，數字用低對比等寬數字區分，不使用提醒徽章樣式；
避免每層導覽都再加一圈卡片邊框。狀態與說明維持較小、較淡的輔助層，
但任務敘述至少 12px 並保留舒適行高。繁中道具清單可雙欄節省高度，英文與日文改單欄以減少名稱截斷；
道具清單與任務清單在各自容器內捲動，不改變面板固定高度。

編成左欄字級（出擊／遠征的名稱列對齊這套，不要吃 body 13px／1.5）：

| 用途 | 字級 |
|---|---|
| 艦名／主名稱 | 12px，行高 1.2 |
| 艦種、Lv、裝備 chip、熟練／改修 | 10px |
| 搭載數 `.oc` | 8px |
| 殘 HP 主數字 | 12px／400；上限 `/max` 10px `--dim`；3ch 等寬左對齊 |

摘要兩列互不 wrap：上面 `.fs-ops` 只在有狀態時出現；下面 `.fs-metrics` 制空／索敵為主，
航速／Lv／TP 為 metadata。索敵 `toFixed(1)`。大破**不進摘要**。

語意色不可跨功能挪用（§4.5）：大破／中破／小破、出擊標籤、資源消長、遠征加成
（`--sparkle`＝有加成）是四組不同角色。

### 7.4 編成列結構（已落地）

單隊 `.ship-body` 固定為三列內容：左側 32px 艦種標籤維持原設計，預設垂直置中；有大破、
入渠或退避狀態時，艦種標籤上移，狀態標籤出現在正下方。右側依序為艦名／等級、HP 條與
數值、士氣／油彈／裝備。HP 數字與艦名同級、正常字重；HP 條在前，數字在後。
條內三條刻度固定在寬度 75%／50%／25%（小破／中破／大破）。條長已正規化，不隨各艦最大 HP 移動；單艦隊與連合 `.hpbar` 共用。

第三列從左到右為士氣、並排的油量與彈藥百分比條、裝備 chip。百分比以白字置於各自的色條中；
完整數值保留在 hover 標題。每艦不再重複顯示泊地修理／給糧文字，這些只留在艦隊摘要。
裝備列固定五格＋增設格，五格不足時以隱形槽補齊；六格裝備／增設格都必須在艦列範圍內完整顯示。
一般裝備 chip 36px、增設格 31px、固定列寬 221px，chip 不換行、不裁切。

一至六船共用相同艦列內距與列間距：每艦上下內距 3px、三列內容間距 1px；有 `.fs-ops`
時摘要指標至首艦、艦間距皆為 5px，沒有時兩者皆為 8px。七船另依 730px 高度目標收緊：
有 `.fs-ops` 時摘要指標至首艦、艦間距皆為 3px，沒有時皆為 4px；底部保留完整安全空間。
艦種徽章保留原本外觀與位置規則。

大破長在艦身：列底洗紅、不畫外框；艦種下方紅底標籤、殘 HP 轉紅；標籤不得另外增加列高。單隊標籤在
32px 狀態槽（`.ship-state`／`.taiha-hp-mark`），連合覆蓋士氣位置（`.taiha-cond-toggle`）。
英文用社群短稱 `Taiha`，退避英文簡作 `Esc`，與「大破」「退避」同密度，避免拉丁文把
艦列撐高。退避不算大破；單隊列退避時淡出艦種／身分／輔助／次列，狀態槽標籤保持對比。
入渠中改顯示「入渠」（與一般分頁入渠同一顆 `#7fd0ff`），不算大破警示；**不附倒數**
（倒數已在一般分頁入渠欄，見「不要重複資訊」）。
連合 compact 同一套階層，但使用自己的精簡艦列與橫向 HP 條，**不顯示**泊地修理／給糧；一般
裝備槽（包含飛機搭載數）固定維持單一 row，五格空母不得因搭載數而另起一列。
370px 雙欄以「編成預覽｜連合艦隊雙欄」、「編成預覽｜連合六格極限」與
「編成預覽｜連合艦隊大破狀態」三個場景校正欄寬、列距及狀態標記。欄間距與艦間距皆為
6px；五格裝備加增設格須完整保留在艦列內，窄欄使用 14px 裝備圖示與 8px 數字，增設格滿改
以星號顯示。繁中與英文均須檢查，不可只確認一般雙欄情境。

出擊中的完整大破警告是另一件事：`.s-taiha` **absolute** 釘在 44px 航空戰格內，不參與
版面計算、不得畫出格外（見 CLAUDE.md 慣例第 5–7 點）。英文兩行短句（`Taiha!`／
`No retreat`），對齊中文「大破！」與「注意，不可退避」的密度。

### 7.5 離線預覽契約

`tools/preview/panel-*.ts` 內聯 `panel/index.html` 的 `<style>`。預覽必須使用正式的
370px 視窗尺寸與 `.ship-body` 三列結構；遠征基本成功與大成功門檻須分組、各組以雙欄逐列排列，
未達條件置前，文字允許換行，不以省略號隱藏條件。預覽與正式面板必須使用同一套艦隊樣式；
四項資源、雙門檻、英文長文字與 12 項條件場景都須量測，確認遠征資訊區無捲軸且不推動編成。

正式面板的 `html, body { height: 100%; overflow: hidden }` 是彈窗用的。預覽頁必須覆寫：

```css
html, body { height: auto; overflow: auto; }
body { display: block; }
```

假視窗 `.pv-app` 維持 `overflow: hidden`＋850px，裁切行為跟實機一樣。

### 7.6 改其他分頁時的對齊清單

出擊／遠征／工廠仍畫在同一個 270px `#tabpanel` 裡，下面編成不能被推跑：

1. 不准放寬 270px，不准拆 165px 戰鬥列釘，不准讓陣型列隨敵艦數上移。
2. 主數字／類別／狀態／輔助／警告用 §7.3 同一套，不要另發明 pill 或黃底標題。

3. 缺值不是 0、不是最小值（算不出來顯示「不可考」）。
4. 有輸入框或展開狀態的區塊不能全量重繪到讓焦點／捲動被洗掉。
5. 先做離線預覽（假窗 370×850、頁面可捲、量測七船 ≤730px），再改 `entrypoints/panel/`。
6. 改完 rebuild；已開的面板要關掉再開（`fitPanelInnerWidth` 與舊窗寬）。
7. 依 §2.4 至少核對台灣華語與英文排版，不得只看一種語言結案。

### 7.7 出擊面板訂版基線（2026-08-22）

出擊分頁目前樣式是後續修改與 review 的**基線**。除非使用者明確要求替換其中一項，不能以
舊版 CSS、舊預覽或「整理」為由回復下列設計；提出變更前先更新
`tools/preview/panel-sortie.ts`，再一併更新 `tests/panel-sortie-layout.test.ts` 的契約。

1. 標頭的 Gauge 不得保留固定 122px 寬度；以 10 個 node（含 Boss）為容量下限，Gauge
   數字在條外、`Final` 在條內，node 維持遊戲原始圓形與 Boss 樣式。
2. 左側依序為制空／航向、Result Rank／敵陣形、敵我飛機戰損、夜戰裝備與友軍；敵艦為右側
   chip 區。敵艦 chip 只呈現名稱、擊沉狀態與 HP 血條，**不重複寫目前 HP 數字**；每格固定
   25px 高，敵艦較少時保留列內留白，不得拉高單格填滿整列。
3. Result Rank 使用遊戲 Result 的斜體襯線、描邊與固有色相；陣形圖示固定黃銅色。
4. 探照燈、夜偵、照明彈、友軍錨，以及月亮／主隊／伴隨夜戰目標指示固定占位，以亮暗表示
   狀態（夜戰裝備與友軍錨未發動或狀態未知時一律灰階，發動才顯示原色）；無夜戰時只套用暗色，不可因尚未夜戰而移除整列。日戰預測的主／伴目標以 KC3Kai
   規則標示，實際夜戰封包抵達後由 `api_active_deck[1]` 覆蓋。
5. 一般大破預設以紅色覆蓋框顯示「大破！」與退避條件（英文為 `Taiha!`／`No retreat`
   等短句，須收進 44px 航空戰格）。點擊後只隱藏這兩行文字、保留同尺寸
   紅框並重新顯示被覆蓋的飛機戰損；這不是收縮態，不得改變列高或移動位置。新節點或新戰鬥
   回到完整警示。旗艦大破優先顯示強制返航訊息，且不得同時顯示司令部退避。

節點軌跡不再另占狀態文字標籤：已驗證的非戰鬥節點使用藍色、能動分歧使用白色；目前出擊節點
以藍綠光暈標示，Boss 保留原本的 Boss 圖形。掉落晶片只保留底色，已有掉落內容不繪製外框；
空的 Drop 位置仍可使用虛線提示尚未有掉落。Rank 名稱優先在自身欄位換行顯示完整字樣，仍不得覆蓋陣形圖示；兩行仍放不下才省略。

這份基線的程式防線是 `tests/panel-sortie-layout.test.ts`；該測試失敗時，不得以刪除斷言
繞過，必須先取得使用者對相應基線變更的明確同意。

## 使用方式

之後提出介面或圖示修改時，先對照本文判斷：

1. 這是新角色/新規則，還是既有規則的變體？→ 變體直接套用第 1–4 節的現有變數/量表。
   **改的是面板彈窗**（一般／出擊／遠征／工廠／編成）→ 先讀 §7，270px 資訊區與七船
   預算不准為了「這一分頁好看」放寬。
   **改的是情報總括左右並排分區**→ 先讀 §4.7，容器還放得下兩欄時不准改單欄往下堆。
   **改的是艦種篩選／列上艦種名**→ 先讀 §4.8，stype 8／9 不得兩顆都顯示「戰艦」。
2. 這個方向是否在第 6 節列為「刻意不做」？→ 若是，先確認觸發重新考慮的條件是否成立，
   不要重新從零推導一次。
3. 影響圖示？→ 先讀 `tools/icons/README.md`，改生成器，不手改 SVG。
4. 落地前依 §2.4 至少核對台灣華語與英文排版。

改動落地後，若引入新的角色變數／量表值／版面約束，**回來更新本文**，維持它描述目前
實際狀態與可驗證理由。
