# 專案補完計畫

本檔的第 1～7 節是**尚未實作的計畫**，不是現行行為。某一項做完並經開發者驗證後：
1. 把它的現行事實寫進 `docs/engineering/` 對應主題檔。
2. 在第 8 節「已完成項目」登記完成日期、commit 與現行行為所在。
3. 從第 3 節總覽表與第 4 節刪掉該項的列與小節本文（順序編號與小節編號都不重排，缺號就是已完成）。

內容與程式碼不一致時以程式碼為準。外部資料的查證基準日是 2026-11-11。

## 1. 排序的依據：對這款遊戲的理解

艦これ把「現實時間」換成「有限次數的賭注」。資源是用來買嘗試次數的；期限、亂數與不可逆的
損失把它變成後勤問題。由此推出四個判斷，本計畫的每一項都對應其中之一：

1. **貨幣是時間與注意力。** 基本資源每 3 分鐘自然回復（燃彈鋼 +3、鋁土 +1），到司令部等級
   決定的上限就停；之後的收入來自「艦隊數 × 玩家不在的時間」。玩家每次登入是在安排離開後會
   發生什麼。
2. **限制玩家的是最短的那塊板，而且每個人不同。** 基本資源上限 350,000、高速修復材 3,000；
   資深玩家常卡在改修資材、開發資材、設計圖等離散資材，新玩家卡在燃彈。流進已滿資源的收入
   是浪費。
3. **資源的單位是「一次嘗試」。** 通關成本＝期望嘗試次數 × 每次成本（補給、修理、修復材、
   艦載機補充、時間）。
4. **勝負在按下出擊前就決定，而錯誤不可逆。** 進戰鬥後只剩陣形、夜戰、進退三個決定。

收斂成一個模型：**目標 → 需求 → 庫存 → 流量 → 到達日**。改造、改修、備蓄是它的三種目標；
第 3 點的「每次成本」是它的單價。

功能的取捨判準是「是否減少一個決策或防止一個錯誤」。只增加資訊、不改變決策的功能排在最後。

## 2. 跨項目原則

- **不預設玩家的瓶頸，也不預設課金行為。** 專案是公開的：改修資材、開發資材等可以在官方
  道具屋購買，每位玩家的取得管道不同。因此關注哪種資材、目標是什麼，一律由玩家自己指定；
  工具只呈現觀測到的流量。帳上對不到來源的增減一律歸「未歸因」，不標成購買，不出現購買建議，
  也不把「不購買」當成計算前提。
- **三種數字分開呈現。** 封包事實（精確）、公式推算（標「推算」）、算不出來（標「不可考」，
  不以 0 頂替）。同一張表混用時逐格標示。
- **歷史不回填。** 新的帳從該功能上線那一刻開始累積，空狀態直說原因（同資源紀錄的既有做法）。
- **硬約束照舊。** 尤其是被動觀察、不上傳、不加權限、未驗證欄位不猜（`AGENTS.md` 硬約束 1、
  2、7、8），以及 derived tables 只經 `EventProjector` 寫入（硬約束 5）。
- **`db.wanted` 的鉤子不得擴充。** 本計畫需要的新樣本由開發者從既有除錯介面或 DevTools 手動
  提供，不靠新增擷取鉤子。

| 9 | 遠征組合建議 | 4.9 | 以我的作息與缺口，三隊該跑什麼？ | 總括「遠征紀錄」 | 6 | 中 | 不變 | 2 個；Sonnet 5.5 高 |

**三種畫面各有歸屬，不混在同一個分區**：

- **紀錄**回答「發生了什麼」：分帳放在資源紀錄、出擊帳單放在出擊紀錄。它們是事實，沒有玩家的
  意圖。
- **目標**回答「我想要什麼、還缺什麼、哪天湊得齊」：只有「目標規劃」分區。裡面每一筆都是玩家
  自己宣告的終點（某艘艦改到某個形態、某種資材存到某個量），分區替它算需求、缺口與到達日。
  沒有玩家宣告就沒有內容；它不放紀錄，也不主動建議該設什麼目標。
- **提醒與建議**回答「現在該做什麼」：閒置檢查、出擊前差異檢查、遠征組合建議，放在
  玩家做那件事的地方（面板、任務導覽、遠征紀錄）。

分區名稱維持「目標規劃」，不叫「改造目標」：備蓄目標與到達日之後也放在這個分區，現在用較窄的
名稱日後還得再改一次，而分區 id、文案鍵與使用者的書籤都跟著名稱走。

分帳與目標規劃的關係是供應：分帳算出的淨流量是目標規劃推算到達日的輸入，但分帳的畫面留在
資源紀錄。§1 的「目標 → 需求 → 庫存 → 流量 → 到達日」是整份計畫的資料模型，不是某一個分區的
範圍。

**開工方式**：一個 session 做一格。開新 session、選表中建議的模型，說「做補完計畫順序 N 的第 K
個 session」，agent 會從 `AGENTS.md` 的索引讀到本檔的對應小節。開工前本檔與已完成的項目必須
已經 commit，否則在獨立 worktree 開的 session 看不到。

目標倒推的第一階段（改造目標）只用遊戲 master 與目前庫存，不依賴任何分帳，而且是全計畫設計量
最大的一項，所以排最前、用最強的模型做；第二階段（到達日）要等分帳完成才有流量可用。
登出前閒置檢查、出擊前差異檢查、改修日程互不依賴，可以穿插在大項之間做。已完成的出擊帳單
（見第 8 節）是基本資源分帳與到達日推算的單價來源。

每項「建議模型」以 2026-11 可用的 Claude 模型為準（Fable 5.2、Opus 5.5、Sonnet 5.5、
Haiku 5.5），是擬定者的判斷，不是量測結果。通則：

- **動到資料模型的 session**（`utils/state.ts`、`event-projector.ts`、`db.ts`、備份格式）：
  用最強的模型、高 effort，先進 plan mode 列出所有會碰到的地方再動手。錯一次的代價是使用者
  資料。
- **純函式加 Vitest 的 session**：Sonnet 5.5、中～高 effort 足夠，前提是規格（本檔該項的
  「資料依據」）已經寫死。
- **介面與三語文案的 session**：Opus 5.5 或 Fable 5.2、中 effort。版面判斷與三語排版需要
  品味，但邏輯輕；先出 `.preview/` 預覽給開發者看再定案。
- **資料轉寫**（經驗表、獎勵解析、改修表）：寫產生器腳本從原始資料轉，不讓模型手抄數字；
  腳本本身用 Sonnet 5.5 即可，產出物加測試比對抽樣值。
- **每項拆成二到三個 session**，順序固定為「純函式＋測試 → 投影與資料表 → 介面與預覽」。
  每個 session 結束於開發者在實際介面確認，確認後才 commit。
- **規格已寫死、可獨立驗收的子任務**（文件修訂、離線預覽腳本、三語文案、照既有樣式的介面、
  資料轉寫腳本）由主模型分派給較便宜的模型，主模型負責看 diff 與跑測試驗收；動到資料模型的
  核心設計不分派。

## 4. 各項內容

### 4.4 登出前閒置檢查

**問題**：面板會告訴玩家每件事何時結束，但不會指出「現在有產能空著」。

**放置原則：不新增列或區塊，只在既有標籤加標記。** `#tabpanel` 釘死 270px（design-guidelines
§7.2），母港的入渠與建造船塢列規定不得出現捲軸，多一列摘要就會壓到清單；而且閒置的事實
（空渠、待修艦、在港艦隊）面板已經各自顯示，再彙整一次會違反「同一事實只完整呈現一次」。
所以提醒只指向「哪個標籤裡有空著的產能」，細節由玩家點進該分組看。

**檢查項與標記位置**（演習以外都來自既有 `GameState`）

| 檢查 | 標記位置 | 備註 |
|---|---|---|
| 第二到第四艦隊沒有出遠征，也不在出擊或支援中 | 母港「遠征」分組標籤 | 標出閒置隊數 |
| 有待修艦，且有空的入渠槽 | 母港「入渠」分組標籤 | 兩個條件同時成立才標 |
| 已接任務中進度已達成但未領獎 | 一般分頁「任務」標籤 | 動手前先確認 `quest-progress.ts` 的判定夠用 |
| 今日演習尚有次數 | 待預覽時決定 | 見下方「演習」 |

分組標籤現有的計數是「運作中的件數」，閒置標記不得改變這個數字的意思，要另外呈現；樣式不得
借用大破、未補給等既有語意色（design-guidelines §4.5）。標籤列的寬度在台灣華語、英文、日文
三語下都不得撐破，四個分組（含「泊地」）同時出現也一樣。

未補給與基地航空隊機數未補滿不列入：面板已有紅框提醒，再標一次是重複。

**演習**
- 剩餘次數＝`api_get_member/practice` 回應中 `api_list` 5 個對手裡 `api_state === 0` 的個數。
  `api_state` 語意依 KC3Kai `src/pages/devtools/themes/natsuiro/natsuiro.js`（`PvPList`）：
  0 為未交戰，1–6 依序為評價 E、D、C、B、A、S。開發者提供的清單回應證實未交戰為 0；已交戰的
  值目前只有 KC3Kai 一個來源，取得交戰後的清單回應時再交叉比對。
- 對手清單於 03:00、15:00 JST 換新。換新後尚未觀測到新清單時，剩餘次數不可考，不得當成 5 場。
- `GameState` 目前不保存對手清單，要新增這份觀測；它只作提醒用的狀態，不進 derived tables。
- 清單回應含其他提督的名稱、ID 與留言，存入 `samples/` 前把這些欄位換成空字串或假值。
- 實作時在 `THIRD-PARTY-NOTICES.md` 的 KC3Kai 條目補登此欄位的參照。

**做法**：純函式回傳各標籤的閒置標記（有無、數字、指向的艦隊或槽位），可用 samples 與 Vitest
獨立驗證；面板只負責把標記掛到既有標籤，不改變 `#tabpanel` 與編成的任何高度。只提醒，不排程、
不通知。

**範圍外**：建議入渠順序；跨分組的彙整摘要；任何自動操作。

**建議**：兩個 session。純函式用 Sonnet 5.5 中 effort；面板版面用 Opus 5.5 或 Fable 5.2
中 effort，先給預覽。

### 4.5 基本資源分帳與溢出

**問題**：燃彈鋼鋁的淨收入是多少；哪些收入因為撞到上限而白流。

**資料依據**
- 自然回復：每 3 分鐘燃彈鋼 +3、鋁土 +1，到司令部等級決定的自然回復上限為止；基地航空隊設為
  休息時鋁土回復速度減半（wikiwiki「資材」頁）。
- 上限：基本資源 350,000、高速修復材 3,000（同頁，2020-11-13 起）。
- 支出：出擊帳單（`db.sortieBills`，見 [`docs/engineering/records.md`](engineering/records.md)）、`db.factory`；收入：`db.expeditions` 的 `resources`（精確）、任務獎勵
  的結構化資源欄位。

**缺口**
- 自然回復上限與司令部等級的對應式要從 wikiwiki 表格轉寫並加測試；自然回復量本身是推算，
  因為兩筆餘額之間玩家可能不在線上。
- 上限為基本資源 350,000、高速修復材等 3,000，開發者已確認。持有量可以超過上限：依開發者的
  判斷，任務獎勵會照發而突破上限（同理，任務取得艦娘也會超過船位上限）。所以「超過上限」是
  合法狀態，溢出提醒不得把它當成資料錯誤。
- 近代化改修、解體、廢棄的資源進出目前沒有紀錄列。

**做法**：沿用離散資材分帳（`utils/material-ledger.ts`）的恆等式函式，加入自然回復這個推算來源與「未歸因」。溢出提醒分兩種：
已達硬上限仍有收入的資源，以及超過自然回復上限因而不再自然回復的資源；兩者都只在資源紀錄
分區與 4.4 的摘要列呈現一次。

**建議**：兩個 session。Sonnet 5.5 高 effort 做函式與測試；介面沿用資源紀錄的離散資材分帳。這項不該新增資料
表，若發現需要，停下來重新評估範圍。

### 4.6 目標倒推（目標 → 需求 → 庫存 → 流量 → 到達日）

**問題**：玩家腦中有目標（把某艦改到某個形態、活動前存到某個量），但要自己查需求、自己算
缺口、自己估時間。

**第一階段（改造目標）已實作，待開發者在實際介面驗證**；現行行為見
`docs/engineering/goals.md`，驗證後把本段刪除。尚未做的是下列各階段。

**第一階段留下的缺口**
- 目標只能從「目標規劃」分區自己的候選清單加入，艦娘全覽還沒有入口。
- 推算類消耗（開發資材、高速建造材、新型砲熕兵裝資材、改修資材、工廠資源）取自外部參照表，
  新艦實裝後要重跑 `tools/remodel-cost/generate.py` 才會更新。

**後續階段的資料依據**
- 流量：離散資材分帳（`utils/material-ledger.ts`）與 4.5 的分帳結果。
- 改造當下的實際消耗：`db.materialUse` 的改造紀錄配改造前後的餘額差，可用來校正推算類消耗。

**做法**
1. 第二階段接上流量：對每個缺口，以最近一段期間觀測到的淨流量推到達日，顯示為區間；觀測
   期間不足時顯示不可考。流量取自玩家自己的紀錄，不套用任何「標準玩家」的假設。
2. 第三階段加入備蓄目標（指定資材與目標量），與改造目標共用同一套庫存分配。
3. 從艦娘全覽加入目標的入口可以獨立做。

**範圍外**：推薦該改造誰；練等地點建議；改修目標（改修只做 4.7 的日程，不算消耗）。

**建議**：第二階段要等 4.5（離散資材分帳已完成），計算部分用最強的模型；艦娘全覽的入口是照既有樣式的介面，
可分派給較便宜的模型。備蓄目標沿用 `db.goals`（主鍵已帶種類前綴），加新種類時要同步放寬
備份驗證並升備份格式版本。

### 4.7 改修日程

**問題**：玩家想在本工具直接看到今天能改修什麼、要用哪艘二番艦，並保留自己用過的配方。

**範圍界線與理由**：完整的改修資料量大且隨營運更新，社群網站的更新速度本專案追不上；面板
既有的「明石改修工廠一覽」外部連結就是為此而設，維持不變。本項不做消耗表、不做全裝備改修
百科、不接到目標倒推的缺口計算。

**資料依據**
- 星期與二番艦：KC3Kai `src/data/akashi.json`（MIT；星期 → 裝備 id → 二番艦 master id
  清單），以產生器腳本轉成本專案的資料模組。
- 玩家用過的配方：既有的工廠紀錄 `db.factory`（`kind: 'improve'`，含裝備、改修前後等級、
  成敗、是否確實化、當時的秘書艦）。

**缺口**
- `akashi.json` 的更新取決於上游，表內沒有的新裝備顯示為「尚未收錄」，並保留外部連結。
- `db.factory` 的 `secretary` 是第一艦隊旗艦（明石），二番艦目前沒有記錄；要不要補記是實作時
  的決定，補記會動到工廠紀錄的資料列。

**做法**：依今天的星期（JST）與玩家持有的裝備、艦娘，列出「今天可改修且持有二番艦」的裝備與
可用二番艦；另列玩家自己的改修紀錄彙總（哪個裝備改過幾次、成功率）。放在總括或面板的位置於
實作時先出預覽。

**範圍外**：消耗量、成功率預測、推薦改修什麼。

**建議**：一到兩個 session，Sonnet 5.5 高 effort；資料用產生器腳本轉，不手抄。

### 4.8 出擊前差異檢查

**問題**：既有的防呆守住了大破進擊與出擊札，沒守的是平凡的準備疏失：支援艦隊沒派、基地
航空隊還在待機、裝備沒換回來。

**資料依據**：`db.replays` 在 `api_req_map/start` 保存主隊、隨伴、支援與基地航空隊的快照
（`ReplayRow`）。拿「上一次在同一海域達成目標的那次出擊」當基準，與目前母港狀態比較。

**缺口**
- 「達成目標」的定義：先用「到達王點且 S 勝」；玩家可改指定任一筆出擊當基準。
- 重播會被保留規則裁剪，基準不存在時顯示沒有可比對的紀錄，不退而用別張圖。
- 檢查只能在母港做（玩家選好海域之前，工具不知道要打哪張圖），所以由玩家在面板選定基準
  後才顯示差異。

**做法**：純函式比較兩份編成快照，輸出差異清單（艦、裝備、支援有無、基地航空隊的行動與
配置）；面板在母港檢視提供「對照上次成功的編成」入口。只列差異，不判斷對錯。

**範圍外**：編成建議；航路預測（常規導航已有）。

**建議**：兩個 session。差異函式 Sonnet 5.5 高 effort；面板入口與版面 Opus 5.5 或
Fable 5.2 中 effort，先給預覽。

### 4.9 遠征組合建議

**問題**：三隊遠征是資深玩家唯一的經常性收入，但組合取決於玩家的作息與缺口。

**資料依據**：`utils/expedition-data.ts`（需求與報酬）、`expedition-bonus.ts`（大發加成）、
`db.expeditions`（玩家自己的成功與大成功紀錄）、4.5 的溢出結果。

**缺口**：回航道具依 `api_useitem_flag` 投影（KC3Kai、ElectronicObserver 交叉比對，本專案沒有樣本），
修正前的紀錄缺高速修復材、高速建造材、開發資材，所以離散資材的遠征收益只能用修正後玩家自己的
歷史平均，樣本不足時標不可考。

**做法**：玩家輸入這次會離開多久與關注的資材，工具從已開放的遠征裡排出三隊組合，並排除
會流進已滿資源的選項。只給排序與理由，不檢查玩家有沒有編得出來的艦隊。

**建議**：兩個 session，Sonnet 5.5 高 effort。放在最後，因為它的價值要靠 4.5 才完整。

## 5. 不排入本計畫的項目

| 項目 | 理由 |
|---|---|
| 夜戰 CI 率、對空 CI 預估 | 只增加資訊，不改變出擊當下的決策；公式（wikiwiki「夜戦」）已查證，日後要做不缺資料 |
| 戰果估算 | 只對衝排名的玩家有用；公式（wikiwiki「称号・戦果」）已查證 |
| 演習經驗預估 | 價值低；對手清單封包沒有樣本 |
| 緊急泊地修理 | 找不到可信的規則出處，也沒有樣本 |
| 把資料送到外部統計站、雲端 LLM | 違反不上傳與權限精簡 |
| 活動特效偵測 | 要由異常傷害反推，複雜且容易誤報 |
| 改修消耗表與改修百科 | 資料量大且隨營運更新，交給社群網站；面板保留外部連結 |
