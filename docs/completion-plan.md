# 專案補完計畫

本檔的第 1～7 節是**尚未實作的計畫**，不是現行行為。某一項做完並經開發者驗證後：
1. 把它的現行事實寫進 `docs/engineering/` 對應主題檔。
2. 在第 8 節「已完成項目」登記完成日期、commit 與現行行為所在。
3. 從第 3 節總覽表與第 4 節刪掉該項的列與小節本文（順序編號與小節編號都不重排，缺號就是已完成）。

內容與程式碼不一致時以程式碼為準。外部資料的查證基準日是 2026-11-11。

## 1. 排序的依據：對這款遊戲的理解

艦これ把「現實時間」換成「有限次數的賭注」。資源是用來買嘗試次數的；期限、亂數與不可逆的
損失把它變成後勤問題。由此推出四個判斷，本計畫的每一項都對應其中之一：

1. **貨幣是時間與注意力。** 基本資源每 3 分鐘自然回復（燃彈鋼 +3、鋁土 +1），到司令部等級
   決定的上限就停；之後的收入來自「艦隊數 × 玩家不在的時間」。玩家每次登入是在安排離開後會
   發生什麼。
2. **限制玩家的是最短的那塊板，而且每個人不同。** 基本資源上限 350,000、高速修復材 3,000；
   資深玩家常卡在改修資材、開發資材、設計圖等離散資材，新玩家卡在燃彈。流進已滿資源的收入
   是浪費。
3. **資源的單位是「一次嘗試」。** 通關成本＝期望嘗試次數 × 每次成本（補給、修理、修復材、
   艦載機補充、時間）。
4. **勝負在按下出擊前就決定，而錯誤不可逆。** 進戰鬥後只剩陣形、夜戰、進退三個決定。

收斂成一個模型：**目標 → 需求 → 庫存 → 流量 → 到達日**。改造、改修、備蓄是它的三種目標；
第 3 點的「每次成本」是它的單價。

功能的取捨判準是「是否減少一個決策或防止一個錯誤」。只增加資訊、不改變決策的功能排在最後。

## 2. 跨項目原則

- **不預設玩家的瓶頸，也不預設課金行為。** 專案是公開的：改修資材、開發資材等可以在官方
  道具屋購買，每位玩家的取得管道不同。因此關注哪種資材、目標是什麼，一律由玩家自己指定；
  工具只呈現觀測到的流量。帳上對不到來源的增減一律歸「未歸因」，不標成購買，不出現購買建議，
  也不把「不購買」當成計算前提。
- **三種數字分開呈現。** 封包事實（精確）、公式推算（標「推算」）、算不出來（標「不可考」，
  不以 0 頂替）。同一張表混用時逐格標示。
- **歷史不回填。** 新的帳從該功能上線那一刻開始累積，空狀態直說原因（同資源紀錄的既有做法）。
- **硬約束照舊。** 尤其是被動觀察、不上傳、不加權限、未驗證欄位不猜（`AGENTS.md` 硬約束 1、
  2、7、8），以及 derived tables 只經 `EventProjector` 寫入（硬約束 5）。
- **`db.wanted` 的鉤子不得擴充。** 本計畫需要的新樣本由開發者從既有除錯介面或 DevTools 手動
  提供，不靠新增擷取鉤子。

**三種畫面各有歸屬，不混在同一個分區**：

- **紀錄**回答「發生了什麼」：分帳放在資源紀錄、出擊帳單放在出擊紀錄。它們是事實，沒有玩家的
  意圖。
- **目標**回答「我想要什麼、還缺什麼、哪天湊得齊」：只有「目標規劃」分區。裡面每一筆都是玩家
  自己宣告的終點（某艘艦改到某個形態、某種資材存到某個量），分區替它算需求、缺口與到達日。
  沒有玩家宣告就沒有內容；它不放紀錄，也不主動建議該設什麼目標。
- **提醒與建議**回答「現在該做什麼」：閒置檢查、出擊前差異檢查、遠征組合建議，放在
  玩家做那件事的地方（面板、任務導覽、遠征紀錄）。

分區名稱維持「目標規劃」，不叫「改造目標」：備蓄目標與到達日之後也放在這個分區，現在用較窄的
名稱日後還得再改一次，而分區 id、文案鍵與使用者的書籤都跟著名稱走。

分帳與目標規劃的關係是供應：分帳算出的淨流量是目標規劃推算到達日的輸入，但分帳的畫面留在
資源紀錄。§1 的「目標 → 需求 → 庫存 → 流量 → 到達日」是整份計畫的資料模型，不是某一個分區的
範圍。

**開工方式**：一個 session 做一格。開新 session、選表中建議的模型，說「做補完計畫順序 N 的第 K
個 session」，agent 會從 `AGENTS.md` 的索引讀到本檔的對應小節。開工前本檔與已完成的項目必須
已經 commit，否則在獨立 worktree 開的 session 看不到。

目標倒推的第一階段（改造目標）只用遊戲 master 與目前庫存，不依賴任何分帳，而且是全計畫設計量
最大的一項，所以排最前、用最強的模型做；第二階段（到達日）要等分帳完成才有流量可用。
登出前閒置檢查、出擊前差異檢查、改修日程互不依賴，可以穿插在大項之間做。出擊帳單是
基本資源分帳與到達日推算的單價來源，也是規模最大的實作項，宜早開工。

每項「建議模型」以 2026-11 可用的 Claude 模型為準（Fable 5.2、Opus 5.5、Sonnet 5.5、
Haiku 5.5），是擬定者的判斷，不是量測結果。通則：

- **動到資料模型的 session**（`utils/state.ts`、`event-projector.ts`、`db.ts`、備份格式）：
  用最強的模型、高 effort，先進 plan mode 列出所有會碰到的地方再動手。錯一次的代價是使用者
  資料。
- **純函式加 Vitest 的 session**：Sonnet 5.5、中～高 effort 足夠，前提是規格（本檔該項的
  「資料依據」）已經寫死。
- **介面與三語文案的 session**：Opus 5.5 或 Fable 5.2、中 effort。版面判斷與三語排版需要
  品味，但邏輯輕；先出 `.preview/` 預覽給開發者看再定案。
- **資料轉寫**（經驗表、獎勵解析、改修表）：寫產生器腳本從原始資料轉，不讓模型手抄數字；
  腳本本身用 Sonnet 5.5 即可，產出物加測試比對抽樣值。
- **每項拆成二到三個 session**，順序固定為「純函式＋測試 → 投影與資料表 → 介面與預覽」。
  每個 session 結束於開發者在實際介面確認，確認後才 commit。
- **規格已寫死、可獨立驗收的子任務**（文件修訂、離線預覽腳本、三語文案、照既有樣式的介面、
  資料轉寫腳本）由主模型分派給較便宜的模型，主模型負責看 diff 與跑測試驗收；動到資料模型的
  核心設計不分派。

## 4. 各項內容

### 4.2 離散資材分帳（改修資材、開發資材、高速修復材、高速建造材）

**問題**：這四種資材不會自然回復，每一筆進出都對應一個動作，理論上幾乎可以完全對帳；但現在
只看得到餘額曲線。

**資料依據**
- 餘額：`db.resources`（`api_port/port` 與 `api_get_member/material` 的八項快照）。
- 工廠支出：`db.factory` 的 `used[]` 已是八項精確消耗（開發、建造、改修、高速建造）。
  `samples/remodel_1.json`／`remodel_2.json` 的 `api_after_material` 是改修後的八項餘額。
- 任務收入：`db.questObserved`（本機觀測到的領獎）加任務獎勵的解析（已完成：`utils/quest-material-income.ts` 的 `materialQuantity()`，見 `docs/engineering/quests.md`）。
- 遠征收入：`db.expeditions` 的 `items`。
- 入渠用掉的高速修復材：`api_req_nyukyo/start` 的 `api_highspeed=1` 與
  `api_req_nyukyo/speedchange`，`utils/state.ts` 已處理這兩支。

**缺口**
- 遠征回航道具的欄位語意已有外部專案佐證：KC3Kai `src/library/modules/Kcsapi.js` 的
  `api_req_mission/result` 以 `api_useitem_flag[i]` 判種類（1＝高速修復材、2＝高速建造材、
  3＝開發資材、4＝改修資材，其中 4 另須 `api_get_item{i+1}.api_useitem_id` 為 4），數量取
  `api_get_item{i+1}.api_useitem_count`。本專案 `samples/` 仍沒有這支封包的樣本，實作時依
  硬約束 8 在註解寫明專案與檔案路徑；其他 flag 值維持原樣呈現不解讀。
- 艦娘改造消耗的開發資材與高速建造材：KC3Kai 同檔的 `api_req_kaisou/remodeling` 不讀回應的
  餘額，而是用 master 的 `api_afterbull`（彈藥）、`api_afterfuel`（鋼材）加上逐艦例外表推算
  消耗；所以改造的離散資材支出屬「推算」，以改造前後兩筆母港餘額之差校正。
- 勳章交換、禮物箱、活動報酬、海域終端的資材點：先全部落在「未歸因」，有樣本後再逐項拆出。
- 高速修復材的入渠消耗目前只更新狀態、沒有留下紀錄列。

**做法**
1. 純函式：輸入一段期間的餘額列與各來源的事件列，輸出每種資材的
   `期初、各來源收入、各去向支出、未歸因、期末`，恆等式 `期初 + 收入 − 支出 + 未歸因 = 期末`
   必須成立並有測試。
2. 先只用現有表做（工廠、任務、遠征、餘額），看「未歸因」佔多少；佔比高的來源才值得補資料。
3. 介面放在資源紀錄分區，期間選擇沿用既有控制項。「未歸因」固定顯示，不隱藏、不改名。

**範圍外**：四種基本資源（留給 4.5）；任何對未歸因來源的猜測。

**驗證**：用開發者一段真實備份跑恆等式；`tests/` 加入手造的期間案例。

**建議**：兩個 session。第一個（純函式＋測試）Sonnet 5.5 高 effort；若第 2 步發現必須新增
紀錄列（入渠用桶、改造），那個 session 改用 Fable 5.2 或 Opus 5.5 高 effort 並先進 plan mode，
因為會動到投影與備份格式。

### 4.3 出擊帳單（每次嘗試的成本）

**問題**：戰鬥紀錄與資源紀錄是分開的兩半。玩家要的是它們的接點：這張圖每趟花多少、每次到王
花多少、每個 S 勝花多少、掉一艘指定的船平均花多少、目前庫存還夠幾趟。

**關鍵觀察**：帳單不必用估算。回港那一刻的母港封包已經包含這趟出擊留下的全部「待付帳」：

| 成本項 | 取得方式 | 性質 |
|---|---|---|
| 燃料、彈藥 | 回港時各艦現有量與 master 最大量之差 | 封包事實＋結婚艦折扣規則 |
| 艦載機補充 | 各格現有搭載數與最大搭載數之差 × 鋁土 5 | 封包事實＋wiki 規則 |
| 修理 | 各艦的 `api_ndock_item`（燃料、鋼材） | 封包事實 |
| 高速修復材 | 之後對這些艦送出的高速入渠 | 封包事實，需歸屬到出擊 |
| 基地航空隊補充 | `api_req_air_corps/supply` 回應的餘額差 | 封包事實 |
| 基地航空隊出擊 | 出擊前後兩筆母港餘額之差扣掉其他各項；單獨估算時依機種與機數的公式 | 推算 |
| 支援艦隊 | 支援艦隊回港後的同一算法 | 封包事實 |
| 途中取得的資源 | 出擊前後兩筆母港餘額之差扣掉以上各項 | 推算 |

因為取的是回港實數，「活動特殊燃彈費率未驗證」這個既有缺口不影響帳單，只影響途中估算。

**資料依據**
- `api_ndock_item`：`samples/slot_to_port.json`、`samples/slot-exchange-index.json` 的艦船物件
  都帶這個欄位；KC3Kai `src/library/objects/Ship.js` 以
  `repair = [api_ndock_time].concat(api_ndock_item)` 讀取，並在
  `src/library/modules/Kcsapi.js` 的 `api_req_nyukyo/start` 以 `repair[1]`、`repair[2]` 扣燃料
  與鋼材。專案目前只用 `api_ndock_time`。
- 補給回應：KC3Kai `Kcsapi.js` 的 `api_req_hokyu/charge` 讀 `api_ship[].api_fuel／api_bull／
  api_onslot` 與 `api_material`；專案 `onReqHokyuCharge` 讀的是同一組欄位。補給前後的
  `api_material` 之差是精確的補給花費，可用來校正上表前兩列。
- 艦載機每架鋁土 5：wikiwiki「補給」頁。
- 基地航空隊補給：`samples/air-corps-supply.json`（`api_after_fuel`、`api_after_bauxite`）。
- 出擊的分組鍵：`SortieLogRow.sortieKey`（`api_req_map/start` 的事件 id）。

**缺口**
- `api_req_hokyu/charge` 與 `api_req_nyukyo/start` 沒有本專案樣本，欄位依 KC3Kai `Kcsapi.js`
  佐證即可實作。補給：`api_ship[].api_fuel／api_bull／api_onslot` 與四項 `api_material`；
  入渠：請求的 `api_ship_id`、`api_highspeed`、`api_ndock_id`，花費取該艦的
  `api_ndock_item`，`api_highspeed=1` 另扣一個高速修復材，`api_ndock_time` 不超過 60 秒時不佔
  槽。結婚艦折扣的進位仍以補給前後的 `api_material` 之差為準，不靠公式。
- 基地航空隊「出擊」本身的燃彈消耗沒有任何封包帶這筆數字。KC3Kai 在 `api_req_map/start`
  當下，對該海域行動為「出擊」的基地，依 `src/library/objects/LandBase.js` 的
  `calcSortieCost`（各中隊 `api_count` × 依機種而定的每機燃料／彈藥係數，噴射機另計鋼材）
  自行扣除，並註明準確度取決於係數。帳單以母港餘額差為準，公式只用來把差額拆給基地航空隊，
  標「推算」。
- 玩家回港後不修就再出擊、或跨多趟才一次入渠時，修理費要歸給造成損傷的那一趟：以回港當下
  的 `api_ndock_item` 與上一次回港的值相減，而不是等入渠請求。
- 帳單要存成新的 derived 資料（每個 `sortieKey` 一筆），需要升 DB 版本、備份格式相容處理，並
  更新 `docs/structure.html` 的版本錨點。

- `billShipFromApi(raw)`：`api_ship[]` 的原始物件轉成計算用的形狀，已用
  `samples/slot_to_port.json` 核對。
- `netCost()`、`summarizeBills()`、`affordableRuns()`：一趟的淨成本、同一張圖的彙總（每趟、
  每次到 Boss、每個 Boss S 勝）、以目前庫存可再出擊的趟數。

這一步定下的設計，後續 session 不要改：

- **帳單是兩個時刻的差，不是途中估算的累加。** 帶傷或未補滿出擊時，舊傷與舊缺額不算到這一趟。
- **結婚艦的補給花費標推算。** 遊戲對補給當下的總缺額打 85 折再捨去，一趟的差額各自取整只是
  近似。
- **出擊期間的餘額變動是合計，不再拆。** 它等於途中取得的資源減掉基地航空隊出擊消耗與噴射機
  鋼材；封包無從區分，所以不套公式硬拆。
- **高速修復材不存進帳單。** 帳單只記這趟新增修理費的艦，之後的高速入渠在讀取時依此歸屬，
  帳單列寫入後不再更動。
- **支援艦隊與基地航空隊補充在帳單上分開標示，不併入出擊艦隊的數字。** 它們在不同的封包
  結算，分開才對得回去（做法見第二個 session 的第 6、7 點）。這兩項還沒做之前，介面要明講
  帳單不含它們。
- **通常海域與活動海域用同一套算法。** 計算只看艦娘狀態，不看海域；活動特殊燃彈費率因此不
  影響帳單。活動才有的進出落在餘額變動裡：緊急泊地修理的鋼材在四項基本資源的合計內；強力
  友軍的高速建造材與終點資材點給的道具在 `specialDelta`（另外四項的餘額變動）。開發者說明
  強力友軍每隊消耗 6 個高速建造材（道中與 Boss 各一隊時共 12 個）；帳單只呈現餘額差，不另外
  推算友軍次數。
- **封包無法再拆的合計維持原樣。** 出擊期間的餘額變動不拆成「基地航空隊出擊」「途中取得」
  等細項；需要細項時另以估值顯示並標推算，不改動合計。

**第二個 session：投影、資料表與備份**（最強的模型、高 effort，先進 plan mode）

1. **出擊前的狀態在 `api_req_map/start` 套用到 state 之後擷取。** 這時艦娘物件還是出擊前的值：
   途中的燃彈估算要到 `battleresult` 才寫回（見 `docs/engineering/battle.md`），所以不能等到
   回港才回頭讀。參與的艦＝出擊艦隊；聯合艦隊且由第一艦隊出擊時加上第二艦隊（同
   `utils/state.ts` 的 `markFleetAway` 判斷）。擷取位置比照 `EventProjector.captureReplay()`。
2. **出擊後的第一筆 `api_port/port` 套用後結算**，用 `billShipFromApi()` 讀 `state.ships`。沒有
   出擊前的狀態（缺出擊開始事件）就不寫；「不記錄的海域」也不寫。出擊前的狀態要跟
   `currentReplay` 一樣活過重播模式，跨 cursor 的出擊才接得上。
3. **餘額變動的前一筆只在可信時才傳。** `state.materials` 只追蹤部分封包（母港、補給、工廠的
   餘額欄位、基地航空隊補充），入渠、改造、解體、廢棄、任務領獎、道具使用都不會更新它。規則：
   上一筆 `api_port/port` 之後到 `api_req_map/start` 之間，只要出現任何「會動到四項基本資源、
   而 state 沒有追蹤」的封包，就傳 `null`。清單要對照 `utils/state.ts` 逐一列出並加測試，
   寧可多判成不可考。後一筆是回港的母港封包，必定完整。
4. **新資料表 `sortieBills`**，主鍵 `sortieKey`（同 `db.replays`），`put` 冪等；列＝
   `{ sortieKey, ts, map, difficulty? }` 加上 `SortieBill` 的欄位。活動海域要存出擊當下的難度
   （`state.mapGauges` 的 `selectedRank`，同 `setDifficulty()` 的來源）：`db.sorties` 沒有難度，
   `db.replays` 會被保留規則裁剪，不存就無法把甲乙丙丁分開彙總。通常海域不寫這一欄。需要升 DB 版本與備份格式版本（比照
   `tests/backup-v9-goals.test.ts` 的四類測試：版本協商、欄位驗證、往返、升級不動既有資料），
   並更新 `docs/structure.html` 的版本錨點、`docs/engineering/capture.md` 的資料表清單。
5. 帳單不參照來源 event id 以外的東西；`sortieKey` 是 event id，要進
   `highestReferencedEventId()`。
6. **支援艦隊**：出擊開始時正在支援遠征的艦隊，用同一支 `sortieBill()` 各算一份，存成帳單列
   的 `support: { deckId, payable, estimated }[]`，介面另列一行。動手前先查證支援艦隊何時
   回港、同一次支援遠征會不會跨多趟出擊（wikiwiki「支援艦隊」）；若會跨趟，花費只能歸給
   回港前的最後一趟或標不可考，不可重複計入。哪一隊在支援看 `api_req_mission/start` 的遠征
   種類與戰鬥封包的 `api_support_info`，沒有證據就不寫這一欄。
7. **基地航空隊補充**：機數在回港的母港封包裡不會更新，所以不能跟艦隊一樣在回港時結算。以
   `api_req_air_corps/supply` 回應的 `api_after_fuel`、`api_after_bauxite` 與補充前的餘額相減
   得到實際花費（封包事實，樣本 `samples/air-corps-supply.json`），留成支出紀錄列，讀取時歸給
   同一海域在它之前最近的一趟出擊，介面另列一行。這與高速修復材是同一種「回港後才付、讀取時
   歸屬」的支出，紀錄列跟 4.2 的入渠用桶一起設計。

第 6、7 點不需要最強的模型：規格已定，可交給 Opus 5.5 連同這個 session 一起做，或另開一個
session，由主模型看 diff 與測試驗收。

**第三個 session：介面與預覽**（可分派給較便宜的模型，主模型驗收）

1. 出擊紀錄的卡片顯示該趟帳單；推算與不可考照 §2 分開標示。
2. 海域彙總用 `summarizeBills()`：到達 Boss 與 Boss 的 rank 取自 `db.sorties` 同一個
   `sortieKey` 的列。活動海域依難度分開彙總，不同難度的成本不可平均在一起；同一難度內
   削血與斬殺階段的成本也不同，至少要能依期間篩選。再用 `affordableRuns()` 顯示以目前庫存可再出擊的趟數。
3. 高速修復材的歸屬要等 4.2 留下入渠用桶的紀錄列之後才做。
4. 打撈紀錄不另做掉落率功能；「平均花多少資源掉一艘」放在同一個海域彙總。

**範圍外**：預測下一趟的成本（那是途中估算的工作）；時間成本的金額化。

**驗證**：正式 build、型別檢查、相關 Vitest；開發者實機打一趟後，比對帳單「要付的帳」與實際
補給、入渠前後的資材差。

### 4.4 登出前閒置檢查

**問題**：面板會告訴玩家每件事何時結束，但不會指出「現在有產能空著」。

**檢查項**（全部來自既有 `GameState`，不需新封包）
- 有待修艦，且有空的入渠槽（`ndockData` 與待修清單，面板「入渠」分組已有這兩份資料）。
- 第二到第四艦隊沒有出遠征，也不在出擊或支援中。
- 艦隊未補給、基地航空隊機數未補滿（面板已有紅框提醒，這裡只是彙整）。
- 演習距離下次更新（03:00、15:00 JST）不到設定的時間，且今日尚有次數。
- 任務重置（05:00 JST）前，已接任務中進度已達成但未領獎的項目。

**缺口**
- 演習剩餘次數與對手清單沒有樣本（`samples/` 只有演習結果）。這一條在開發者提供
  `api_get_member/practice` 的樣本之前不做。
- 「已達成未領獎」取決於任務狀態欄位，動手前先確認 `quest-progress.ts` 已有的判定夠不夠用。

**做法**：純函式回傳一個有序清單（每項含原因與所指的艦隊或槽位），面板母港檢視放一個折疊的
摘要列，沒有項目時不佔空間。只提醒，不排程、不通知；面板編成高度的硬上限照
design-guidelines §7.1。

**範圍外**：建議入渠順序；任何自動操作。

**建議**：兩個 session。純函式用 Sonnet 5.5 中 effort；面板版面用 Opus 5.5 或 Fable 5.2
中 effort，先給預覽。

### 4.5 基本資源分帳與溢出

**問題**：燃彈鋼鋁的淨收入是多少；哪些收入因為撞到上限而白流。

**資料依據**
- 自然回復：每 3 分鐘燃彈鋼 +3、鋁土 +1，到司令部等級決定的自然回復上限為止；基地航空隊設為
  休息時鋁土回復速度減半（wikiwiki「資材」頁）。
- 上限：基本資源 350,000、高速修復材 3,000（同頁，2020-11-13 起）。
- 支出：4.3 的出擊帳單、`db.factory`；收入：`db.expeditions` 的 `resources`（精確）、任務獎勵
  的結構化資源欄位。

**缺口**
- 自然回復上限與司令部等級的對應式要從 wikiwiki 表格轉寫並加測試；自然回復量本身是推算，
  因為兩筆餘額之間玩家可能不在線上。
- 上限為基本資源 350,000、高速修復材等 3,000，開發者已確認。持有量可以超過上限：依開發者的
  判斷，任務獎勵會照發而突破上限（同理，任務取得艦娘也會超過船位上限）。所以「超過上限」是
  合法狀態，溢出提醒不得把它當成資料錯誤。
- 近代化改修、解體、廢棄的資源進出目前沒有紀錄列。

**做法**：沿用 4.2 的恆等式函式，加入自然回復這個推算來源與「未歸因」。溢出提醒分兩種：
已達硬上限仍有收入的資源，以及超過自然回復上限因而不再自然回復的資源；兩者都只在資源紀錄
分區與 4.4 的摘要列呈現一次。

**建議**：兩個 session。Sonnet 5.5 高 effort 做函式與測試；介面沿用 4.2。這項不該新增資料
表，若發現需要，停下來重新評估範圍。

### 4.6 目標倒推（目標 → 需求 → 庫存 → 流量 → 到達日）

**問題**：玩家腦中有目標（把某艦改到某個形態、活動前存到某個量），但要自己查需求、自己算
缺口、自己估時間。

**第一階段（改造目標）已實作，待開發者在實際介面驗證**；現行行為見
`docs/engineering/goals.md`，驗證後把本段刪除。尚未做的是下列各階段。

**第一階段留下的缺口**
- 目標只能從「目標規劃」分區自己的候選清單加入，艦娘全覽還沒有入口。
- 推算類消耗（開發資材、高速建造材、新型砲熕兵裝資材、改修資材、工廠資源）取自外部參照表，
  新艦實裝後要重跑 `tools/remodel-cost/generate.py` 才會更新。

**後續階段的資料依據**
- 流量：4.2 與 4.5 的分帳結果。
- 改造當下的實際消耗：4.2 所述的改造前後餘額差，可用來校正推算類消耗。

**做法**
1. 第二階段接上流量：對每個缺口，以最近一段期間觀測到的淨流量推到達日，顯示為區間；觀測
   期間不足時顯示不可考。流量取自玩家自己的紀錄，不套用任何「標準玩家」的假設。
2. 第三階段加入備蓄目標（指定資材與目標量），與改造目標共用同一套庫存分配。
3. 從艦娘全覽加入目標的入口可以獨立做。

**範圍外**：推薦該改造誰；練等地點建議；改修目標（改修只做 4.7 的日程，不算消耗）。

**建議**：第二階段要等 4.2、4.5，計算部分用最強的模型；艦娘全覽的入口是照既有樣式的介面，
可分派給較便宜的模型。備蓄目標沿用 `db.goals`（主鍵已帶種類前綴），加新種類時要同步放寬
備份驗證並升備份格式版本。

### 4.7 改修日程

**問題**：玩家想在本工具直接看到今天能改修什麼、要用哪艘二番艦，並保留自己用過的配方。

**範圍界線與理由**：完整的改修資料量大且隨營運更新，社群網站的更新速度本專案追不上；面板
既有的「明石改修工廠一覽」外部連結就是為此而設，維持不變。本項不做消耗表、不做全裝備改修
百科、不接到目標倒推的缺口計算。

**資料依據**
- 星期與二番艦：KC3Kai `src/data/akashi.json`（MIT；星期 → 裝備 id → 二番艦 master id
  清單），以產生器腳本轉成本專案的資料模組。
- 玩家用過的配方：既有的工廠紀錄 `db.factory`（`kind: 'improve'`，含裝備、改修前後等級、
  成敗、是否確實化、當時的秘書艦）。

**缺口**
- `akashi.json` 的更新取決於上游，表內沒有的新裝備顯示為「尚未收錄」，並保留外部連結。
- `db.factory` 的 `secretary` 是第一艦隊旗艦（明石），二番艦目前沒有記錄；要不要補記是實作時
  的決定，補記會動到工廠紀錄的資料列。

**做法**：依今天的星期（JST）與玩家持有的裝備、艦娘，列出「今天可改修且持有二番艦」的裝備與
可用二番艦；另列玩家自己的改修紀錄彙總（哪個裝備改過幾次、成功率）。放在總括或面板的位置於
實作時先出預覽。

**範圍外**：消耗量、成功率預測、推薦改修什麼。

**建議**：一到兩個 session，Sonnet 5.5 高 effort；資料用產生器腳本轉，不手抄。

### 4.8 出擊前差異檢查

**問題**：既有的防呆守住了大破進擊與出擊札，沒守的是平凡的準備疏失：支援艦隊沒派、基地
航空隊還在待機、裝備沒換回來。

**資料依據**：`db.replays` 在 `api_req_map/start` 保存主隊、隨伴、支援與基地航空隊的快照
（`ReplayRow`）。拿「上一次在同一海域達成目標的那次出擊」當基準，與目前母港狀態比較。

**缺口**
- 「達成目標」的定義：先用「到達王點且 S 勝」；玩家可改指定任一筆出擊當基準。
- 重播會被保留規則裁剪，基準不存在時顯示沒有可比對的紀錄，不退而用別張圖。
- 檢查只能在母港做（玩家選好海域之前，工具不知道要打哪張圖），所以由玩家在面板選定基準
  後才顯示差異。

**做法**：純函式比較兩份編成快照，輸出差異清單（艦、裝備、支援有無、基地航空隊的行動與
配置）；面板在母港檢視提供「對照上次成功的編成」入口。只列差異，不判斷對錯。

**範圍外**：編成建議；航路預測（常規導航已有）。

**建議**：兩個 session。差異函式 Sonnet 5.5 高 effort；面板入口與版面 Opus 5.5 或
Fable 5.2 中 effort，先給預覽。

### 4.9 遠征組合建議

**問題**：三隊遠征是資深玩家唯一的經常性收入，但組合取決於玩家的作息與缺口。

**資料依據**：`utils/expedition-data.ts`（需求與報酬）、`expedition-bonus.ts`（大發加成）、
`db.expeditions`（玩家自己的成功與大成功紀錄）、4.5 的溢出結果。

**缺口**：回航道具欄位語意已有外部專案佐證，但本專案沒有樣本（同 4.2），所以離散資材的遠征
收益只能用玩家自己的歷史平均，樣本不足時標不可考。

**做法**：玩家輸入這次會離開多久與關注的資材，工具從已開放的遠征裡排出三隊組合，並排除
會流進已滿資源的選項。只給排序與理由，不檢查玩家有沒有編得出來的艦隊。

**建議**：兩個 session，Sonnet 5.5 高 effort。放在最後，因為它的價值要靠 4.5 才完整。

## 5. 不排入本計畫的項目

| 項目 | 理由 |
|---|---|
| 夜戰 CI 率、對空 CI 預估 | 只增加資訊，不改變出擊當下的決策；公式（wikiwiki「夜戦」）已查證，日後要做不缺資料 |
| 戰果估算 | 只對衝排名的玩家有用；公式（wikiwiki「称号・戦果」）已查證 |
| 演習經驗預估 | 價值低；對手清單封包沒有樣本 |
| 緊急泊地修理 | 找不到可信的規則出處，也沒有樣本 |
| 把資料送到外部統計站、雲端 LLM | 違反不上傳與權限精簡 |
| 活動特效偵測 | 要由異常傷害反推，複雜且容易誤報 |
| 改修消耗表與改修百科 | 資料量大且隨營運更新，交給社群網站；面板保留外部連結 |

**封包佐證現況**
