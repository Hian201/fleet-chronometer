# 專案補完計畫

本檔的第 1～7 節是**尚未實作的計畫**，不是現行行為。某一項做完並經開發者驗證後：
1. 把它的現行事實寫進 `docs/engineering/` 對應主題檔。
2. 在第 8 節「已完成項目」登記完成日期、commit 與現行行為所在。
3. 從第 3 節總覽表與第 4 節刪掉該項的列與小節本文（順序編號與小節編號都不重排，缺號就是已完成）。

內容與程式碼不一致時以程式碼為準。外部資料的查證基準日是 2026-11-11。

## 1. 排序的依據：對這款遊戲的理解

艦これ把「現實時間」換成「有限次數的賭注」。資源是用來買嘗試次數的；期限、亂數與不可逆的
損失把它變成後勤問題。由此推出四個判斷，本計畫的每一項都對應其中之一：

1. **貨幣是時間與注意力。** 基本資源每 3 分鐘自然回復（燃彈鋼 +3、鋁土 +1），到司令部等級
   決定的上限就停；之後的收入來自「艦隊數 × 玩家不在的時間」。玩家每次登入是在安排離開後會
   發生什麼。
2. **限制玩家的是最短的那塊板，而且每個人不同。** 基本資源上限 350,000、高速修復材 3,000；
   資深玩家常卡在改修資材、開發資材、設計圖等離散資材，新玩家卡在燃彈。流進已滿資源的收入
   是浪費。
3. **資源的單位是「一次嘗試」。** 通關成本＝期望嘗試次數 × 每次成本（補給、修理、修復材、
   艦載機補充、時間）。
4. **勝負在按下出擊前就決定，而錯誤不可逆。** 進戰鬥後只剩陣形、夜戰、進退三個決定。

收斂成一個模型：**目標 → 需求 → 庫存 → 流量 → 到達日**。改造、改修、備蓄是它的三種目標；
第 3 點的「每次成本」是它的單價。

功能的取捨判準是「是否減少一個決策或防止一個錯誤」。只增加資訊、不改變決策的功能排在最後。

## 2. 跨項目原則

- **不預設玩家的瓶頸，也不預設課金行為。** 專案是公開的：改修資材、開發資材等可以在官方
  道具屋購買，每位玩家的取得管道不同。因此關注哪種資材、目標是什麼，一律由玩家自己指定；
  工具只呈現觀測到的流量。帳上對不到來源的增減一律歸「未歸因」，不標成購買，不出現購買建議，
  也不把「不購買」當成計算前提。
- **三種數字分開呈現。** 封包事實（精確）、公式推算（標「推算」）、算不出來（標「不可考」，
  不以 0 頂替）。同一張表混用時逐格標示。
- **歷史不回填。** 新的帳從該功能上線那一刻開始累積，空狀態直說原因（同資源紀錄的既有做法）。
- **硬約束照舊。** 尤其是被動觀察、不上傳、不加權限、未驗證欄位不猜（`AGENTS.md` 硬約束 1、
  2、7、8），以及 derived tables 只經 `EventProjector` 寫入（硬約束 5）。
- **`db.wanted` 的鉤子不得擴充。** 本計畫需要的新樣本由開發者從既有除錯介面或 DevTools 手動
  提供，不靠新增擷取鉤子。

**三種畫面各有歸屬，不混在同一個分區**：

- **紀錄**回答「發生了什麼」：分帳放在資源紀錄、出擊帳單放在出擊紀錄。它們是事實，沒有玩家的
  意圖。
- **目標**回答「我想要什麼、還缺什麼、哪天湊得齊」：只有「目標規劃」分區。裡面每一筆都是玩家
  自己宣告的終點（某艘艦改到某個形態、某種資材存到某個量），分區替它算需求、缺口與到達日。
  沒有玩家宣告就沒有內容；它不放紀錄，也不主動建議該設什麼目標。
- **提醒與建議**回答「現在該做什麼」：閒置檢查、出擊前差異檢查、遠征組合建議，放在
  玩家做那件事的地方（面板、任務導覽、遠征紀錄）。

分區名稱維持「目標規劃」，不叫「改造目標」：備蓄目標與到達日之後也放在這個分區，現在用較窄的
名稱日後還得再改一次，而分區 id、文案鍵與使用者的書籤都跟著名稱走。

分帳與目標規劃的關係是供應：分帳算出的淨流量是目標規劃推算到達日的輸入，但分帳的畫面留在
資源紀錄。§1 的「目標 → 需求 → 庫存 → 流量 → 到達日」是整份計畫的資料模型，不是某一個分區的
範圍。

**開工方式**：一個 session 做一格。開新 session、選表中建議的模型，說「做補完計畫順序 N 的第 K
個 session」，agent 會從 `AGENTS.md` 的索引讀到本檔的對應小節。開工前本檔與已完成的項目必須
已經 commit，否則在獨立 worktree 開的 session 看不到。

出擊前差異檢查不依賴其他項，可以穿插在大項之間做。

每項「建議模型」以 2026-11 可用的 Claude 模型為準（Fable 5.2、Opus 5.5、Sonnet 5.5、
Haiku 5.5），是擬定者的判斷，不是量測結果。通則：

- **動到資料模型的 session**（`utils/state.ts`、`event-projector.ts`、`db.ts`、備份格式）：
  用最強的模型、高 effort，先進 plan mode 列出所有會碰到的地方再動手。錯一次的代價是使用者
  資料。
- **純函式加 Vitest 的 session**：Sonnet 5.5、中～高 effort 足夠，前提是規格（本檔該項的
  「資料依據」）已經寫死。
- **介面與三語文案的 session**：Opus 5.5 或 Fable 5.2、中 effort。版面判斷與三語排版需要
  品味，但邏輯輕；先出 `.preview/` 預覽給開發者看再定案。
- **資料轉寫**（經驗表、獎勵解析、改修表）：寫產生器腳本從原始資料轉，不讓模型手抄數字；
  腳本本身用 Sonnet 5.5 即可，產出物加測試比對抽樣值。
- **每項拆成二到三個 session**，順序固定為「純函式＋測試 → 投影與資料表 → 介面與預覽」。
  每個 session 結束於可 commit 的狀態；commit 的條件見 `AGENTS.md`「工作方式」。
- **規格已寫死、可獨立驗收的子任務**（文件修訂、離線預覽腳本、三語文案、照既有樣式的介面、
  資料轉寫腳本）由主模型分派給較便宜的模型，主模型負責看 diff 與跑測試驗收；動到資料模型的
  核心設計不分派。

## 4. 各項內容

### 4.8 出擊前差異檢查

**問題**：既有的防呆守住了大破進擊與出擊札，沒守的是平凡的準備疏失：支援艦隊沒派、基地
航空隊還在待機、裝備沒換回來。

**資料依據**：`db.replays` 在 `api_req_map/start` 保存主隊、隨伴、支援與基地航空隊的快照
（`ReplayRow`）。拿「上一次在同一海域達成目標的那次出擊」當基準，與目前母港狀態比較。

**缺口**
- 「達成目標」的定義：先用「到達王點且 S 勝」；玩家可改指定任一筆出擊當基準。
- 重播會被保留規則裁剪，基準不存在時顯示沒有可比對的紀錄，不退而用別張圖。
- 檢查只能在母港做（玩家選好海域之前，工具不知道要打哪張圖），所以由玩家在面板選定基準
  後才顯示差異。

**做法**：純函式比較兩份編成快照，輸出差異清單（艦、裝備、支援有無、基地航空隊的行動與
配置）；面板在母港檢視提供「對照上次成功的編成」入口。只列差異，不判斷對錯。

**範圍外**：編成建議；航路預測（常規導航已有）。

**建議**：兩個 session。差異函式 Sonnet 5.5 高 effort；面板入口與版面 Opus 5.5 或
Fable 5.2 中 effort，先給預覽。

### 4.11 開場節點字母辨識

**問題**：第 10 項只補得出活動中途開放的節點（追加檔的 `labels`）。開場就有的節點，字母只畫在地圖
的 point 圖層上，新活動開放到本專案下一版上架前，這些節點只能顯示原始 edge 編號（62 活動約四成）。

**資料依據**
- 遊戲以 `PIXI.Texture.fromFrame("map" + 海域關卡 + "_" + 圖層名)` 建立地圖背景，圖層名來自 info 的
  `bg` 陣列，字母所在的是名稱以 `_point` 結尾的那一層（62-1 為 `map06201_map62-1_point`，1200×720）。
  離開地圖時 `UIImageLoader.clearMemoryCache("map")` 清掉。main.js 沒有 `Proxy`、沒有對 PIXI 的
  `defineProperty`／`freeze`，也沒有 `getImageData`／`toDataURL`。依據：開發者 2026-11-26 另存的 main.js
  靜態閱讀（主程式檔不放進專案）。
- point 圖層包含節點圓圈（白）、路線虛線（淺紫）與字母（深色字身加淺色外框），字母在節點右下 45px 內。
  依據：KagamiChan/kcs2-mapdata（MIT）的 62 活動 `_image.png`／`_image.json`；poi `fcd/map-ocr.js` 以同一圖層
  辨識初始節點名。
- 離線實驗（2026-11-27，62-1～62-3，每次把一張圖當新地圖、只用另兩張圖與追加檔 sprite 當字形庫）：
  圖層上的字與追加檔 `labels` 正好互補，合起來涵蓋每關全部節點；字形庫有收錄的名稱 33 個全部讀對、
  0 讀錯，其餘 6 個（C3、A3、E1、E2、D1、D2）不在字形庫而不讀。同名字形跨圖**不是**像素完全相同
  （邊緣抗鋸齒不同），必須容錯比對。實驗參數：
  - 字身遮罩：alpha ≥ 128 且亮度（0.299R＋0.587G＋0.114B）< 110 的像素。
  - 切字：8 連通元件，水平間距 ≤ 8px 且垂直重疊（容許 2px）的元件併成一個字（間距 4px 會把 `A1`
    拆成 `A` 與 `1`）。
  - 指派：字與「沒有標籤字母的終點節點」距離 ≤ 45px 的組合由近到遠，各取一次。
  - 比對：二值遮罩在 ±1px 位移內取最小不吻合率（不吻合像素／聯集像素）；最佳 ≤ 0.15，且比次佳的
    **其他名稱**低至少 0.10 才採用，否則不讀。

**範圍與限制**
- 只補靜態表與第 10 項都沒有的 edge，查表順序不變：人工覆蓋 → KC3Kai 靜態表 → 遊戲內字母 → 原始編號。
  KC3Kai 更新後一律以靜態表為準。
- 字形庫沒有的名稱、或比對不夠明確時不讀，維持原始編號；寧可少補，不可讀錯（硬約束 8）。
- 遊戲改圖層命名或材質不保留原圖時，讀取直接放棄，不影響其他功能。

**做法**
1. **字形庫產生器**（`tools/map-glyphs/`）：一次 `git clone --depth 1` 取得 kcs2-mapdata（不逐檔呼叫 API，
   硬約束 11），以 KC3Kai `edges.json` 的名稱監督過去各活動 point 圖層的字，加上追加檔的標籤 sprite，
   輸出 `utils/map-glyph-data.ts`：只存「名稱 → 二值遮罩（位元打包）」，同名多個變體去重保留，**不存原圖**。
   產生器可排除指定海域，供測試做留一驗證。
2. **純函式**（`utils/map-glyph.ts`）：字身遮罩、切字、指派、比對，參數照上方實驗。測試用 62-1～62-3
   萃取出的小型遮罩 fixture（每個缺字節點附近的裁切，總量 < 200 KB，不放原圖），做留一驗證並要求
   0 讀錯。
3. **遊戲頁讀取**（MAIN world，只在被要求時動作）：
   - background 在 `mapLabels` 更新後算出「該關仍缺字母、且靜態表沒有」的終點節點；沒有就到此為止，
     所以常規海域與已補齊的地圖永遠不讀（2026-11-27 核對：37 張常規海域的路線在靜態表全部有字母）。
     平常只會在新活動海域、或極少數新增的常規海域觸發。
   - 同一關、同一組缺字節點最多讀一次（成功、讀不出或放棄都算），記在 `mapLabels`；地圖開放新階段
     （缺字節點改變）才可能再讀。字形庫認不得的名稱不會讓每次出擊都重讀。
   - 需要時經 bridge 對遊戲頁送一個讀取要求（point 圖層的影格名與節點座標）；私有 MessagePort 增加
     bridge → MAIN 這一個方向，只承載這種要求。
   - MAIN 等材質出現（低頻檢查、有逾時），在瀏覽器閒置時一次處理一個節點：從
     `PIXI.utils.TextureCache[影格名]` 取材質，只把節點附近約 100×100 的區域畫到擴充自己的小畫布，
     算出字身遮罩後送出。不修改、不包裝任何遊戲物件，不發請求；材質不存在或底圖不可讀就放棄。
   - background 做比對（不佔遊戲執行緒），結果併入 `mapLabels`（另存一份「圖層辨識」的對照，與標籤
     來源分開），沿用第 10 項的廣播與注入。
4. **驗證模式**（只在開發建置）：可對靜態表已有的常規海域照樣讀取，把結果與靜態表逐一比對並記錄，
   讓開發者不必等活動就能在 live 驗證準確度與效能。正式建置關閉。

**現況（2026-11-27）**：字形庫與比對（第 1 段，`6a8a240`）在 main，未被任何入口使用。遊戲頁讀取與調度（第 2 段）在分支 `wip/point-layer-ocr`（`9f051e7`），完整檢查通過、劇場模式回歸已由開發者確認修正，但圖層讀取尚未 live 驗證；在那之前 main 只觀察 axios，上架版本不含讀取遊戲物件的行為。下次活動切到該分支以正式建置驗證，通過後才合併。合併時一併：硬約束 1 加上唯讀讀取地圖 point 圖層材質的例外（開發者 2026-11-27 已同意，文字見該分支的 AGENTS.md）、更新產品網站 `site/content.ts` 三語的擷取說明與隱私權頁。字形庫只存二值遮罩。

**驗收**
- 自動：留一驗證 0 讀錯；產生器重跑結果穩定；MAIN 端只在收到要求時讀取（測試）。
- 開發者 live（開發建置的驗證模式）：開常規海域地圖，確認辨識結果與靜態表一致；DevTools「網路」
  沒有多出請求；DevTools「效能」錄一次開地圖，確認讀取落在閒置時段、沒有造成掉幀。另請記下
  `pixi.js` 的版本（網路面板的檔名）。

**建議**：兩個 session。字形庫產生器、純函式與 fixture 用 Sonnet 5.5 高 effort；遊戲頁讀取、通道方向、
background 調度與驗證模式用 Opus 5.5 高 effort，先進 plan mode，對照硬約束 1–3、7。

## 5. 不排入本計畫的項目

| 項目 | 理由 |
|---|---|
| 夜戰 CI 率、對空 CI 預估 | 只增加資訊，不改變出擊當下的決策；公式（wikiwiki「夜戦」）已查證，日後要做不缺資料 |
| 演習經驗預估 | 價值低 |
| 緊急泊地修理 | 找不到可信的規則出處，也沒有樣本 |
| 把資料送到外部統計站、雲端 LLM | 違反不上傳與權限精簡 |
| 活動特效偵測 | 要由異常傷害反推，複雜且容易誤報 |
| 改修消耗表與改修百科 | 資料量大且隨營運更新，交給社群網站；面板保留外部連結 |
| 以實際改造紀錄校正改造的推算類消耗 | 不改變決策：推算類消耗已在目標規劃標「推算」，並請玩家以遊戲改造畫面為準 |
