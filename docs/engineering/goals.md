# 目標規劃（`utils/remodel-goals.ts`、`utils/stockpile.ts`＋`sections/goals.ts`）

**分區的範圍**：「目標規劃」只放玩家自己宣告的終點，並替每個終點算需求、缺口與（有流量資料後
的）到達日。目標有兩種：改造（玩家指定「某艘艦改到某個形態」，分區列出還缺的等級、經驗與各項
消耗，並依目標的排列順序分配庫存）與備蓄（見下方「備蓄」）。資材分帳、出擊帳單這類紀錄，以及閒置檢查、遠征
組合這類建議，都不放在這個分區；各自的歸屬與尚未實作的階段見
[`../completion-plan.md`](../completion-plan.md) §3、§4.6。

## 需求的兩種來源，介面必須分開標示

| 項目 | 來源 | 性質 |
|---|---|---|
| 所需等級 | `api_mst_ship.api_afterlv` | 封包事實 |
| 彈藥、鋼材 | `api_mst_ship.api_afterbull`、`api_afterfuel` | 封包事實 |
| 改裝設計圖、試製甲板彈射器、戰鬥詳報、新型航空兵裝資材、新型兵裝資材、海外艦最新技術、新型高溫高壓缶 | `api_mst_shipupgrade` | 封包事實 |
| 開發資材、高速建造材、新型砲熕兵裝資材、改修資材、工廠資源 | `utils/remodel-cost-data.ts` | 推算 |

- **`api_afterfuel` 是鋼材不是燃料**。`samples/start2-master.json` 核對：長門改→長門改二為
  `afterbull` 8800、`afterfuel` 9200，與改造畫面的彈藥 8800、鋼材 9200 一致。
- **`api_mst_shipupgrade` 以「改造前」為鍵**（`GameState.remodelItems`）。同一個改造後形態可有
  多個來源（可逆改裝），而一艘艦只有一個下一段；只收 `api_id` 與該艦 `api_aftershipid` 對得上
  的列。欄位語意以樣本對照 wikiwiki「改造」頁核對，逐欄對照見 `utils/state.ts` 的宣告處。
- **新型高溫高壓缶是裝備**（`api_boiler_count`），庫存以日文原名查裝備持有數，其餘六種查道具
  持有數（id 見 `REMODEL_USEITEM_ID`，名稱沿用 `utils/item-catalog.ts`）。
- **推算類的數量寫死在遊戲 client 裡，master 沒有**。`tools/remodel-cost/generate.py` 從上游的
  逐艦表擷取數值，產出 `utils/remodel-cost-data.ts`；來源與授權見 `THIRD-PARTY-NOTICES.md` §9c。
  表內沒有的艦不代表確定為 0，所以這幾列一律標「推算」。新艦實裝後要重跑產生器。
- **開發資材的通則**（例外表沒列時）：用了設計圖就不耗，少數艦例外
  （`BLUEPRINT_STILL_NEEDS_DEVMAT`）；否則依鋼材量分級——未滿 4500 為 0、未滿 5500 為 10、未滿
  6500 為 15、其餘 20。

## 路徑

`remodelPath()` 沿 `afterShipId` 一段一段走到目標形態，消耗逐段加總，所需等級取各段的最大值。
可逆改裝會互指成環（鈴谷改二 ⇄ 鈴谷航改二、大和改二 ⇄ 大和改二重），繞回走過的形態就停：
`remodelTargets()` 因此讓環上每個形態各出現一次，到不了的目標回傳 `null`，介面顯示「目前的形態
改不到這個目標」而不是猜一條路。

## 經驗

`SHIP_EXP_TOTAL[等級]` 是到達該等級的累計經驗，與 `api_exp[0]` 相減得到差距。表只到 Lv99：
改造所需等級目前最高 98，Lv100 以上牽涉結婚後的累計基準，用不到就不帶；超出範圍時回傳
`null`，介面顯示不可考。

## 庫存分配

`planRemodelGoals()` 依目標陣列的順序逐一分配：排前面的先拿，後面的目標看到的是剩餘量。
不替玩家排優先順序，也不在目標之間平均分配。已達成、艦已不在名冊、到不了的目標不佔庫存。

持有量尚未收到對應封包時是 `null`，該列的「可用」與「缺口」顯示不可考，不以 0 頂替——把不可考
當成 0 會讓每個目標都顯示成缺貨。

## 儲存

目標是玩家的意圖，不是封包衍生資料：存 `db.goals`（schema v15），由分區直接寫入、不經
`EventProjector`，做法同活動作戰板的 `eventPlans`。備蓄只有一列
`{ key: 'stockpile', kind: 'stockpile', until }`（不帶 `order`），直接 put／delete；改造目標的列是
`{ key, kind: 'remodel', order, shipId, targetMst }`：

- `key` 是 `remodel:${shipId}`，一艘艦只有一個改造目標；`shipId` 是艦娘實例 id，同名艦可各自
  設目標。主鍵帶種類前綴，日後新增其他種類的目標不必再開表。
- 順序存在每一列的 `order`。分區每次變更都在同一個 transaction 內把 `remodel:` 前綴的列整批
  換掉，避免逐列寫入中途失敗留下半套順序；寫入失敗時畫面退回原狀並顯示原因。
- 隨完整備份帶走（改造目標自備份格式 v9、備蓄自 v12，見 [backup.md](backup.md)）。新增種類不需升 DB
  版本（只有 `key` 索引）。

`utils/remodel-goals.ts` 不 import Dexie，只提供 `goalsFromRows()`／`goalsToRows()` 兩個純轉換。

## 到達日（`utils/goal-arrival.ts`）

`observeFlow()` 從最後一筆資源取樣往回切整週（最多 4 週），每週的流量是
「期末餘額 − 期初餘額 + 該週改造支出」÷ 實際天數；`goalArrivals()` 以缺口 ÷ 最快一週得最早天數、
÷ 最慢一週得最晚天數。流量只取玩家自己的紀錄，不套用「標準玩家」的假設。

- **用餘額差，不用分帳的收入**：分帳只拆出部分來源，淨增加才含自然回復、出擊與工廠消耗等全部步調；
  分帳的恆等式保證兩者總和一致。
- **改造支出加回**：未來的改造已經是目標的需求，不加回會重複扣。消耗取 `remodelStep()`，開發資材、
  高速建造材、改修資材屬推算。
- **缺口取累計**：排在後面的目標要等前面的也湊齊，缺口是「到這個目標為止的累計需求 − 目前持有」，
  與庫存分配的順序一致。
- **只有資源取樣的八種資材有序列**（改造用得到的是彈藥、鋼材、高速建造材、開發資材、改修資材）。
  道具類與新型高溫高壓缶沒有歷史，
  標 `untracked`；觀測不足一週或持有量不可考標 `no-data`；最快一週也沒有淨增加標 `stalled`；
  這個目標本身的需求超過蓄積上限標 `over-cap`（改造逐艘花掉，累計超過上限不算：前面的做完就扣）。這些項目列在 `blocked`，此時整個目標的到達日只是下界；
  最慢一週沒有淨增加時上界為 `null`。
- 線性外插不模擬自然回復在上限停止，餘額接近自然回復上限時實際會比推算慢。
- 經驗與等級沒有流量序列，不推到達日。

## 備蓄（`utils/stockpile.ts`）

玩家宣告「正在存資源」，分區替八種有資源取樣序列的資材（燃料、彈藥、鋼材、鋁土、高速修復材、
高速建造材、開發資材、改修資材）回答兩件事：哪天到蓄積上限，以及期限當天各有多少。

- **終點固定是蓄積上限，玩家不填數量**。存資源多半是為了活動，用量事前說不準，實際做法是能存多少
  就存多少；上限之後流進來的收入會浪費，所以「哪天到上限」是該花掉或換遠征的訊號。上限同
  `utils/resource-cap.ts`（基本資源 350,000，其餘 3,000）。
- **期限選填**（`<input type="date">` 的本地日期，從當天 0 時起算），通常是活動開始日。有期限才有
  「期限時」欄；照最快一週的步調會在期限前到上限的資材加粗，並在表上列出（「最快會」，因為慢的週
  可能來不及）。持有量到上限是合法狀態，只加粗不用警示色，同資源紀錄的溢出提醒。
- **不參與改造目標的排序分配**。上限等於「全部」，排進順序會把後面的目標吃光；改成先扣掉所有進行中
  改造目標的需求（`planRemodelGoals()` 的合計，視為已花掉），剩下的才是備蓄。期限時的量夾在 0 與
  上限之間：保留比持有多時缺口已在改造卡片列出，這裡不顯示負數。
- 不替玩家判斷哪一項是瓶頸，八種全列（`docs/completion-plan.md` §2「不預設玩家的瓶頸」）。
- 流量沿用到達日的逐週淨增加；同樣不模擬自然回復在自然回復上限停止，表下說明這個限制。
- 卡片放在改造目標之上；外殼（期限輸入、移除鈕）只在出現時建一次，之後只換表格，期限輸入框才
  不會被即時封包的重繪打斷。

**介面**：分區進入時讀最後一筆取樣往回 4 週的 `db.resources`（加上邊界前最後一筆）與 `db.materialUse`，
讀不到只讓湊齊日顯示不可考，不擋住目標。每張卡在等級列下寫資材湊齊日，消耗表多一欄「預計天數」
（每項都夠時整欄省略）。卡片文字的規則：有 `stalled`／`over-cap` 寫「照目前步調湊不齊」；全部可推算
且上界都看得到才寫「預計 A–B」；否則只寫「最快 A」。天數無條件進位，起點是每次重繪的當下。

## 艦娘全覽的入口

艦娘全覽（`entrypoints/overview/sections/ships.ts`）有「目標」欄，緊接在 Lv 之後、預設顯示，
可在欄位選單關閉。欄位偏好會記下存檔當下的全部欄位（`known`），之後新增的預設開啟欄位對既有偏好
照預設顯示，玩家自己關掉的欄位維持關閉（`mergeSavedColumns()`）。

- 該艦已有改造目標：顯示「已設」連結；沒有目標但 `remodelTargets()` 非空：顯示「＋」連結；
  不能再改造的艦留空。目標清單進入分區時讀一次 `db.goals`，讀不到視為沒有目標，不擋名冊。
  CSV 只在已設目標時輸出「已設」。
- 連結是 `#/goals?ship=<艦娘 id>`。目標規劃分區進入時讀這個參數：該艦已有目標就捲到它的卡片並
  短暫加上外框；否則展開「新增目標」、捲到該艦的候選列並聚焦目標下拉，玩家再自行按「加入」。
  不能改造或已不在名冊時不做事。參數用完即從網址移除。分區不會因入口自動新增目標。
