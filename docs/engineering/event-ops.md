# 活動作戰板：關卡與出擊標籤（`utils/event-plan.ts`、`utils/tag-board.ts`＋`sections/tag-board.ts`）

**機制前提（使用者提供，決定整個資料模型的形狀，別照紙本表格照抄）**：

1. **標籤是船身上的屬性，不是編成的容器**。一艘船同時只能有一個標籤，貼上不可逆。
2. **貼標時機是出擊，由「關卡＋路線」決定**——提督事前怎麼安排都會被蓋掉，
   **只能以出擊實際貼上的為最終標準**。故 `api_sally_area` 是唯一權威，計畫只是意圖標註。
3. **關卡按標籤限制路線**：特定標籤組合才能走特定路線（`allowedTags`）。
4. **帶無標籤船出擊，該船會被貼上「該關卡會給的標籤」**（`grantsTag`）——與 `allowedTags`
   是**兩件不同的事**：某圖可能允許 A 標籤的船進入，但無標籤船走某路線會被貼上 B 標籤。
5. **標籤 id 全活動唯一、只增不減**；後段沿用前段的船時標籤 id 繼續沿用 → 一次活動一份計畫
   （`db.eventPlans` 主鍵 `areaId`），前後段不分檔。

**三層結構**：Layer 1 實際標籤（從 `api_sally_area` 即時讀取，**零輸入且權威**；使用者只需替標籤
取名）→ Layer 2 計畫（手輸：標籤名與欄色、路線規則 `allowedTags`／`grantsTag`、每艘船的計畫
標籤 `planByShip`）→ Layer 3 檢查（純函式）。使用者紙本表格裡「編成」那一欄其實就是標籤的
成員名單：已貼標的船會自己出現在對應標籤欄，不需重抄。

**歷史標籤快照**：選定活動仍存在於目前 master、且目前名冊有非零 `api_sally_area` 時，overview 載入會
以變更過的非零名冊更新 `EventPlanRow.sallySnapshot`；即時名冊無有效標籤時不覆寫。顯示一律優先使用
即時 `api_sally_area`。master 尚未載入才回退快照。master 已載入但該 area 已不在海域清單＝本次活動
結束：刪除該筆 `eventPlans`，不讀快照、不沿用標籤分類。快照只保存艦實例 id→標籤 id。

**計畫以 `EventPlanRow.planByShip`（艦實例 id → 計畫標籤 id）為唯一分配真相**：一艘船在計畫裡
同時只能歸一個標籤，與機制前提 1 同形，所以「同一艘無標籤艦被排進兩個會貼不同標籤的關卡」在
結構上就不會發生，不需要另做矛盾偵測。`PlanStage` 只表達路線規則（`allowedTags`／`grantsTag`）；
`PlanStage.slots` 是舊編成格，介面不再寫入。`planByShip` 為空、且 `slots` 仍有艦時，載入會以
`migrateSlotsToPlanByShip()` 遷移一次：依關卡順序先到先得；同艦被不同 `grantsTag` 指派的後續
格列入 `dropped`、`grantsTag` 未填的格列入 `skipped`，兩者都不寫入計畫，並在板上方顯示遷移筆數。
`slots` 本身不刪，舊資料仍隨備份保留。

**出擊檢查（`checkRoute()`）**：工具列「出擊檢查」開啟後選路線（含階段）與第 1～4 艦隊，讀遊戲
目前的艦隊編成逐艦判定，以實際標籤為準：`ok`＝已持有該路線允許的標籤；`blocked`＝持有別的標籤，
**這隊走不了這條路線**；無標籤艦若計畫標籤不在 `allowedTags` 且不等於 `grantsTag`，也判
`blocked`——它出擊後會被貼上不符計畫的標籤；其餘無標籤艦是 `willStamp`：**不是「安全可調度」
而是「即將被不可逆消耗」**，出擊後就會被貼上 `grantsTag`。結果列在板上方，`allowedTags` 不含的
標籤欄同時變暗。`allowedTags` 未填時整條路線回 `unknown`，**不可判紅**——使用者還沒填就滿江紅
會讓整張表失去訊號價值。

**已驗證**：`api_sally_area` 欄位名與位置已用真封包確認（`samples/slot_to_port.json`，
每艘 `api_ship` 末三欄為 `api_locked`／`api_locked_equip`／`api_sally_area`）；純函式由
`tests/event-plan.test.ts` 與 `tests/tag-board.test.ts` 把關。
`api_port/port` 的 reducer 本來就 `ships.clear()` 後全量重建，**故 Layer 1 零攔截改動、
零新權限**；標籤只能經出擊取得而出擊必以回港收尾，port 必發 → 自我修復，不需監聽 ship2/ship3。

**未驗證（別當成已知）**：標籤 id 的實際語意（所有樣本取自非活動期，值全為 0）；
**標籤名是否存在於任何封包**——start2 的 master 表清單沒有標籤表，上次活動的出擊紀錄
（`samples/61-5-jibun-rengou-node52.json`）遞迴掃過 189 個 key 零命中，但該檔只含戰鬥封包、
不含母港類封包，**答不了這題**。第三方工具（KC3Kai／poi）都手維護標籤名表，方向一致。
故 `PlanTag.nameSource` 的 `'auto'` 分支**預留但目前永遠不會被寫入**，UI 一律手動命名。

**標籤名驗證只走 `wantedTag` 的未知 sally key 鉤子**（`findUnknownSallyKey()`）：已知只有
`api_sally_area`／`api_sally_flag`；冒出第三個就是標籤名最可能的所在，上限 3 筆。
深度上限 3、陣列只看首元素——實測掃 1MB＋ start2 僅 0.2ms，且對現有真封包**零誤觸**。
「首見帶標籤的艦娘清單」不再列入擷取——那類封包會重複出現、洗版並永久釘住 raw event。

**順帶的新假設**：`api_sally_flag`（`api_mst_mapinfo` 與 runtime mapinfo 皆有，1-1 為
`[1,0,0]`）ElectronicObserver 視為剩餘挑戰次數，語意未解；依上述機制，它也可能是**該圖的出擊
制限旗標**（允許哪幾個標籤）。下次活動一測便知。

**版面：自由池 × 標籤欄網格**（分區名「活動配船板」）。一次活動可有 **12 個標籤、5～7 個關卡**（使用者實測，非估計），
版面按這個規模配置：

- **左欄自由池**：未貼標、也未排入計畫的艦，依艦種分組成可摺疊的 `<details>`（展開狀態在重繪
  間保留，可「全部收起」），自帶搜尋框並獨立捲動。網格再寬，找船都不必離開左欄。
- **右側網格**：欄頭兩列——上列是關卡（`E{n}`＋作戰名），下列是該關的標籤欄；列是艦種分組
  （`DEFAULT_STYPE_GROUPS`，未列舉的艦種歸「水母・補助」）。格子裡是計畫或已貼上該標籤的艦，
  **「現在每個標籤鎖了哪些船」因此常駐可見**。
- **分配不依賴遊戲編成**：玩家不可能為了找船一直切回遊戲確認，主路徑是在板上點選艦（可多選）
  後點標籤欄頭，或拖曳到格子；拖曳時底部投放列列出自由池與每個標籤欄（附關卡），不必橫向
  捲到最右。放回自由池＝刪除該艦的計畫。遊戲艦隊只在出擊檢查時讀取。
- 關鍵字、艦種、航速、可裝備四個篩選同時作用於自由池與網格；航速與可裝備的選項與語意沿用
  `utils/ship-filter.ts`，與艦娘全覽一致。

**「計畫」與「現實」放在同一張卡片上，用卡片狀態區分**（`cardState()`）：把船排進計畫**不會**
讓它被貼上標籤，標籤只有實際出擊才產生；只顯示現實那半邊，排進去的船就像人間蒸發，兩者
分開顯示又容易被誤讀為同步錯誤。四態：

- `pool`＝計畫與實際皆無，留在自由池；`planned`＝已排入計畫、尚未貼標；`stamped`＝實際標籤
  等於計畫（附「貼」章）；`mismatch`＝實際標籤與計畫不同。卡片所在欄由 `columnOf()` 決定：
  `mismatch` 有計畫就留在計畫欄，否則落到實際欄。
- **已貼標的船計畫強制跟實際走**（`syncPlanFromActual()`，每次載入執行）：貼標不可逆，沒有
  「套不套用」的選擇。所以 `stamped` 卡片不可拖動、批次移動時也會被略過；`mismatch` 在同步後
  正常不會出現，只作防禦。
- 工具列以 `boardBudget()` 顯示全鎮守府四態艦數（自由池／計畫中／已貼／偏差）；每個標籤欄頭
  另顯示該欄「計」「貼」艦數。
- 標籤欄由 `knownTagIds()` 合併三個來源：計畫已宣告的標籤、船上實際帶著的標籤、`planByShip`
  指到的標籤。手動新增但遊戲裡還不存在的標籤也有欄位，否則使用者建了標籤卻找不到。
- 欄色存在 `PlanTag.color`（13 色，缺省時依標籤 id 取 `defaultColorForTag()`）；存起來才不會因
  標籤增減而整排換色。

**標籤欄歸到哪一關**（`mapsForTag()`）＝該標籤當 `grantsTag` 的關卡 ∪ `PlanTag.columnMaps`。
`allowedTags` 是路線規則，不算進欄位，否則「E2 可帶 E1 札」會把所有允許的標籤複製進 E2。
欄頭的 E1～En 鈕可手動增減歸屬；有實際觀測撐腰的關卡（該關 0→N，或已貼標艦出擊過、且編號
≥ 已歸類最小關）鈕會鎖住。沒有任何歸屬的標籤進「未歸類」群組。

**實際貼標觀測（`observeGrantedTags()`）**：「出擊結果才是唯一依歸」。資料來源是 raw events
的 `api_port/port`＋`api_req_map/start`（`path` 有索引；出擊海域優先讀 response，缺欄才退
`req`；**不需新表、不動 EventProjector**）。

- **只認 `0 → N`**：出擊前無標籤、回港後帶著 N ⇒ 該圖會貼出 N。`N → M` 不採信。兩次母港
  之間多次出擊時，這條歸因到最後一次並標記 `ambiguous`。
- **已貼標艦再出不改關卡歸屬**。後段船回打前段（或簡易難度無鎖）時，編成裡會帶著共用／
  後段標籤；把它們算進該圖會把 E1 塞滿。KC3Kai／poi 以 `api_sally_area` 直接入箱、不依
  出擊關卡分欄——本板有關卡欄，不能沿用那條。
- **已歸類的標籤在每一個對應關卡底下各出現一次**（`PlanTag.columnMaps` ∪ grants）。
  未歸類才進 SHARED。跨關使用來自「已貼標艦實際出過的圖」，只往編號 ≥ 已歸類最小關
  的方向補，避免後段札回打 E1 被寫進 E1。尚未歸類的札由使用者用欄頭關卡鈕指定。
- **未分類的已貼標**：從海域清單開頭連續已有 grants 的關算已分類；其後若只剩一關，船上
  已有、尚未入欄、且編號高於前段已分類區間的標籤掛到那一關（不寫死某一關、不等 0→N）。
  編號仍落在前段區間的未綁色進 SHARED。後面還有兩關以上時不猜。多關活動第一關只留該關
  0→N（無觀測則只留比後面已分類最小 id 更小的色），誤掛的後段色從第一關清掉。
  某一關已有 grants 時，id ≥ 該關最小 grants 的未出擊色仍補到那一關。
- 涵蓋範圍受 raw event 裁剪限制，UI 要講明「尚無觀測」可能是沒出擊過**或紀錄已被裁剪**。

**海域編號結構（使用者說明，已用真封包驗證）**：`mapKey = areaId * 10 + mapNo`，`61-5` 就是
活動 area 61 的第五海域 E5；本次活動 area 62 故 E1＝621。

**海域名稱與活動標題都拿得到，不必只顯示編號**（使用者的完整 start2 實測）：
`api_mst_maparea[62].api_name` ＝**活動標題**「反撃！第三十一戦隊の戦い」；
`api_mst_mapinfo[621..625]` 各帶 `api_name`（海域名，如「九州沖/南西諸島沖」）與
`api_opetext`（作戰名，如「第三十一戦隊駆逐艦の出撃」），本次活動正好五關。
存進 `GameState.masterMapInfo`（`mapsOfArea()` 取用）。

**抓得到 master 時，UI 一律不讓使用者重複輸入遊戲已經回答的事**：

- **關卡＝遊戲的海域清單，不由使用者建立**。網格以 `columnGroupsWithMaps()` 依
  `api_mst_mapinfo` 固定排出 E1～En，還沒有標籤的關卡也佔一欄，欄內放「＋再加標籤」入口；
  已有標籤的關卡改由關卡名旁的「＋標籤」新增。路線規則裡同樣是一圖一個主列，主列不可刪，
  也沒有「新增關卡」「關卡名稱」「對應海域」三個控制項。
- **關卡名格式**：網格欄頭是 `E{n}` 加一行作戰名（`api_opetext`）；路線規則與出擊檢查的
  下拉是 `E{n}　作戰名`，沒有作戰名才退用海域名（`api_name`，地理位置、通常又臭又長）。
  **不顯示 area 編號**——玩家不需要知道 62 是什麼。
- **活動名不需要自己命名**，直接用 `api_mst_maparea` 的活動標題，只顯示一次；同時有多個
  活動海域時才畫下拉選擇。
- 對應不上任何海域、但**有內容**的既有關卡列一律保留在末尾，保留使用者填過的資料。

抓不到 master（舊活動、或手動建立的板）才回退：沒有任何活動時可輸入活動海域編號手動建板；
活動名改為手填，路線規則改為「新增關卡」並可刪除每一列。

**路線規則與階段**（「路線規則」`<details>`，預設收起）：每列是一個 `PlanStage`，可勾
「可進入的標籤」（`allowedTags`，複選）。主列的「此關會貼的標籤」也可複選
（`setMapGrantTags()`）：同一張圖的不同路線可以貼不同標籤（使用者的 E2 就同時存在兩個標籤），
而一個 `PlanStage` 只有一個 `grantsTag`，所以第二個以後的標籤會各自開一個階段子列
（`PlanStage.phase`，系統名 `E{n}#{k}`）。使用者也可手動新增階段（預設名 `E{n} 階段{i}`），
階段列以單選下拉指定本路線會貼的標籤，可刪除。主列與階段都是完整的 PlanStage，出擊檢查的
路線下拉兩者都列出，`checkRoute()` 不必特別處理階段。標籤解除後只剩系統名稱的空階段會一併
清掉；使用者改過名的空階段保留。主列另顯示該圖的實際觀測（「E{n} 貼出過 …」或「尚無實際觀測」）。

`reconcileStages()`（純函式，node 已測）的首要職責是**保留既有資料**：有 mapNo 照 mapNo
對應、沒有的用 `guessMapNo(label)` 反推、同圖第二個主列轉成階段而非丟棄、對應不上但填過
東西的列保留在末尾；只有「對應不上又完全空白」才會消失。maps 為空時原樣返回（手填模式）。**這比 runtime 的
`api_get_member/mapinfo` 更早可用**——start2 登入就送、且在 `db.snapshot` 永久保留，
runtime mapinfo 要玩家開過海域選擇畫面才有。master 已載入時只認目前海域清單裡的活動圖；
master 尚未到才退回 mapGauges／已存計畫，避免 start2 延遲把當次板洗掉。
活動結束後該活動海域會從 master 消失，故 `masterMapInfo` 每次 start2 全量重建（不 merge）。
標籤對應關卡是單次活動限定：該 area 從 master 消失時刪除 `db.eventPlans` 那一筆（標籤、
關卡、觀測、快照），配船板留空等下一檔，不沿用 gauge 或舊計畫。`PlanStage.mapNo` 是關卡列與真實海域的連結——
`label` 是自由文字（「E4-3」「E5 解謎 1」），沒有這個欄位就無從拿實際觀測校對。
**多個關卡列可指向同一 mapNo**（E4-1／E4-2／E4-3 都是 E4 的不同階段）。
`guessMapNo()` 從 label 代填預設值時取 **E 後的第一個數字**（E4-3 → 4，不是 3），且只在
`mapNo` 為 null 時填，永不覆寫使用者已選的值。

**鎖定規則**：標籤一旦「已確立」（`establishedTags()`＝遊戲裡實際已有船帶著它），其名稱與
**牽涉該標籤的關卡**之標籤約束（`allowedTags`／`grantsTag`）即轉為唯讀，欄頭的移除／刪除鈕
也不顯示。理由：實際貼標不可逆，計畫端再改只會讓兩邊對不上，此時玩家只能依實際標籤填船。
僅當次活動進行中可暫時解除（`EventPlanRow.unlocked`，工具列在有已確立標籤時才出現切換鈕）。
活動結束後整份計畫刪除，不是解鎖後繼續改舊檔。鎖定狀態**由實際資料推導**、不另存旗標，只有
解除動作才落地——避免兩份狀態要同步。船上仍有人帶著的標籤不可刪除（`deletePlanTag()` 拒絕）。

**標籤出現的地方一律帶名稱**（不能只有 `#id`）：欄頭是可編輯的名稱欄（未命名時顯示
「標籤 #n」）、投放列是名稱＋關卡、路線規則與出擊檢查是 `#id 名稱`。只剩編號就認不出是哪個
標籤。
