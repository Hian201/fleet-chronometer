# 遠征加成、資料與期間彙總

## 遠征資源加成（`utils/expedition-bonus.ts`）

**遊戲完全不送這個機制的封包**——與 `repair.ts` 同類：公式是社群機制轉寫（非封包驗證），
面板必須標示為估算。來源：**直接讀取** wikiwiki.jp/kancolle/遠征（`#daihatsu` 節，裝備
基礎加成率表）與 wikiwiki.jp/kancolle/特大発動艇（`#bonus` 節，完整公式＋特大発超頂 2D
表）的**原始 HTML**，2026-08-03 逐字核對。**別用 WebFetch 對這類數字表格做摘要**——同一份
資料先後兩次用 WebFetch 摘要，兩次結果互相矛盾（且其中一版還混進了一段整段捏造、原頁面
根本不存在的「改修補正公式」），唯有 `curl` 原始 HTML 自己讀表格才收斂到一致且經五個算例
交叉驗證過的版本；日後任何缺資料，同一批 wikiwiki.jp 頁面應優先查，且一律読原始 HTML。

**master id 與基礎加成率**（id 已用 `samples/start2-master.json` 核對，非猜測；百分比為
wikiwiki.jp 原始表格數值）：大発動艇(68) 5%／大発動艇(八九式中戦車＆陸戦隊)(166) 2%／
特大発動艇(193) 5%（另有超頂加成）／武装大発(409) 3%／特二式内火艇(167) 1%／
装甲艇(AB艇)(408) 2%／特四式内火艇(525) 4%／特四式内火艇改(526) 5%。**大発動艇是子字串
會誤中大量改造/合體型裝備**（193/230/449/482/494/495/514/436/576等），比對務必用完整
master id 相等，不可用名稱 `includes`。

**公式**（wikiwiki.jp 原文逐字）：`獲得資源量 ＝ floor(基本量 × 大成功 × {1 ＋
min(基本補正之和,0.2) ＋ (0.2%×艦隊全體大発系★平均值)}) ＋ floor(基本量 × 大成功 ×
特大発補正)`。「基本補正之和」是艦隊全體（六艘）計入裝備的基礎加成率加總（特大発動艇的
基礎5%也算在內），封頂20%；**改修★項是平坦的 `0.2%×平均★`（★0–10，故最高+2%），
與基本補正是否已達20%上限無關**——別誤植成「乘以 min(基本補正,0.2)」，來源公式沒有這層
乘積，兩者是各自獨立的加法項。特大発補正是另一段獨立相加、**不受20%上限**，且**同時吃
「特大発個數」與「同時裝備的一般大発動艇(68)個數」兩個維度**（`TOKU_BONUS_TABLE`，2D
表，特大発+1／+2兩列對大発個數不敏感，+3／4以上兩列才隨大発個數變動 5.0~6.0%）——
**只看特大発個數的 1D 表不符合來源公式**；
`大発動艇(八九式中戦車＆陸戦隊)`等其他上陸用舟艇裝備**不計入這個「大発個數」維度**（wiki
腳注明載，只有大発動艇本體才算）。兩段各自 `floor` 後相加，不可先加總再取一次整。
大成功倍率沿用面板既有的 `×1.5` 慣例（`applyExpeditionBonus` 的 `successMultiplier`
參數），無加成時退化成原本的 `mul15` 行為。公式與 2D 表已用 wiki 原文五個算例（22%／28%／
20%／27.4%／27.8%）鎖進 `tests/expedition-bonus.test.ts`「wiki 原文算例」區塊。

**顯示**：`panel/main.ts` 的 `renderExped()`——直接把加成後數字取代原本的 `reward_*`
顯示值（不並排顯示兩個數字），**只有裝了計入加成的裝備時才變色**（`rewards.bonusActive`）。
變色用 `--sparkle`（金色）＝「有加成」語意色，**不可挪用 `--res-gain`／`--res-drain`**——
那組是資源紀錄的餘額消長語意（見該分區「刻意不共用」的既有注記），混用會稀釋兩邊各自的
視覺意義。**大成功那行不標示 `(×1.5)` 徽章**——`rewards.great.*` 已經是套用完大成功
倍率後的最終數字，並排一個「×1.5」字樣容易被誤讀成「這數字還要再乘1.5」。

**掃描範圍**：只掃 `expedCheck()` 正在檢查的那個艦隊（`deck.api_ship`），與既有的 drum
缶掃描（`DRUM_MST_ID` 同段邏輯）同一顆迴圈風格；不掃補強增設（大発系裝備不會裝在
ex-slot）。

## 遠征資料完整性（`utils/expedition-data.ts`）

**面板換裝後的成功門檻**：輸送桶數量與搭載艦數依目前槽位重算。火力、對空、對潛與索敵
以艦船快照的顯示素質為準；單件裝卸、補強增設換裝或一般槽全卸若只更新槽位，先依該項
素質對應的舊裝備與目前裝備算出裝備主檔素質差額。這段期間用 `~` 標記推算值，額外的
艦與裝備搭配加成變化不在推算內；缺必要資料時顯示 `—`。收到新的艦船素質時逐項校正。
跨艦移裝的 `slot_deprive` 直接套用同一回應中的兩艘艦資料，來源見
`THIRD-PARTY-NOTICES.md`。此端點仍待真實封包驗證。

**資料覆蓋範圍**：`EXPEDITION_DATA` 的 id 集合以真實 `api_mst_mission`
（`samples/start2-master.json`，2026-07-21 匯出）核對。poi-plugin-expedition 的
`assets/expedition.json` 自 2018-12-10 起未再更新，遊戲後續新增的 20 個遠征（id
41–46／103–105／112–115／131–133／141–142，涵蓋 maparea 1/2/4/5/7）條件取自持續維護的
ElectronicObserver（MIT）`Data/MissionClearCondition.cs`，轉換規則見下。id 301／302
（活動支援遠征，`expedDisplayName()` 已知的 S1/S2）以封包 `api_win_item1/2`／
`api_win_mat_level` 皆為 0 確認零收益，條件比照同為「駆逐2隻」支援任務的 id 33/34。

**條件資料的翻譯規則**（把 EO 的 C# 判定式轉成本專案 `required_shiptypes` 陣列）：
- `CheckShipCountByType(type, n)` → `{shiptype:[id], count:n}`；`CheckSmallShipCount(n)`
  （駆逐+海防）→ `{shiptype:[1,2], count:n}`（沿用既有 id100 等的既定寫法）。
- `CheckEscortFleet()`／`CheckEscortFleetDD3()`／`CheckEscortFleetDD4()` 是 OR 條件
  （軽巡+駆逐/海防N ‖ 護衛空母+... ‖ 駆逐+海防3 ‖ 練巡+海防2），本專案 schema 只能
  表達 AND，**沿用既有 id4/5/9（DD2）、id102（DD3）已經在用的簡化寫法**：只取最常見的
  「軽巡1 +（駆逐+海防）N」分支，即 `[{shiptype:[1,2],count:N},{shiptype:[3],count:1}]`。
  這是 schema 無法表達 OR 時的一致簡化規則。
- `CheckFlagshipType(x)` → `flagship_shiptype`；`CheckEquippedShipCount`／
  `CheckEquipmentCount`（TransportContainer＝輸送用ドラム缶）→ `drum_ship_count`／
  `drum_count`（與既有 id21/37/38 的既定對應逐筆核對一致）。
- id44（航空装備輸送任務）的 EO 條件含 `OrCondition`（水上機母艦2 ‖ 水上機母艦1+空母1），
  取第一分支簡化（與封包 `api_details`「水上機母艦2」的文字描述一致），會漏掉另一分支
  合法但更少見的編成；其餘 19 筆皆為單純 AND。

**收益數字來源**：EO 只驗證出擊「條件」，不含 `reward_fuel/bullet/steel/alum` 這類實際
收益數字。master 的 `api_win_mat_level` 是 0–4 的收益級距，同級距在不同
遠征對應的實際數字差異很大（如 level=1 在不同遠征分別對應 45/50/70/120/240/300 燃料，
無法單獨換算，因此數值取自 wikiwiki.jp/kancolle/遠征 的「詳細一覧表」原始 HTML，並與
`api_win_mat_level` 的 0/非0 pattern 逐筆交叉比對**全數一致**（見 `utils/expedition-data.ts`
檔頭註記）。這 20 筆與其餘 47 筆一樣正常顯示燃彈鋼鋁數字；`state.ts`／`panel/main.ts` 的
`amountsVerified` 分支邏輯予以保留（供之後若又出現條件已知但收益不明的新遠征使用），
只是目前沒有任何一筆會走到那個分支。

**itemtype 對照**：`rewardNames`（`state.ts` 的 `expedCheck()` 內）採 1＝高速修復材、
2＝高速建造材，與封包 `api_win_item` 的值相同。家具箱小／中／大在現行封包使用 10／11／12，
而 poi 2015–2018 快照仍使用 4／5／6；兩組必須同時相容。改修資材使用未占用的編號 7，避免與
舊資料的家具箱小（4）衝突。完整對照與來源寫在 `rewardNames` 旁的註解。

**id 165／166 是未確認資料**：這兩筆存在於 poi 資料裡（`reward_*` 全 0、
`required_shiptypes` 為駆逐2，與 33/34/301/302 同一種「支援任務」樣板），但**不存在於
目前的 `api_mst_mission` 快照**，無法確定是已停用／重新編號，或快照未收錄。因為 `expedCheck()`
只在 `masterMissions.get(expedId)` 查得到時才會用到 `EXPEDITION_DATA`，若遊戲從未送出
這兩個 id，資料不會造成錯誤顯示；在取得明確證據前保留原值。

## 遠征紀錄的期間彙總（`utils/expedition-stats.ts`＋`sections/exped-log.ts`）

**現行行為**：遠征紀錄可依指定日期區間彙總資源總量與各遠征次數；逐筆資料仍保留供明細查閱。

**為什麼落在遠征紀錄而不是資源紀錄（別搬家）**：兩者的數字語意根本不同——

- 遠征收入是**逐筆事件的獲得量**（`api_get_material`，封包直接給、可加總、精確）；
- 資源紀錄的一切消長是**兩個時刻的餘額差分**（封包只給餘額）。

放同一張表必然被拿去互相對照，但中間還隔著出擊消耗、補給、建造、任務獎勵，本來就對不
起來。缺席規則也相反：期間內沒有餘額取樣時資源紀錄必須寫「不可考」，遠征收入只在
`db.expeditions` 已投影的紀錄中計算。分區頂端的 `ov.expedStatsNote` 就是在
講這件事，**不要因為「畫面太囉唆」把它拿掉**。

**兩個誠實性前提**：

1. **母集合是「已投影紀錄中的」遠征，不是遊戲的完整歷史**。`db.expeditions` 由面板的
   `EventProjector` 投影（資源序列才是 background 落地的例外）。面板未開時投影會延後；
   raw event 只有在投影成功且通過保護規則後才可裁剪，因此不能把未開面板直接等同於永久缺席。
2. **回航道具（`items`）以 useitem id × 數量原樣彙總**，不併入四資源小計。種類看
   `api_useitem_flag[i]`：1／2／3＝高速修復材／高速建造材／開發資材，這三種的
   `api_useitem_id` 不是正數，投影時直接存成 useitem id 1／2／3（正好就是這三種資材的
   useitem id）；4 以上才看 `api_useitem_id`（家具箱 10–12、改修資材 4 等）。數量一律取
   `api_get_item{i+1}.api_useitem_count`。依據：KC3Kai `src/library/modules/Kcsapi.js` 與
   ElectronicObserver `Observer/kcsapi/api_req_mission/result.cs`。本專案沒有這支封包的原始樣本，但開發者 2026-11-18 的
   備份有依此規則寫入的實際紀錄：高速修復材 11 筆、開發資材 3 筆（11-13 起）。
   缺 `api_useitem_flag` 的封包維持只收 `api_useitem_id > 0`。修正前的紀錄沒有 flag 1–3 的道具，
   raw events 已裁剪，無從回填。依這個規則寫入的紀錄帶 `flagItems: true`（備份往返保留），讀的一方用它分辨
   「真的沒拿到」與「沒記到」，不用時間切分：更新前的版本寫的紀錄時間再新也缺這三種道具。

**道具名稱顯示**：逐筆明細、期間總計與明細 CSV 共用 `utils/item-catalog.ts` 的三語名稱，
以 useitem id 對照（資材使用目錄 id 1–4，不是持有量的 material apiId）。家具箱小／中／大
分別是 10／11／12。明細與期間總計的資材、家具箱、伊良湖顯示圖示與數量，名稱放在 hover 提示與圖片
替代文字；CSV 保留名稱與數量。沒有圖示的道具顯示名稱，未知編號保留 `#id`。
數量仍取紀錄的 count，不猜名稱、不改寫歷史資料。

`samples/start2-master.json` 的 65 筆 `api_mst_mission`，`api_win_item1/2[0]` 的非零值
只有 1／2／3／4／10／11／12／59，全部已有圖示。59 為伊良湖，出現在 D2「西方潜水艦作戦」，
使用既有的 `public/icons/ui/provision.svg`；`tests/exped-log-overview.test.ts` 從樣本枚舉全部
獎勵編號，檢查名稱與圖示檔案，避免新增遠征獎勵後漏接。這份覆蓋範圍是樣本中的遠征，
不代表道具目錄裡的所有道具都會由遠征取得。

**設計決定**：

- **期間捷徑的錨點是最後一筆紀錄、不是現在**（同資源紀錄的 `rangeBounds`）：久沒上線時
  以現在為錨會讓「7 天」一片空白，看起來像資料不見了。實際起訖一律寫在彙總列上，且**取
  的是實際落在期間內那幾筆的頭尾**，不是使用者選的那個窗（窗通常比資料寬）。
- **自訂日期只要填了任一端就蓋過捷徑窗**（另一端維持不設限），這樣「從某天以後」也是一次
  輸入就問得出來；此時捷徑鈕一律不亮，否則兩個控制項會同時看起來像正在生效。反過來按捷徑
  會清掉日期，否則按了沒反應。
- **「活動期間」捷徑**借 `resource-log.ts` 的 `buildEventPeriods()`（純函式）從
  `db.resourceMarks` 推出區段，直接回答「這次活動期間遠征賺了多少」。它只是捷徑：該表讀不到
  （v12 之前的舊安裝）就不顯示這個控制項，不影響彙總本身。
- **分組鍵是 `missionId` 不是名稱**（名稱隨語言與改版變動）；但 `missionId` 為 0 的舊紀錄
  只剩名稱可辨識，那批以名稱分組，不把互不相干的遠征全塞進同一列 `#0`。
- **摘要把大成功折進成功裡並寫明**（「成功 54（含大成功 10）」）：`共60 大成功10 成功54
  失敗6` 四個數字並排會被讀者加總（10+54+6≠60），但成功本來就含大成功。逐項比較留給彙總表
  的獨立欄位。
- **兩份 CSV 對應兩個問題**：彙總＝「哪些遠征各幾次、賺了多少」，明細＝逐筆紀錄且**跟著顯示
  欄位走**（同 ships／equipment 的規則）。兩者都是唯讀報表的匯出，**不是**可重新匯入的資料
  交換格式（那是 drop-log／build-log 的固定英文欄位集合），故表頭直接用目前語言的欄名。
- 分區**刻意不遵守「全量重繪」慣例**：有關鍵字與日期輸入框，整塊重繪會讓輸入框每打一個字
  就失焦。控制項只建一次、只重繪 `.el-body`，彙總表的排序走事件委派。

**驗證**：純函式以 `tests/expedition-stats.test.ts` 覆蓋（分組／加總／排序／CSV，含「壞資料
不得讓整個期間的小計變成 NaN」）；HTML 產出以 `tests/exped-log-overview.test.ts` 覆蓋。版面
另以 `playwright-core`（`channel:"chrome"`）實跑 `.output/chrome-mv3/overview.html`、用原生
IndexedDB 塞 60 筆假遠征紀錄驗證過期間切換／表頭排序／關鍵字篩選（含輸入框不失焦）與深淺
兩色主題。**已知殘留**：亮色主題下成功綠 `#7fd17f` 對白底偏淡——那是分區既有「遠征結果」欄
的色值，尚未調校（改色需先跑 dataviz 驗證器）。

## 遠征組合建議（`utils/expedition-plan.ts`＋`sections/exped-log.ts`）

**現行行為**：遠征分區的「規劃」子分頁「遠征組合建議」（標「推算」）。玩家填「多久收一次」遠征、
「睡多久」（每天一次較長的離開，0＝不另排）並勾選要存的資材，工具三隊一起挑：有備蓄期限時，讓勾選資材在期限時的「存量 ÷ 上限」最低的那一項最高；沒設期限時，讓勾選資材
全部存滿的天數最短（存不滿時退回比四週後的比例，與流量觀測窗同長）。結果區由上而下：
- 沒設期限、組合能全部存滿時，先一句「約 N 天後全部存滿（含最近的消耗）」。
- 一句結論：最需要補的資材（`focus`）現有多少、這組遠征到推算時點帶進多少、合計多少（上限多少）；合計會超過上限時
  改說幾天存滿。數量只算遠征本身的淨收入（已扣補給），玩家才能直接對上「跑這三條能存幾萬」；出擊、開發、建造等
  增減只用來判斷哪項最需要補，結論下方另一行寫明。基本資源以「21.1 萬」這種簡寫（`Intl` compact），離散資材照原數。
- 建議組合（有睡多久時分「在線時」與「睡前派出」兩表，同一列是同一隊），每條標「補哪一項」。
- 推算表（各資材現有／照目前步調／照建議的存量比例與每日淨增減，標出瓶頸）與全部候選：細節預設收合，
  重算時保留玩家展開的狀態（`data-part`）。
- 月常小表。

不檢查玩家編不編得出艦隊。計算全在純函式 `resourceNeeds()`／
`planExpeditions()`；分區檔只管偏好、載入與 HTML。

**不讓玩家設權重**：權重是要玩家把「哪項比較缺」自己換算成數字，而存量、上限、流量與期限都已在手，缺多少可以算；
玩家只回答程式猜不到的三件事：想存哪些（勾選）、存到何時（備蓄期限）、何時不在（收取間隔與睡多久）。
為了讓結果不必讀表就懂，頂端寫一句結論、每條遠征標它主要補的資材。

**補哪一項**（`rolesOf()`）：勾選、持有可考、還沒滿、這條有正收入的資材中，推算時點仍未滿的優先；取這條占組合中
該資材遠征收入比例最高的一項（「這項主要靠它」），比例相同（例如都是唯一來源）時取推算比例較低的一項。
在線那條的收入按該隊實際在線時間換算，睡前那條算一趟。

**為什麼是比例最低的那一項，不是加權加總**：存資源是為了活動之類每項都要夠的場合，資材之間是互補、不是替代，
彈藥再多也補不了鋁土。加權加總會讓三隊擠向單趟總量最高的同一類遠征（例如三隊裡兩隊跑彈藥）。改用推算時點的
存量比例，最大化其中最小的那個；同樣低時再比第二低的，依此類推（leximin）。
- 比例超過上限算 1：已滿或會滿的資材不再吸走隊伍，不需要另外排除「會浪費」的資材。
- 用「占上限的比例」比較，基本資源（上限 350,000）與高速修復材等（3,000）不同量級才可比；每日淨增減為負時照樣成立
  （先前以「到上限天數」比較，淨增減為負時全是「不會滿」，退化成比較原始數量，小單位的資材永遠不會被當成瓶頸）。
- 稀缺程度不由程式指定權重，而是從玩家自己的流量算出：平常打得兇、回復慢的資材比例自然最低。
- 比例同分時依序再比：到上限天數（由最慢的一項比起，越短越好；已滿但淨增減為負、會掉出上限的算存不滿，溢出不算好處、
  維持在上限才算數）、推算時點仍未滿的勾選資材每日淨增減 ÷ 上限的總和（已滿資材多拿只是溢出，不算）、
  八種資材每日淨收入 ÷ 上限的總和（順便多給沒勾的資材者優先，例如兩條遠征每天給一樣多的鋼時取另給燃料的 38）。
  期限前都會滿的組合在比例上全部同分；沒有這兩層，窮舉時第一個碰到的組合（編號最小、可能完全不給該資材）就會入選。

**沒設期限：全部存滿的天數最短**：要的是「最快讓每項都到上限」。收入是線性的，最快的分配會讓各項大約同一天到上限，
所以不必另寫目標：推算時點先放在一年後（`UNTIL_FULL_MAX_DAYS`）比較，一年內能全部存滿的組合比例都是 1、勝過任何有資材
存不滿的組合，再由「到上限天數」挑最快的；推算時點收到這組實際存滿的那天，畫面的推算表與結論都以那天為準。
一年內怎樣都存不滿（消耗大於遠征補得上的量，或已滿卻會掉出上限）時，「最快存滿」沒有意義，回到四週後照常比較。
固定比四週後的比例不行：四週後最好看的組合可能有一項永遠差一點存不滿，比「多花幾天但全部會滿」的組合差。

**支出照**（`SpendBasis`）：推算時每天遠征以外的淨增減（出擊、開發、建造等支出與自然回復、任務收入）照哪一段算，
組合會跟著換。接下來怎麼打只有玩家知道，所以由玩家選：
- 最近幾週平均（`recent`，預設）：整段觀測期間（最多四週），照常出擊時用。
- 支出最少的一週（`lightest`）：`observeFlow()` 的各週明細（`blocks`）中，四大資源基本淨增減 ÷ 上限總和最大的一週，
  準備進入備蓄、少出擊時用；畫面寫明是哪一週。那週有沒帶 `flagItems` 的遠征紀錄時，高速修復材等道具的遠征收入不全、
  基本淨增減不準，道具沿用整段平均並說明。沒有完整一週可比時退回整段平均。
- 不計支出（`none`）：基本淨增減當 0，只看遠征本身能存多少。
「目前步調」一欄與此無關，固定照觀測期間的實際步調，當作對照。選擇存在 `kc-exped-plan`。
用開發者 2026-11-17 的備份（每 2 小時收、睡 8 小時、沒設期限）：最近四週平均因 11 月初出擊特別多而一年內存不滿；
支出最少的一週（10/20–10/27）約 80 天、不計支出約 75 天全部存滿，與社群「活動後約百日回到上限」同一量級。

**推算存量**：持有 ＋（基本淨增減 ＋ 三隊遠征每日淨收入）× 天數。
- 持有＝目前持有 − 改造目標的需求，有沒有設備蓄都扣改造保留（同備蓄的 `stockpileLinesOf()`）。
- 基本淨增減＝所選期間（見「支出照」；預設為 `observeFlow()` 整段觀測期間的 `mean`）的每日淨增減 − 同期間遠征的每日淨收入（收益 − 補給），
  也就是自然回復、任務等收入減去出擊、工廠等消耗。遠征的補給算在遠征帳上，換遠征時補給才不會重複算或漏算。
  觀測不足一週時不可考，當 0 並在畫面說明只用遠征本身推算。
- 「目前步調」直接用觀測的每日淨增減（含當時跑的遠征），與「照建議」對照。
- 最需要補（`focus`，結論句與排列依據）＝不跑遠征時推算時點比例最低的一項（持有＋基本淨增減 × 天數），只看有候選遠征
  給得到、還沒滿的資材（例如改修資材給不到，依它排序沒有意義）。它只取決於現況與消耗，不隨收取間隔或組合改變；
  若取照建議跑完後最低的一項，組合每換一次答案就換，玩家會以為短板在變。
- 瓶頸＝照建議跑完仍未滿、比例最低的資材，只標在推算表：「這組跑完還剩誰最弱」與「現在最缺誰」是兩件事。

**遠征的每日淨收入**：每趟期望淨收益 × 每天能收幾次。玩家每隔「多久收一次」回來一次，耗時 t 的遠征一輪佔
間隔 × ⌈t ÷ 間隔⌉，所以比間隔長的遠征要等兩輪以上。候選約六十條，三條的組合在數萬以內，直接窮舉求精確解。
窮舉前剔除被至少五條其他遠征全面勝過（八種資材都不少，睡前的還要佔用不更長）的遠征：組合用到它時，至少有一條勝過它的
不在組合中、也不和別隊衝突，換上去每項都不減，評分只會更好或同分，所以不影響結果。收取間隔與睡多久的輸入停 300 毫秒才重算。

**睡前組合**：玩家的登入不是整天均勻的，單一間隔會把睡覺那段也當成能一直收（高估短遠征），或把白天的頻繁收取全部
抹掉。「睡多久」S 分鐘大於 0 時，每隊一天＝在線組合跑「一天 − 佔用」分鐘＋睡前遠征一趟。
- 在線趟數取整數：⌊在線分鐘 ÷ 一輪⌋。醒來出發、睡前收回，最後一趟睡前收不回來就不能派（那一隊也派不了睡前遠征）。
  例：每小時收、睡 8 小時，東京急行（2 時 45 分，一輪 3 小時）在線 16 小時跑 5 趟而不是 5.33 趟；9 小時一輪的遠征在線
  只跑 1 趟而不是 1.78 趟。沒有作息離開（S＝0）時整天連續收，一天的趟數不必是整數。
  剔除被全面勝過的在線遠征時，比的是每一種可能的在線時數下的收入：取整數後，每日收入較高的遠征在某些在線時數下反而較少。
- 佔用＝S；睡前遠征耗時 t 比 S 長時，回來後要等到下一個收取點，佔用＝S ＋ 間隔 × ⌈(t − S) ÷ 間隔⌉，那一隊在線時間跟著變短。
  佔用超過一天的遠征不能每天睡前派，只當在線候選。
- 同一條遠征不能兩隊同時跑：在線組合的某條若是另一隊的睡前遠征，睡前出發時它可能還沒回來，所以只允許同一隊白天、
  睡前跑同一條。佔用不同時試三條的所有排列，取最好的配對。
- 兩組一起比同一個目標（同上的 leximin），求精確解。兩組合的配對有數萬 × 數萬，直接窮舉要算數十分鐘，分兩步：
  1. 近似解：交替固定一組、窮舉另一組，直到不再變好；每一步都含目前的組合，分數不下降。從「先挑在線」與「先挑睡前」
     兩個起點各跑一次取較好的。以開發者的遠征紀錄隨機抽 100 種持有量、支出與作息，約兩成停在局部解（組合與精確解不同）。
  2. 分枝定界：以近似解為目前最好，對每個在線組合算上界（在線那條取各種在線時數下最有利的趟數，睡前取各項收入最高的
     三條，不必是同一組），上界的存量比例與到上限天數都比目前最好差就整組跳過；沒跳過的再對每個睡前組合用該組實際收入
     算一次上界。存量比例與天數對每項收入都單調，收入只會更少的組合不可能更好，所以結果與完全窮舉相同（隨機 300 組
     六到九條遠征的小資料，與關掉剪枝的完全窮舉逐一比對都一致）。後兩層同分規則（total、byproduct）不單調，上界同分時照常比較。
- `planExpeditionSteps()` 分段執行：第一段給近似解，之後每段不超過數十毫秒。畫面先同步算 100 毫秒，算得完就直接顯示
  精確解；算不完先顯示近似解，頂端加一個帶轉圈的狀態膠囊「還在比對其他組合」（與說明文字區隔；減少動態效果時改為靜態圓點），其餘每段 30 毫秒在背景算完再換上，條件改變時放棄舊的計算。
  以開發者的紀錄量測，近似解平均約 0.2 秒（沒設期限要比兩個推算時點時最多約 0.5 秒），精確搜尋再平均約 0.2 秒、
  最多約 2 秒。

**每趟期望收益**：
- 玩家該遠征的紀錄達 `MIN_RUNS`（10）趟：用紀錄平均（含失敗、大成功與大發加成，是玩家實際的跑法）。
  高速修復材、高速建造材、開發資材只數帶 `flagItems` 的紀錄（見上方「兩個誠實性前提」第 2 點），沒帶的紀錄沒記到這三種
  道具、不是真的 0；有標記的不足 `MIN_RUNS` 時這三項改用固定報酬推算。捷徑：「最近幾週平均」的觀測期間裡還有沒帶標記的
  紀錄時，這三項的基本淨增減會偏高（那些紀錄的道具收入沒扣到），觀測期間的紀錄都有標記後就沒有這個偏差。
- 不足時以固定報酬推算，畫面以斜體標示：
  - 資源＝`expedition-data` 的固定報酬 ×（成功比例 ＋ 1.5 × 大成功比例）× 大發加成水準。大成功 1.5 倍依
    wikiwiki.jp/kancolle「遠征」。成功／大成功比例取玩家全部紀錄（平常是否刷閃反映在這裡；沒有紀錄時當成功、
    不假設大成功）。大發加成水準＝常跑遠征的實際資源 ÷ 理論值的中位數，下限 1；沒有常跑的遠征時為 1。
  - 道具依主檔 `api_win_item1`／`api_win_item2`（`samples/start2-master.json` 的真封包欄位）與 wikiwiki「遠征」的規則：
    item1（遠征詳細畫面左側）成功或大成功都隨機入手，數量 0～上限平均分布，期望＝上限 ÷ 2；item2（右側）只有
    大成功入手，數量 1～上限平均分布，期望＝(上限 + 1) ÷ 2。B1、A2、41、11 的高速修復材都在 item2，是大成功限定。
- 沒有固定報酬資料也沒有紀錄的遠征、以及沒有任何收益的遠征（支援遠征等）不列入。

**補給**：燃料與彈藥的每趟收益已扣補給。依 wikiwiki「遠征」，各艦消耗出發時燃彈 × 消費率（主檔 `api_use_fuel`／
`api_use_bull`），端數切捨。編成取玩家最近一次跑該遠征的紀錄快照，艦名對 master 的燃彈上限（紀錄存的是當時語言的
顯示名稱，對照表同時收原名與目前語言的譯名）；對不到或沒跑過時，以最低編成艘數（`expedition-data` 的 `ship_count`）
× 玩家遠征艦燃彈上限的中位數推算。社群推薦也提醒，30 分鐘級的短遠征一天跑二十多趟，補給燃料可能讓淨燃料為負。

**候選**：所有非月常、有收益、目前能派的遠征。沒跑過的照列並標「沒跑過」；若只列玩家跑過的遠征，沒常跑的高效遠征
（如 2、A2、B1）永遠進不了候選。遠征不能同時由兩支艦隊執行，組合內不重複。

**遠征清單**（`api_get_member/mission`，進遠征畫面時送）：`GameState.missionList` 記最近一次的清單，`api_get_member/mission`
在 `SNAPSHOT_PATHS`，重新登入後仍保留。依 `samples/mission-list.json`（開發者 2026-11-18）：
- `api_list_items` 是 `{api_mission_id, api_state}`。不在清單的遠征目前不能派：樣本缺的 11 條是 S1／S2 支援遠征，以及
  43、44、A5、A6、B3–B6、D3，正好是 KC3Kai `src/library/helpers/KanColleHelpers.js` 的 `monthlyUnlockTable` 裡本期前置
  月常還沒成功的那些（B3–B5 在 8 月跑過，現在仍缺，所以「不在清單」不是「從沒開過」，月常每期換期後前置要重跑）。
- `api_state`：已通關的一般遠征 2，本期還沒跑的月常與 33／34 支援遠征 1，沒有 0；與 ElectronicObserver
  `Other/Information/apilist.txt`（0＝未出撃、1＝未達成、2＝達成済み）一致。月常本期成功後變 2、直到換期，
  以它為前置的月常同時出現在清單（`samples/mission-list-a4-done.json`：A4 跑完後 103 由 1 變 2、44 出現）。
- `api_limit_time[0]` 是下次月常換期的 Unix 秒（樣本為 2026-12-15 12:00 JST，與推算一致；KC3Kai `Kcsapi.js` 同樣取 `[0]`）。

規劃器的用法：有清單時，不在清單的一般遠征不列入候選，畫面寫明條數（一般遠征開了不會再鎖，上一期的清單也可用）；
候選的「沒跑過」不再請玩家確認是否開放。清單的換期時間還沒到（本期的清單）時，月常小表把不在清單的標「未開放」、
排在本期能跑的之後，本期截止用 `api_limit_time`；上一期的清單不用來判斷月常，本期截止回到推算。從沒收到清單
（新安裝、還沒進過遠征畫面）時全部照列。限制：開發者的一般遠征都已開放，一般遠征未開放時的樣子沒有直接樣本，
依月常的情形推論為同樣不在清單。

**月常**：主檔 `api_reset_type === 1` 的遠征每月只能通關一次，當定額收入，不進組合。判別依 KC3Kai
`src/pages/devtools/themes/natsuiro/natsuiro.js`（遠征規劃以 `api_reset_type == 1` 標 "(M)" 並接每月重置時間）
與 ElectronicObserver `ElectronicObserver/Data/MissionData.cs`（`ResetType => api_reset_type`，註解
「進捗リセットタイミング」）交叉比對，`samples/start2-master.json` 中值為 1 的有 16 條（42、43、44、46、
A4–A6、B2–B6、D2、D3、E1、E2）；`GameState.masterMissions` 存 `resetType`、`winItems`、`use`。月常小表是提示：只列獎勵
（`api_win_item1/2`）含開發資材（useitem 3）或改修資材（4）、且本期還沒完成的月常，不論有沒有紀錄（`MONTHLY_HINT_ITEMS`；
樣本主檔 16 條月常中有 12 條符合，A4、B3、42、D2 不符），附最後一次成功的日期（沒有成功紀錄寫明）與本期狀態（未完成、

## 遠征分區的子分頁與開放檢查（`utils/expedition-unlock.ts`＋`sections/exped-unlock.ts`）

**子分頁**：遠征分區（hash 仍為 `#/exped-log`）分「紀錄｜規劃｜開放」，`sub=log|plan|unlock`，沒有參數時看紀錄
（最常用），不記住上次的選擇。三頁在同一次 render 建好、切換只改 `hidden`，輸入、展開與捲動都保留；網址隨子頁以
`replaceState` 更新。目標規劃的「用遠征補」連到 `?sub=plan`，規劃頁「有 N 條遠征目前還不能派」連到 `?sub=unlock`。

**狀態來源**：只看最近一次遠征清單（`GameState.missionList`，見上節「遠征清單」）。在清單＝能派，`api_state` 2＝已達成
（月常為本期完成）。清單是上一期的（`api_limit_time` 已過）時，依換期規則推算：月常本期完成清空、有每期前置的月常
不出現，畫面寫明是推算。從沒收到清單時只顯示「進一次遠征畫面」。開放頁註冊 `onStateChange`，進遠征畫面後就地重繪，
保留一般遠征區塊的展開狀態。

**開放條件**（遊戲不送，只用來寫「還缺什麼」，不改變能不能派的判斷）：
- 月常每期的前置 `MONTHLY_UNLOCK`：wikiwiki.jp/kancolle/遠征「各遠征の開放要件」標「(毎月)」的九條
  （B3←B2、B4←B3、B5←B4、A5←A4＋B3、A6←A5＋B4、B6←A4＋B4、44←A4、43←42、D3←D2）。與 KC3Kai
  `src/library/helpers/KanColleHelpers.js` 的 `monthlyUnlockTable` 逐條相符，也與 `samples/mission-list.json`
  （缺 43、44、A5、A6、B3–B6、D3）及 `mission-list-a4-done.json`（A4 本期完成後 44 出現）一致。其餘月常
  （A4、B2、42、46、D2、E1、E2）換期後直接出現，同頁有明文。
- 首次開放條件 `FIRST_UNLOCK`：同一張表（2026-11-18 讀原始 HTML；該表注明參照英 wiki 2023-05-16），只有這一個來源。
  同頁留言有兩筆未寫回表格的回報（B2 可能另需 B1、東京急行可能不需 1-5），照表不改，等有實際清單佐證再修。
  `tests/expedition-unlock.test.ts` 檢查兩張表涵蓋主檔所有遠征（活動支援 S1／S2 除外）。

**狀態措辭**：可派、本期完成、未出現（有每期前置的月常，前置一路追得回清單裡的月常）、未開放（首次條件還沒滿足）。
遊戲不分「從沒開過」與「本期還沒出現」，兩者要做的事相同，區分只影響措辭。每組第一個可派的標「下一步」。

**版面**：月常解鎖路徑是一張依組分段的表，第一組依最快順序 A4 → B2 → B3 → A5 → B4 → A6（wikiwiki 同頁
「(A4+B2+B3)→A5+(B4)→A6」），分支 B5、B6、44 接在後面；其後 42 → 43、D2 → D3、每期直接出現（46、E1、E2）。組標題寫本期
完成數與合計遠征時間。每列附消耗（主檔 `api_use_fuel／api_use_bull`，各艦燃彈上限的比例）與成功收入（四資源取
`expedition-data`，沒收錄寫不可考；道具取主檔 `api_win_item1`＝成功時最多 n 個、`api_win_item2`＝大成功限定）。
一般遠征全開時收成一行放最後；沒開完才展開放在路徑前面，只列還有未開放遠征的海域。

## 遠征紀錄的逐筆明細（`sections/exped-log.ts`）

**遠征類型欄**：遠征名下方寫「第 N 艦隊 · 遊戲內編號」（B2、05 等，取主檔 `api_disp_no`）；主檔沒載入時只寫艦隊。
`missionId` 是 `api_mission_id`（例：B2＝111），只在內部使用，不顯示。CSV 同樣寫遊戲內編號。

**編成欄**：預設收合，展開看艦名與等級。月常（`api_reset_type` 1）與交戰型（`api_damage_type` 1／2）遠征的紀錄另存
裝備（`ExpeditionShip.gears`＝一般槽的裝備 master id＋改修值，`ex`＝補強增設），展開時一艦一行列出裝備圖示、名稱與★；
這兩類要湊條件、會受損，玩家會回頭查當時怎麼配。一般遠征與這次改版前的紀錄只有艦名，不回填。
`api_damage_type` 的語意：`samples/start2-master.json` 中值為 1 的 43、A5、B4、D2 與值為 2 的 46、A6、B5、B6、D3、E1、E2，
與 wikiwiki.jp/kancolle「遠征」交戦 I 型／II 型的清單逐條相符。備份還原會驗證並保留 `gears`／`ex`。

**工具列**：打撈、遠征、建造、開發四個紀錄頁的下拉選單與日期、搜尋框共用同一組外觀（`.rs-search` 那組規則）。
