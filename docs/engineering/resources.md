# 資源紀錄（`utils/resource-capture.ts`＋`resource-log.ts`＋`line-chart.ts`）

**兩個貫穿全部設計的事實**：

1. **封包只給餘額，不給消耗**。`api_material` 是「現在剩多少」，任何「花了多少」都是
   **兩個時刻的餘額相減**。故 UI 的每一個消長數字都成對顯示起訖時刻；算不出來
   （期間內沒有取樣）一律寫「不可考」，**不以 0 頂替**（同全專案的缺席處理原則）。
2. **歷史無法回填**。序列從擴充安裝那一刻開始累積——`db.events` 早被裁剪、
   `db.snapshot` 只留最新一筆。故 v12 **不做任何 upgrade 回填**，UI 的空狀態也直說原因。

**擷取落在 background，不是 EventProjector**（與其他四張 derived tables 相反，理由要記住）：
資源列不需要任何 GameState 上下文（封包裡就是八個數字），而它的價值**恰恰在於連續**
——面板沒開的那幾天要是斷掉，「這次活動花了多少」就永遠算不出來。故與 `db.snapshot` 同層，
在 `ingestEvent()` 的 post-processing 落地。主鍵用**來源 raw event id**（非自增）：
SW recovery 會重跑同一筆事件，put 冪等才不會把同一個時刻記兩次。

**取樣來源只認帶完整八項的 path**（`api_port/port`、`api_get_member/material`）。
`charge`／`createitem` 那類只帶部分項目的封包不構成一列快照；任一項不是有限非負數字就
**整筆放棄**——寧可少一列樣本，也不要把 undefined 當 0 畫成一道不存在的暴跌。
索引順序＝`api_material` 順序：0燃料 1彈藥 2鋼材 3鋁土 4高速建造材 5高速修復材
6開發資材 7改修資材（與 `FactoryLogRow.used`、panel 的 `MAT_KEYS` 同一組）。

## 特殊時間點（`db.resourceMarks`）

使用者要的是「一次活動每個關卡各花了多少」，故要在資源序列上標出界線。兩種標記：

| 標記 | 來源 | 語意 |
|---|---|---|
| `stage-open` | `api_req_map/start` 且 `api_maparea_id >= 10` | 第一次出擊到該活動海域（add-if-absent，只留最早那次） |
| `gauge-clear` | `api_get_member/mapinfo` 的量表歸零 | 首次**觀測到**該海域血量歸零 |

**`gauge-seen` 是第三種 row，但它不是里程碑，是守衛**：量表歸零只能從 mapinfo 觀測，而
「一裝上擴充就看到某圖已經是 cleared」不代表剛剛打通（同 EventProjector 的
`gaugeSeenUncleared` 守則）。故必須先觀測到該圖「未歸零」才武裝，之後的歸零才算數；
記下 `gauge-clear` 時刪掉守衛，下一段量表重生時再重新武裝。SW 隨時會死，這個守衛
**不能是記憶體變數**，只能落地。

**clear 的 `seq` 用「該圖已有幾筆 clear」推導，不用 `api_gauge_num`**——後者語意未經驗證
（61-5 樣本為 4，可能是第幾段也可能是總段數），拿它當主鍵等於賭在猜測上。原始值仍存
（`gaugeNum`），只存不推導。歸零判定與 `EventProjector.isGaugeBroken` 逐條相同、欄位皆已實測：
`api_cleared`／HP 量表 `now_maphp === 0`／擊破數達標；**`now_maphp === 1` 是「最終段、還差
一沉」不是通關**。

**時刻的誠實性**：`gauge-clear` 的時間是「**觀測到**歸零的時刻」，不是斬殺當下——遊戲要等
玩家再開海域選擇畫面才送那筆 mapinfo（即時性尚未觀測，見 [maps.md](maps.md)「斬殺偵測」）。UI 文案已明講，
不假裝那是斬殺時刻。

## 趨勢圖：最上方一張大圖、八條線、圖例即開關

**趨勢圖固定為一張大圖、八條線與可切換圖例**：八項資材共用一個時間軸，便於比較資源變化；
量級差距由序列開關與各自 y 值域處理。

量級差距（燃料十萬級、螺絲千級）的解法是**開關**：`multiChartGeometry()` 的 y 值域
**只由「顯示中」的序列決定**，關掉燃料之後螺絲那條就會撐滿整張圖。工具列另有
「全部顯示」與「只看四大資源」（燃彈鋼鋁量級相近，最常用的一組）兩顆捷徑。
**雙 y 軸仍然不做**——兩套刻度沒有共同基準，任何交叉都是視覺巧合。

**圖例是控制項不是說明**：一顆一項資材，色塊＋圖示＋名稱＋目前值，點了就開關那條線。
關掉的**留在列上**（淡化＋空心色塊），不然使用者不知道還有那一項可以打開。

**序列配色是 dataviz 參考色盤的固定順序，資材 i 恆定拿第 i 個色位**——開關序列時絕不
重新分配顏色，否則關掉一條線會讓其他線全部換色（dataviz 硬規則：色彩跟著實體，不跟著
排名）。深淺兩套色值各自用 `validate_palette.js` 驗過亮度帶／彩度／CVD 分離／對比。

x 依 `ts` 的相對位置而非等距索引——取樣本來就不等距（一天打十場、隔天不上線），
等距畫會把時間軸扭曲。

**SVG 實作約束**：

- **`hidden` 是 HTML 屬性，對 SVG 元素無效**。十字準線與游標點掛 `hidden` 之後照樣畫在
  (0,0)，畫面左上角會出現一顆莫名其妙的點。要用 CSS `[hidden] { display: none }`。
- **不要用 `preserveAspectRatio="none"`**。非等比縮放會把 y 軸刻度的文字橫向拉伸
  （容器 1600px 時字被拉成 1.6 倍寬）。改成等比＋`aspect-ratio: 1000 / 300`，
  線寬另用 `vector-effect: non-scaling-stroke` 固定成實際像素。

**抽稀是純減量，不平滑**（`downsample()` 每個時間桶取最後一筆、首尾必留）：平滑會把
「一次活動燒掉十萬燃料」的那道陡降磨圓，而那正是這張圖唯一要看的東西。粒度收斂
（`bucketSamples()` 每筆／每小時／每日）同理取**最後一筆**而非平均——餘額是「當下有多少」，
取平均沒有意義；每日依**本地時區**切，玩家心裡的「今天」是本地日期。

**新增兩個語意色變數 `--res-gain`／`--res-drain`**（增加／消耗）。刻意不挪用 `--dmg-*`
（大破/中破/小破）或 `--sally-*`（標籤狀態）——那兩組承載的是完全無關的語意，共用會互相
稀釋（design-guidelines §4.5）。色值 `#2f8fcf`／`#cf7526` 已用 dataviz 驗證器對深色
`#182030` 與亮色 `#ffffff` 兩種底色跑過亮度帶／彩度下限／CVD 分離／WCAG 對比四項檢查，皆 PASS。

## 版面與驗證

分區**刻意不遵守「全量重繪」慣例**（design-guidelines §4.2 的第二種例外）：這裡有使用者
自己造出來的狀態——圖表的十字準線、詳細清單的捲動位置與分頁。控制項只建一次，之後只重繪
`.rl-top`（摘要＋圖表）與 `.rl-bottom`（欄位開關＋詳細清單）；夾在中間的活動資源消耗只建
一次（它有搜尋框），結果區一律事件委派。**詳細清單的欄位開關做成表格正上方的一排圖示鈕
（`colRackHtml`，一項資材一顆、只放圖示不放文字，同表頭也是純圖示）**，不是藏在下拉選單裡；
名稱靠 title 與圖表圖例補足。欄位開關**跟著 CSV 匯出走**（同 ships／equipment
的規則）。期間／粒度／欄位／每頁筆數存 localStorage（`kc-resource-view`），不進 Dexie、不進備份。

版面驗證走離線預覽（`tools/preview/resource-log.ts`）——上面那兩個坑都是它抓到的
（外加 i18n 字串裡的 Markdown `**` 會原樣顯示在畫面上）。與出擊紀錄的預覽有一點不同：
`samples/` 裡**沒有現成的餘額歷史**（那要跑好幾週才生得出來），故用**有依據的合成序列**
——起訖水位、每場出擊的消耗量級、活動的關卡數與里程碑順序都照 `samples/61-*.json` 那次
活動的形狀。合成的是「時間軸」，欄位語意仍走與分區完全相同的那份程式碼（HTML 建構器抽到
module scope 共用）。真實規模才看得出版面問題——八格折線並排、六位數的欄寬、一次活動
八個里程碑，手捏三筆假資料一切都很好看。預覽輸出三語（`resource-log{,-en,-ja}{,-light}.html`）。

## 活動資源消耗：歷次活動清單、前後段與攻略後

**資料面沒有改**：每次活動是不同的 maparea，`buildEventPeriods()` 本來就按 area 分組；不改
schema、不改備份格式。改的是呈現與切分。

**版面＝左清單＋右明細／比較**。活動的身分（年份季節＋各段作戰名）只在左側清單完整呈現一次，
數字只在右側表格；表格內**不插標題列**（夾在數字中間會打斷縱向比對）。清單依年份分組
（原生 `<details>`、組標題 sticky、預設展開最近兩年），卡片內只寫季節（年份由組標題交代）。
篩選列＝關鍵字（比對日文原名、譯名、年份季節）＋年份＋季節大類（初春併春、梅雨夏併夏、
初秋併秋，卡片仍顯示原季節）。篩選**只切 `hidden`**，不重繪輸入框與展開狀態。右側「比較」把
目前篩選到的活動排成一表，可切「攻略合計／攻略後／攻略＋攻略後」與「合計／日均」，列首只放
短標、點了跳回明細。合計／日均、明細／比較、比較項目都只切外層 data 屬性。

**作戰名**：遊戲只在活動期間送前段作戰名（`api_mst_maparea.api_name`），後段名不在封包裡、
活動結束後前段名也消失，故歷代作戰名人工維護於 `event-calendar.ts` 的 `EVENT_OPERATIONS`
（日文原名／英文／台灣華語＋各段 `firstMap`）。非日文介面在原名下方附譯名，與原名相同時
不重複。kcdata `_maparea/52` 記的是「帰ってきた鎮守府秋刀魚祭り」、koubrowser 記的是
「海上護衛！本土近海航路の防衛」——兩者都對：2021秋前段是通常海域的秋刀魚祭（沒有活動
關卡，`firstMap: null`），後段才開活動海域，所以 E1 屬於後段。

**切分**（`buildEventSummary()`，純函式）：
- 各段攻略＝該段第一個里程碑 → 該段出擊過的關卡全部歸零。仍有 `seen:` 守衛的關卡代表下一段
  血條已武裝，不算打完；未打完的段算到該段最後一次出擊後的第一筆餘額（補給／入渠回港才扣），
  並在各關區段末尾列「E{n} 未歸零」。
- 攻略後＝各段歸零後、下一段開打前仍有出擊的時間窗（撈船等），多個窗合併一列、期間逐窗列出。
  段間沒出擊的空檔只有遠征收入，不計。跨段的區段（前段打完 → 後段開打）不顯示差值。
- 出擊時刻取自 `db.sorties`（只讀最早一次活動之後、world ≥ 10 的列）：被設為「不記錄的海域」
  的出擊與尚未被面板投影的戰鬥不會算進攻略後。
- 任一段不可考，合計也不可考（不以 0 頂替）。

## 離散資材分帳（`utils/material-ledger.ts`，資源紀錄分區的 `.rl-ledger`）

高速建造材、高速修復材、開發資材、改修資材不會自然回復，期間內的增減幾乎都對應一個動作。
`buildMaterialLedger()`（純函式）對一段期間輸出每種資材的
`期初 + 收入 − 支出 + 未歸因 = 期末`，恆等式恆成立（測試逐案驗證）。對不到來源的差額一律
歸「未歸因」，不猜是購買或其他來源；欄位固定顯示、不可隱藏、不改名，正負號一律顯示。

**期間與計入邊界**：期間沿用分區上方同一組期間控制項（含「只看這次活動」的指定期間）。
期初／期末取期間兩端**實際存在的餘額樣本**，頁面上寫的是這兩筆樣本的時刻，不是選單的期間。
各來源（工廠、入渠與改造、遠征、任務領獎）同一條規則：`期初樣本 < ts ≤ 期末樣本`。期初那一刻的事件已經
反映在期初餘額裡，不能再算一次；期末那一刻的事件已反映在期末餘額裡，必須算。期間內不足兩筆
樣本（或期末不晚於期初）回 null，介面寫「不可考」與原因，不以 0 頂替；資源序列整個為空時沿用分區原有的空狀態。

**最新餘額之後的紀錄**：餘額只在回母港（`api_port/port`）與 `api_get_member/material` 取樣，所以在入渠或
工廠畫面的動作要等下一筆餘額才能對帳。期間一路到最新樣本時，頁面另寫「最後一筆餘額之後還有 N 筆紀錄」
（`countRecordsAfter()`），不默默略過。分區收到餘額或分帳相關封包的 `kc:live` 通知後，等 1.5 秒（餘額由
background、紀錄由面板投影寫入，與通知的先後不保證）重讀餘額序列與分帳來源再重畫；活動清單與篩選不重建。
面板的高速修復材在入渠用桶當下就扣 1（`GameState.useBucket()`），不必等回母港。

**各來源**：
- 支出（工廠）：`db.factory` 的 `used[]`（八項精確消耗）依 `kind` 分入開發、建造、改修、高速建造四欄，
  **只取該動作真的會消耗的資材**（`FACTORY_CONSUMES`）：開發＝開發資材；改修＝開發資材、改修資材；
  建造＝高速建造材、開發資材；高速建造＝高速建造材。理由：`used` 是「上次已知餘額 − 回應後餘額」，
  會吸進期間內其他減少（例如入渠用桶）；入渠已另有紀錄，不濾會重複計。
- 支出（入渠）：`db.materialUse` 的 `bucket` 每筆＝1 個高速修復材，歸「入渠」欄。
- 支出（改造）：`db.materialUse` 的 `remodel` 存艦實例 id 與改造前 master id，讀取端用 `remodelStep()`
  查改造消耗表（`remodelCostResolver`），開發資材、高速建造材、改修資材歸「改造」欄。查不到
  （master 未載入、已是最終形態）不計入，計 `counts.remodelUnknown`，頁面寫「N 次改造查不到消耗，未計入」。
  消耗量是外部參照資料而非封包欄位，所以介面標「推算」（數字前加「≈」）；但開發者真實資料的 7 次
  改造段落已逐一吻合（北上改二 55／550、Béarn改 60／40、狭霧改 20／38 等），所以標推算而非不可考。
  表日後修正時不必改已存資料。
- 遠征收入：`db.expeditions.items` 的 `id` 即回航道具的 `api_useitem_id`，1–4 對應道具目錄的
  高速修復材、高速建造材、開發資材、改修資材（目錄的 `countSource.apiId` 減 1 即餘額索引）。
  投影時 flag 1–3 已存成 useitem id 1–3（見 [expeditions.md](expeditions.md)），其他 id 一律忽略不解讀。
- 任務收入：`db.questObserved` 的領獎時刻配任務目錄的報酬文字（`materialQuantity().fixed`）。
  **只計確定報酬**：擇一報酬不計。無法確認是哪個任務的領獎回 null、不計入收入，並在頁面上寫
  「其中 N 次無法確認報酬，未計入」——營運重用編號（遊戲任務標題與目錄不符，目錄報酬屬於舊任務）、
  沒有標題可核對的期間限定任務（每年內容不同）、目錄沒有的編號都屬此類。標題來自
  `db.questSeen.title`。任務領獎只能乾淨地歸「該次所有資材都確認」或「有任一項無法確認」，
  後者整次計入 `questUnknown`，已能確認的資材仍照計。

**未歸因的內容**：勳章交換、禮物箱、活動報酬等尚未拆出的來源都在這一欄，這是預期行為。
入渠與改造的紀錄從 DB v16 開始累積、不回填，更早的用量仍在這一欄。要拆哪一項取決於這一欄實際的量，有真實封包樣本後再逐項補。
**工廠與遠征兩張表由面板投影**（`EventProjector`），任務領獎（`questObserved`）與餘額序列由 background
擷取：面板久未開啟時，那段期間的工廠支出與遠征收入尚未寫進表，差額會暫落在未歸因，補投影後才會歸位。

**版面**：整塊是原生 `<details class="rl-ledger" open>`，只建一次；`draw()` 只重繪
`.rl-ledger-body`，玩家收合的狀態不會被洗掉（design-guidelines §4.2）。來源表（只讀最早樣本之後的列）
在餘額讀完後獨立 try 讀取，失敗只讓這一塊顯示載入失敗訊息，不拖垮上方圖表與清單；讀取期間
顯示「載入中」。收入、支出、未歸因三組之間以 1px 分隔線加寬欄距（§4.1.2）；支出組含工廠四欄與入渠、改造；英文欄名縮寫（Exped.、Dev.、Rush、Dock）是為了三語都放得進內容寬度；收入與支出的色彩沿用
資源紀錄自己的 `rl-gain`／`rl-drain`。離線預覽的分帳區塊使用合成的工廠、入渠與改造、遠征與任務領獎事件
（最近 30 天），餘額仍取自合成序列。
