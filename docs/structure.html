Fleet Chronometer — 架構規格

MV3 瀏覽器擴充：被動觀察《艦隊これくしょん -艦これ-》自身的 kcsapi 流量， 於本機重建遊戲狀態、預測戰鬥、歸檔歷史。純前端、無後端、不上傳。 本文件的目標是讓一位沒看過原始碼的實作者（人或 AI）能據以重建等價的系統。

00如何使用本文件

本文件是什麼

  • 是：契約、不變量、狀態機、資料 schema、已用真實封包驗證的事實、 以及「曾經改壞過所以不准改回去」的 guardrail。
  • 不是：逐行程式碼、UI 像素稿、每個決策的完整敘事。 決策脈絡在 docs/engineering-log.md，UI 量表在 docs/design-guidelines.md。
權威順序

衝突時一律以下列順序為準：
① 原始碼 → ② tests/ → ③ 本文件 → ④ CLAUDE.md / AGENTS.md → ⑤ docs/engineering-log.md。

理由：測試是唯一會在 CI 上失敗的文件。本文件描述「應該長成什麼樣」， 測試證明「實際長成什麼樣」。

重建順序（建議 checklist）

  1. 建立 WXT 專案骨架、wxt.config.ts（含 §19 的 manifest 與 build hook）與三語 public/_locales。
  2. 實作 utils/db.ts（§8 schema v12），先讓 tests/db-schema-migration.test.ts 等價測試通過。
  3. 實作 utils/kcsapi.ts、utils/runtime-message.ts、utils/idle-capture-queue.ts（§4）。
  4. 實作兩支 content script（§4）。此時應能在 SW console 看到 kc:api 訊息。
  5. 實作 utils/ingestion-persistence.ts ＋ utils/background-ingestion-lifecycle.ts（§6）， 再把 background.ts 的 ingestEvent() 接上去。
  6. 實作 utils/state.ts 的 GameState（§12）。先只做 master／port／艦隊， 用 samples/ 的真實封包在 node 上驗證。
  7. 實作 utils/battle.ts（§13），用真實戰鬥封包對照 rank／MVP／終末 HP。
  8. 實作 utils/event-projector.ts ＋ utils/projection-cursor.ts（§9）與 utils/state-recovery.ts（§11）。
  9. 實作面板（§14）。到此為止即 M1–M3 的最小可用系統。
  10. 實作 utils/event-pruning.ts（§10）與 postProcessEvent() 其餘副作用（§7）。
  11. 實作 popup、overview 殼與各分區（§15、§16）。
  12. 實作備份／還原／保留規則（§18）。這一步最容易造成資料損失，務必先寫測試。
重建時最容易做錯的四件事
  1. 把擷取寫成主動請求。任何 fetch／重放／改寫遊戲流量都是紅線（§1）。
  2. 繞過 ingestEvent() 直接寫 db.events。去重、狀態機、recovery 全部會失效。
  3. 把 db.snapshot 餵進 EventProjector。snapshot 只是 GameState baseline，投影會產生重複 derived rows。
  4. 猜測未驗證的封包欄位語意。本專案已被 API 格式坑過兩次，見 §23。

01產品定義與硬約束

一句話：攔截遊戲自身的 kcsapi 回應 → 於本機 reduce 成遊戲狀態 → 面板即時顯示艦隊／遠征／入渠／基地航空隊／關卡進度與戰鬥預測（終末 HP、rank、MVP、 大破警告）與燃彈估算 → 歷史歸檔成可查詢、可繪圖、可備份的本機資料庫。

五條設計原則（硬約束，不可協商）

原則內容實作落點
1. 被動擷取 只攔截遊戲自身流量，絕不重放／修改／代發請求；不延遲、不重排、不改變遊戲行為。帳號安全紅線。 entrypoints/interceptor.content.ts（clone response，永不 await 原始流程）
2. token 不落地 api_token 在 bridge 層剔除，永不寫入 DB、不出境；不上傳任何資料。api_verno 同時剔除。 bridge.content.ts（第一道）＋ background.ts（第二道）
3. 擷取與 UI 解耦 資料落地於 SW 寫入的 IndexedDB 事件日誌；面板只是訂閱者＋重放者，關閉期間不漏資料。 SW 視為隨時會死，不持跨事件狀態（任何跨事件狀態必須落地）。 db.notified、db.meta['game-page']、resourceMarks['gauge-seen']
4. 核心零瀏覽器依賴 utils/state.ts ＋ utils/battle.ts 不含 chrome.*／DOM， 可獨立編譯、用 node 餵真實封包測試。 大多數 utils/*.ts（見 §17 純度欄）
5. 權限精簡 安裝時權限只有 alarms、notifications、scripting、 activeTab、tabs，且 host permission 一律為空。 wxt.config.ts ＋ tests/manifest.test.ts 常駐斷言

被動性的具體定義

擴充不得加入任何會做下列事情的程式碼：

  • 變更送出的遊戲請求（method、URL、header、body 皆不可）
  • 變更收到的遊戲回應（遊戲拿到的 Response 必須與沒有擴充時完全相同）
  • 注入遊戲指令、自動化玩家操作
  • 延遲、重排、重送遊戲請求

唯一允許的介入是觀察：Response.clone() 取副本、XMLHttpRequest 的 load 事件讀 responseText。連讀取大字串都刻意延到 idle slice，避免與遊戲 renderer 競爭 （見 §4）。

未驗證資料的處理原則

不猜

沒有真實封包佐證的欄位語意，一律：保留原始值、回 null、 或 UI 顯示「不可考」。不得以 0、最小值或推算值頂替。

已被此原則救回的例子：節點字母（兩種推算法皆被真實資料否證 → 改查表）、 節點類型（改用查表，查不到回 null）、活動標籤語意（值全 0，標為未驗證）、 資源餘額差分（無樣本 → 顯示「不可考」）。

缺席值語意（跨功能一致）

  • 排序時缺值一律排最後，不論升冪或降冪。
  • 統計算不出來（查詢範圍內沒有樣本）一律顯示「不可考」。
  • 「本機擷取沒有這個欄位」與「值是 0」是兩件事，欄位一律 optional、缺席而非 false／0。

04擷取管線

4.1 interceptor（MAIN world）

fetch hook

const origFetch = window.fetch;
window.fetch = async function (...args) {
    const url = typeof args[0] === 'string' ? args[0] : (args[0] as Request).url;
    const p = getKcsapiPath(url);
    // Request 必須在原始 fetch 消耗前 clone；只啟動非同步讀取，絕不 await，
    // 因此不會延後或改變原始 fetch 的回應／錯誤傳遞。
    const reqBody = p ? readFetchRequestBody(args[0], args[1]) : null;
    const res = await origFetch.apply(this, args as Parameters<typeof fetch>);
    if (p && reqBody) {
        try {
            const responseCopy = res.clone();               // 必須在遊戲讀取前 clone
            void reqBody.then(body =>
                captureQueue.enqueue(p, body, () => responseCopy.text()));  // .text() 留到 idle
        } catch (error) {
            console.warn('[KC-Monitor] 無法複製 fetch 回應，略過此筆', p, error);
        }
    }
    return res;                                              // 原封不動回傳
};
不變量
  • 遊戲拿到的 Response 物件與沒有擴充時完全相同（回傳的是 res，不是 clone）。
  • 擷取路徑上的任何例外都只 console.warn 並略過該筆，絕不可冒到遊戲的 fetch。
  • reqBody 只啟動、不 await；.text() 延到 idle slice。

XHR hook

兩個實際踩過的陷阱，重建時必須複製：

  1. { once: true } 是必要的。若遊戲重用同一個 XHR 實例送出下一筆請求， 留著的舊 listener 會在下一次 load 時與新 listener 一起觸發， 此時 this.responseText 已是新請求的內容，卻會被標上舊的 path 重複入列。
  2. open() 時要先 flush 上一筆未讀的 response。 正常情況每個 API 都是新 XHR、responseText 可留到 idle 才讀； 但遊戲若重用 XHR，open() 會清掉上一筆 response。故 open() 先呼叫 this.__kcPendingResponse?.read()（該 read 具快取）強制 materialize。

IdleCaptureQueue（utils/idle-capture-queue.ts）

存在理由：初始登入會連續回傳 start2／port／require_info 等多 MB 封包。 不能只把 postMessage 包在 setTimeout(0)——XHR 的 load callback 仍會同步 materialize responseText，下一輪 task 又會一次送完所有待處理封包。

  • 每個 idle slice 只處理一筆，保序。
  • 排程用 requestIdleCallback(cb, { timeout: 1000 })；不支援時 fallback 為 setTimeout(cb, 50)（仍維持單筆與順序）。
  • 輸入靜默窗：INPUT_QUIET_MS = 750。監看 pointerdown／keydown／ wheel（capture、除 keydown 外 passive），使用者操作後先留一段安靜時間再處理， 避免與遊戲的介面轉場繪製競爭。nextEligibleDelayMs() 回傳仍需等待的毫秒數。
  • 刻意不在剩餘很短的同一個 idle slice 立即重排（defer 走 setTimeout）， 避免載入海域等連續繪製期間反覆取得短 idle budget 而空轉。

傳出格式

window.postMessage(
  { __kc_monitor__: 1, path, req: reqBody, apiText: text },
  location.origin,          // 明確指定 targetOrigin，不用 '*'
);

傳原始文字而非解析後的物件：structured clone 只需處理字串，不會在遊戲 renderer 深拷貝 start2 這種多 MB 的巢狀物件。解析留給 service worker。

4.2 bridge（ISOLATED world）

這支腳本承擔五件不相干的事，全部是「必須零額外授權」的功能：

職責實作要點
封包轉發 驗 e.source === window && e.origin === location.origin → Object.fromEntries(new URLSearchParams(d.req)) → delete req.api_token; delete req.api_verno; → createKcApiRuntimeMessage() → sendKcApiRuntimeMessageWithRetry()
關閉分頁前警示 標準 beforeunload ＋ e.preventDefault()。只在 isOutermostGameFrame() 為真時安裝（讀不到 window.parent.location ＝跨源＝最外層）。
靜音狀態下行 browser.runtime.connect({ name: PORT_MUTE }) 長連線。 斷線後延遲 250ms 重連一次（SW 被回收會斷線，不重連則靜音鈕對該分頁永久失效）； connect() 本身丟例外才代表 extension context 已失效，不再重試。
Esc 轉發 只轉發 Escape，{ passive: true, capture: true }、 不 stopPropagation／preventDefault，遊戲照樣收到原本的事件。
遊戲畫布量測 父頁問一次才答一次；驗 e.source === window.parent。 取所有 <canvas> 中 width≥200 && height≥150 的最大者， 量不到回 null（父頁退回不裁切，不猜矩形）。
為什麼 beforeunload 掛在遊戲框而非 DMM 頂層頁

掛在頂層 DMM 頁需要 optional host permission，全新安裝、還沒授權過的使用者就完全沒有保護—— 對「防止手滑關掉進行中的出擊」這種關鍵功能不可接受。掛在 kancolle-server.com 是 manifest 靜態注入，安裝當下即生效。

已知代價，刻意接受：跨源 iframe 掛 beforeunload 在 Chromium 有已知的 「按取消後又跳一次」問題（crbug.com/1119438）。曾嘗試用 playwright-core 重現， 但 CDP 自動化關閉分頁本來就不觸發 beforeunload，故未能本機重現。 零權限、可能跳兩次 優於「單次跳窗但需要先授權」——沒有保護才是真正的風險。

4.3 傳輸 envelope 與 retry

export interface KcApiRuntimeMessage {
    type: 'kc:api';
    captureId: string;      // crypto.randomUUID()，一次擷取一個，retry 不重生
    ts: number;
    path: string;           // 已去 /kcsapi/ 前綴
    req: Record<string, string>;   // 已去 api_token / api_verno
    apiText: string;        // 原始 response text，未解析
}

// 只在第一次傳送失敗後等待並重試一次；同一個 message 物件直接重用。
export async function sendKcApiRuntimeMessageWithRetry(
    message: KcApiRuntimeMessage,
    { send, retryDelay }: RuntimeMessageSender,
): Promise<void> {
    try { await send(message); }
    catch { await retryDelay(); await send(message); }   // retryDelay = 300ms
}
retry 的正確性來源

SW 若在寫入途中被回收，訊息通道會以錯誤關閉 → bridge 重試一次 → 因為 captureId 相同， db.events 的 &captureId unique index 會去重，不會產生第二筆 raw event。 這就是為什麼 retry 必須重用同一個 envelope、絕不可重新產生 UUID 或時間戳。

4.4 background 接收端

  1. 若 msg.apiText 是字串 → parseKcsapiResponse()；解析失敗只 warn 並略過該筆 （保留舊 bridge 的 msg.api 相容路徑，讓擴充重載後尚未 F5 的遊戲分頁不漏事件）。
  2. token 的第二道防線：淺拷貝 req 後再 delete api_token / api_verno。 不信任上游已經處理乾淨——這是 ingestEvent() 之前最後也是唯一的關卡。
  3. replyWhenSettled(ingestEvent({...}), sendResponse, reportIngestFailure)： ingestion 完成後才回覆，讓通道開到寫入結束（見上面的 retry 正確性）。

utils/kcsapi.ts 的 path 正規化

  • getKcsapiPath(url)：URL 含 /kcsapi/ 才回傳其後的路徑（形如 api_port/port），否則回 null。
  • parseKcsapiResponse(text)：剝除 svdata= 前綴 → JSON.parse → 取 api_data（無則整包）。
MV3 訊息回覆

所有 onMessage 回覆一律走 utils/runtime-reply.ts 的 replyWhenSettled(work, sendResponse, onError?)，該函式回傳 true。 不可回傳 Promise：那只有 Chrome 148 起才支援，舊版會讓 sender 立刻收到 undefined 而不是真正的回覆。tests/runtime-reply.test.ts 會掃描 onMessage 契約。

05Provider 合約

ApiEventRow 是「擷取來源」與「下游」之間的正式邊界。下游（GameState、面板、 overview）對封包從哪裡來一無所知也能運作。

export interface ApiEventRow {
    id?: number;
    ts: number;
    path: string;                    // 已去 `/kcsapi/` 前綴與 `svdata=`，形如 api_port/port
    api: unknown;                    // 已 JSON.parse 且取出 api_data（無則整包）
    req: Record<string, string>;     // 已剔除 api_token、api_verno
    captureId?: string;              // bridge 傳輸識別碼；歷史事件沒有，故 optional
    postProcessState?: 'pending' | 'processing' | 'done';
    source?: 'main' | 'native' | 'proxy';   // 未標記者視為 'main'
}

不變量

  • path 已正規化、api 已解析、req 無 token／verno。
  • 帶 captureId 的 events 以 unique index 去重；同 captureId 若 path 或 ts 不同即拒絕為 collision（不是覆寫、不是新增）。
  • 任何 provider 都不得繞過 ingestEvent() 直接寫 db.events。
  • 唯一例外：單場 JSON 匯入與兩種 CSV 匯入——它們借用 event ID 但不寫 raw event（見 §9.4）。
擴充新來源的方法

未來要加 Native Companion（runtime.onConnectNative）或 Proxy 來源時： 在 background.ts 各自加一個 listener、構造同格式的 row、標上對應的 source， 同樣呼叫 ingestEvent()。下游一行都不用改——裁剪、通知、 db.events → GameState → 面板全部沿用。

API

規則

  1. 先落地再處理：新 event 必先以 postProcessState: 'pending' 保存。
  2. captureId 去重：同 captureId 只允許相同 path 與 ts； 不同即丟 collision error（可由 createCollisionError 客製）。
  3. claim 才做副作用：pending → processing 必須在 transaction 內完成； 取得 claim 者才執行廣播、snapshot、通知、裁剪。成功標 done，失敗歸還 pending。
  4. 已 done／processing 的 duplicate 直接跳過，不重複執行副作用。
  5. SW 啟動 recovery：先把帶 captureId 的遺留 processing 歸還 pending，再依 event ID 順序重跑所有 pending。
  6. 單一序列 queue：新 ingestion 與 recovery 共用同一條 promise chain； 新 ingest() 先 await recoveryPromise。recovery 失敗則新 ingestion 一律 reject。
  7. listener 不等 recovery 才註冊：BackgroundIngestionLifecycle 在 defineBackground 一開始就建構，但 onMessage listener 立即註冊， 避免 SW 剛被喚醒時漏接訊息；交進來的 ingestion 在 queue 中等待。
歷史事件不是待處理工作

v10 之前的 events 沒有 captureId 也沒有 postProcessState， 且刻意不回填。recovery 只處理帶 captureId 的列， 否則整個歷史都會被當成待重跑的工作。

冪等性要求

因為 recovery 會重跑同一筆事件的 post-processing，所有副作用都必須冪等：

  • 通知：使用固定 notification ID（createEventNotificationId(eventId, purpose)）， 重跑只會覆寫同一則。
  • snapshot、derived rows、resources、shipObtained：一律 put 或 add-if-absent。
  • alarms：以穩定 key 命名（艦隊編號／渠號，不用玩家可改的 api_name）。

  1. 保留即將被誤刪的入渠 alarm：先記下 clearAll() 前仍在未來的 /^入渠ドック\d+ 修理完了$/ alarms；重建迴圈跑完後，快照沒涵蓋到的原樣續存。 理由：這筆 port 之前才剛建立的入渠 alarm，其 api_ndock 狀態可能還沒同步反映， clearAll() 會刪掉它而重建迴圈不會補回。殘留頂多誤發一次通知（Chrome 觸發後自動移除）， 「不會靜默漏發」更安全。

  3. 疲勞回復：自然回復每 3 分鐘 +3、上限 49。回復 tick 的相位未知（伺服器全域計時）， 取上界 ceil((49 - minCond) / 3) * 3 分鐘——通知響起時保證全隊已回復到 49，不會提早誤報。

13.3 predictRank（clean-room 重寫，已用真實資料校準）

損害率 ＝ (開戰殘HP合計 − 現在殘HP合計) / 開戰殘HP合計。由上而下：

  1. 敵全滅 ＋ 我無轟沈 → S（不吐 SS）
  2. 敵全滅（我有轟沈）→ A（edge 未實測）
  3. 我無轟沈 ＋ 敵數 > 1 ＋ 敵沉 ≥ floor(敵數 × 0.7) → A （floor 非 ceil，1-1 boss 實證）
  4. 敵損害率 > 我 × 2.5 → B
  5. 敵損害率 > 我 × 0.9 → C
  6. 其餘 → D

15.3 跨分區慣例（硬約束）

  1. 有輸入框的分區一律不能全量重繪。整塊重繪會讓輸入框失焦、捲動位置與展開狀態被洗掉。 作法：控制項只建一次（事件綁定一次），篩選／排序變更時只重繪結果子容器 （.rs-body／.eq-body／.el-body／.rl-body／.sp-list 之類）。 適用：ship-picker、ships、equipment、sortie-log、 resource-log、exped-log。
  2. 一律先畫殼、再 await 資料。render() 第一件事是塞 shell HTML 並綁好事件， 之後才讀 DB。先讀後畫會讓「讀取卡住」（例如 Dexie 版本升級被其他分頁擋住） 變成整個分區空白、連工具列都按不到，且看不出原因。
  3. 折疊一律用原生 <details>。不要用 transform: rotate 做展開箭頭—— rotate 在 prefers-reduced-motion 下要關掉，關掉後兩態長得一樣，狀態訊號就消失了。
  4. 缺席值不是 0、不是最小值（見 §1）。
  5. 語意色不可跨功能挪用：損傷色（--dmg-*）、標籤狀態色（--sally-*）、 資源增減色（--res-gain／--res-drain）分屬不同語意，混用會互相稀釋視覺意義。
  6. 沒有真封包佐證的欄位語意一律回 null／顯示原始值，不猜。

15.4 各分區的關鍵事實

活動作戰板（event-ops ＋ utils/event-plan.ts）

  • 機制前提：標籤是船身屬性非編成容器；一艘船同時只有一個標籤、貼上不可逆； 貼標時機是出擊，由「關卡＋路線」決定；api_sally_area 是唯一權威。 allowedTags（哪些標籤能走這條路線）與 grantsTag（無標籤船走這條路線會被貼上什麼標籤） 是兩件不同的事。
  • 三層：Layer 1 標籤總帳（從 api_sally_area 即時分群，零輸入且權威）→ Layer 2 計畫（手輸）→ Layer 3 檢查（純函式）。
  • 燈號語意：ok＝已持有本關允許的標籤；blocked＝持有別的標籤走不了； willStamp＝無標籤船即將被不可逆消耗（不是「安全可調度」）； allowedTags 未填一律 unknown，不可判紅。
  • 「計畫」與「現實」是兩個維度，必須並排顯示（曾被使用者回報三次以為是 bug）。 plannedByTag() 刻意不去重（同艦排進兩個關卡要在兩邊都看得到）； 計數用 sallyBudget()（那支有去重）。
  • 實際貼標觀測（observeGrantedTags()）：只認 0→N 的轉變， N→M 不採信（更可能是漏收封包）；只警示 ＋ 一鍵套用，絕不自動覆寫。
  • 鎖定規則：標籤一旦「已確立」（實際已有船帶著它），其名稱與相關關卡的 allowedTags／grantsTag 轉為唯讀，需明確按「解除鎖定」才可再編輯。
  • mapKey = areaId * 10 + mapNo。reconcileStages() 改版不得丟資料： 有 mapNo 照 mapNo 對應、沒有的用 guessMapNo(label) 反推、對應不上但填過東西的列保留在末尾。

艦娘全覽（ships ＋ utils/ship-roster.ts）

  • 十九個排序欄位，缺值一律排最後。裝備欄一律畫滿真實槽數、空槽畫虛線空框； 補強增設無孔時整格不畫。
  • 近代化改修上限 ＝ master 的（最大 − 初期），已用叢雲改二 420 逐項核對。 api_kyouka 後三格（運／耐久／對潛）無可比對上限，只能判斷「有沒有加過」。
  • 補強增設特殊類別：api_mst_equip_exslot_ship 的 key 是裝備 master id 而非類別 id，值以 api_ship_ids／api_stypes／api_ctypes 三種方式指定對象—— master 必須存 ctype，否則艦級條件全部漏判。已對全 862 艘図鑑內艦驗算。
  • 素質「不含裝備」是估算：裸值＝顯示值減裝備 master 自身加成， 但裝備ボーナス（隱藏加成）已計入顯示值卻不在裝備資料裡，相減後會偏高，UI 已標示。
  • 先制對潛是全功能唯一的推算值（遊戲不送旗標）：依 wikiwiki 機制頁轉寫， 海防艦／輕空母／例外艦（Fletcher 級 ctype 91、John C. Butler 級 ctype 87）／ 其餘四類規則。UI 提示須保留「推算」字樣。開幕雷擊則是事實：裝備特殊潜航艇（類別 22）即成立。

  • master 三個關鍵欄位：api_sortno＝図鑑番号； api_aftershipid 是字串（'0' 代表無後續，當 number 比對會靜默失效）； api_mst_shipupgrade.api_original_ship_id 才是改造→基礎形態的可靠解法 （純走 api_aftershipid 反向圖覆蓋率僅 94%）。 可逆轉換改裝會讓 aftershipid 形成環（如 Glorious 戦艦⇄正規空母）， 反解必須用帶 visited 的圖搜尋，不能用單鏈。

資源紀錄（resource-log）

  • 兩個貫穿設計的事實：(1) 封包只給餘額，任何「花了多少」都是兩個時刻的餘額相減， 算不出來一律「不可考」；(2) 歷史無法回填（v12 起才有序列）。
  • 擷取落在 background 而非 EventProjector（與其他四張 derived tables 相反）： 資源列不需要 GameState 上下文，價值在連續，故與 db.snapshot 同層。 取樣來源只認帶完整八項的 path（api_port/port、api_get_member/material）； 任一項不是有限非負數字則整筆放棄。
  • gauge-seen 是守衛而非里程碑：必須先觀測「未歸零」才武裝， 之後的歸零才算數，不能是記憶體變數，只能落地（SW 隨時會死）。
  • 趨勢圖是使用者指定的形狀，曾明確否決「八張小圖各自 y 軸」，不要改回去： 最上方一張大圖、八條線、圖例即開關；multiChartGeometry() 的 y 值域 只由「顯示中」的序列決定；雙 y 軸不做（沒有共同基準）； 序列配色固定順序，資材 i 恆定拿第 i 個色位——開關序列絕不重新分配顏色。
  • 抽稀是純減量不平滑（downsample() 每桶取最後一筆）： 平滑會把「一次活動燒掉十萬燃料」的陡降磨圓。
  • 兩個踩過的坑：hidden 屬性對 SVG 元素無效 （要用 CSS [hidden]{display:none}）；不要用 preserveAspectRatio="none" （非等比縮放會拉伸 y 軸文字，改用等比 ＋ aspect-ratio，線寬用 vector-effect: non-scaling-stroke）。

遠征紀錄（exped-log ＋ utils/expedition-stats.ts）

  • 為什麼期間彙總落在這裡而不是資源紀錄：遠征收入是逐筆事件獲得量（精確可加總）， 資源紀錄的消長是餘額差分——兩者語意不同，混在一起會被拿去互相對照卻對不起來， 缺席規則也相反。
  • 母集合是「紀錄中的」遠征，不是遊戲的完整歷史：面板長期沒開 ＋ raw event 已被裁剪的期間 會永久缺席。

  • 分組鍵是 missionId 不是名稱（名稱隨語言變動）；missionId 為 0 的舊紀錄才以名稱分組。
  • 回航道具欄位語意未經真封包驗證，一律以 id × count 原樣彙總， 不併入四資源小計。

16.2 視窗適應（theater.content.ts ＋ utils/theater.ts）

產品意圖是讓遊戲畫面等比填滿瀏覽器視窗（不是全螢幕、不是手動縮放劇場）。 UI 文案為「視窗適應」／Fit to Window／ウィンドウ適応；程式碼與訊息型別仍沿用 theater 識別名。

  • 遊戲框辨識：DMM 遊戲頁已改版為 SPA，沒有固定 id/class，故靠 src 主機名 ＋ 尺寸（pickGameFrame()）；無命中一律回 null 不亂挑。
  • 顯示的是「遊戲畫布」不是「整個 iframe」：畫布位置由框內 content script 跨源回報， 父頁 clip-path: inset() 裁掉其餘部分並置中。 只信任「直接子框」的回覆（e.source === frame.contentWindow）， 量不到就退回整個框不裁切、不猜矩形。transform-origin 固定 0 0。
  • 標記屬性 ＋ 外部樣式表，不寫 inline style；不用 position: fixed 當主要手段 （祖先的 transform／filter／contain 會變成 containing block）。
  • 工具列固定佔底部一條，絕不覆蓋遊戲畫面。只留進入／離開／靜音／拍照—— 不做 +/−、百分比、1:1、平移鈕（那些會脫離 fit、弄出黑邊）。
  • 永遠 contain／fit：fitZoom() 硬性維持 contain（Math.min）。 cover（Math.max）已被明確否決，未經使用者再次明確指示不得改回，也不得加回手動縮放 UI。 頁面縮放交給瀏覽器原生 Ctrl／⌘ ＋ 滾輪。

popup「視窗適應」

16.3 遊戲靜音

  • installAudioMute() 在 MAIN world（document_start）把每個 AudioContext 的 destination 換成 master GainNode；<audio>／<video> 同理。
  • BGM 路徑不可考時，background 用 tabs.update({ muted: true }) 對整個遊戲分頁保底 （這是 tabs 權限存在的唯一理由，不讀取分頁內容）。
  • 狀態持有者是 SW（db.meta['game-page']），遊戲分頁重載後仍生效。
  • popup 顯示 connected＝目前連上的遊戲分頁數。 0 代表沒有任何分頁跑著新版 content script（擴充更新後未 F5），此時靜音一定無效—— 這種「靜靜沒反應」最難查，故直接寫在選單上。stateKnown 區分「查不到狀態」與「確實是 0」。

16.4 拍照（utils/screenshot.ts）

  • 只擷取遊戲畫面、不含 DMM 頁面其餘部分。裁切矩形絕不重新推算： 兩個入口（popup／視窗適應工具列）都呼叫已校準過的 measureScreenshotRect()； 量不到畫布時回 rect: null，誠實回報找不到，不猜矩形。
  • 權限是 activeTab（不是 <all_urls> 也不是既有的 optional host permission）—— captureVisibleTab() 只認 <all_urls> 或 activeTab， 不認一般 origin host permission（這正是第一版拍照「已授權仍失敗」的根因）。
  • 「沒有回覆」與「量不到遊戲畫面」是兩件事，訊息不可混為一談： sendMessage 收不到回覆時是 resolve 成 undefined（不是 reject）。

每個 schema 版本的 restore 表組合各自固定——舊檔不因缺少後來新增的表被拒， 新檔也不得少帶或夾帶。

18.3 還原的前置條件

匯入不是 merge，也不會警告後覆寫
  1. 第一次匯入只接受乾淨環境：沒有 raw events、沒有 notified、 沒有 projection metadata、目標 rows 為空。
  2. 後續只有 meta['backup-restore'] marker 證明的 complementary split file 可接續（restore 已匯入 → 可再匯入 replays，反之亦然）。
  3. validation、destination preflight、所有 writes、event-ID sequence reservation／high-water 與 import marker 全部在同一個 transaction，任一失敗完整 rollback。
  4. BackupValidationError（格式錯）與 BackupDestinationError（環境不符） 必須能由 UI 明確分流；被拒時 transaction 尚未寫入任何使用者資料， 既有資料與 event key generator 都保持原樣。
  5. MAX_RESTORABLE_SOURCE_EVENT_ID = Number.MAX_SAFE_INTEGER - 2： 兩個拆檔各用一個 auto-generated guard 驗證 generator rollback， 之後還要保留至少一個 safe integer 給真正的 ingestion。
  6. meta['game-page']（靜音／語言鏡像）不算「來源不明的既有資料」，preflight 略過。

18.4 為什麼是 File System Access API

Google Drive／WebDAV 的原生 API 需要 OAuth 或 host_permissions，違反權限精簡。 FSA（entrypoints/overview/fsa.ts）零 manifest 權限： 使用者選一個資料夾（可以是 Google Drive Desktop 的同步資料夾）， handle 存在獨立的原生 IndexedDB kc-fsa。 API：fsaSupported()、pickBackupDir()、savedBackupDir()、 forgetBackupDir()、ensureRw()、writeFileTo()。

18.5 重播保留規則（utils/retention.ts）

planRetention() 的保護判定，由上而下：

  1. 手動 ★ 釘選（replays.pinned）
  2. 打撈到新船（firstOwnedDropKeys()，須 source='auto' ＋ observedEventId）
  3. 斬殺（sorties.cleared）
  4. 活動 boss
  5. 所屬海域尚未通關
  6. 皆非 → 只留最近 keepRecentDays（預設 45）天，且保底最近 keepRecentCount 場

斬殺偵測（detectClear()）

在 mapinfo 更新後比對量表，觀測到「未擊破→擊破」就把該圖最近一場 boss 出擊標 cleared。 只在「本次事件流曾看過該圖未擊破」時才判定轉變—— 「一裝上擴充就看到某圖已經是 cleared」不代表剛剛打通。 唯一未驗證：擊破當下遊戲是否即時推一筆 now_maphp=0 的 mapinfo （只影響觸發延遲，不影響判定正確性）。
